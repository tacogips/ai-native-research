# 医療データのLLM利用：施設内処理・管理された外部API・周辺制御の事例と論文

調査日：2026年10月7日。LLMは大規模言語モデル、local LLMは施設や利用者の設備で動かす言語モデルを指す。ここではモデルの学習より、診療記録の非識別化、情報抽出、要約とその周辺の管理を対象にする。

「harness」は、本報告では**入力取得から、モデル呼出し、結果の検査、記録、保存・削除までを制御する周辺システム**と説明する。秘密計算を必須としない方式を含むが、通常の通信・保存の暗号化まで不要という意味ではない。

## 1. 結論と使い分け

医療データを平文で読むAIを施設内に限定する研究・導入例はある。公開提供されるモデルを、病院が契約・接続・権限を管理する外部APIで利用する研究もある。**一般向けの公開チャット画面に識別可能な診療記録を投入し、質問文の工夫だけで守る構成とは異なる。**

参考になる順序は、外部モデルの運用基盤ならStanford、施設内の情報抽出ならLLM-AIx、複数の文書・画像・音声を一括して非識別化する周辺制御ならMultimodal Anonymizer、実装上の管理策ならKatherLabの現行ツールである。最後のツールは元の論文の評価実装とは別物である。

| 構成 | 誰が平文を読むか | 主に守るもの | なお残る課題 |
|---|---|---|---|
| 施設内モデルだけで抽出・要約 | 許可された施設内AI | 外部送信を減らす | 内部権限、管理者、記録、モデル更新、誤出力 |
| 施設内で識別情報を削除してから外部APIへ | 非識別化AIは原本、外部AIは加工文 | 外部に渡す直接識別情報を減らす | 削除漏れ、希少疾患・時系列からの再識別、前処理での医学的情報の欠落 |
| 専用接続・契約下の外部API | 承認された外部モデル | 接続と処理先、二次利用、契約・運用の範囲を管理する | 提供者側で平文処理される事実、保持条件、外部機能・保守・変更 |
| 秘密計算・ゼロ知識証明を併用 | 方式による | 平文開示の削減、計算結果の検証 | 性能、入力の真正性、証明対象、出力からの漏えい |

## 2. 実装・研究の比較

### 2.1 Stanford Medicine「Secure GPT」：外部モデルを使う共通基盤

**Development of secure infrastructure for advancing generative artificial intelligence research in healthcare at an academic medical center**（JAMIA、2025年、査読済み。2024年公開原稿も保存）では、専用Azure OpenAI環境、病院との契約、ExpressRouteによる専用接続、限定したAPI接続先、鍵保管、非公開のコード管理を組み合わせる。APIは他のプログラムからモデル等を呼び出す接続手段。研究審査を得て、診療記録から術後転倒や精神健康関連情報を解析した。[査読済み全文](https://pmc.ncbi.nlm.nih.gov/articles/PMC11833461/)。

価値は研究者ごとの無管理な送信経路を、中央管理された共通基盤へ置き換える点。専用接続でもモデルは診療情報を平文で処理する。本文の「保持されない」等の説明は当時の構成についての著者の説明であり、現在の全Azureサービス・機能の一律の保証とは扱わない。保存本文のMethods、Use Caseが重要。2024年公開原稿と2025年の最終論文の双方を照合した。

### 2.2 LLM-AIx：病院設備で完結する情報抽出

**A software pipeline for medical information extraction with large language models, open source and suitable for oncology**（npj Precision Oncology、2025年）では、文書準備、文字読取、分割、施設内モデルでの抽出、正解データとの評価を一つの流れにまとめる。llama.cpp等を使い、100件の研究用病理報告から腫瘍・リンパ節・転移の段階情報を抽出して評価した。[論文](https://www.nature.com/articles/s41698-025-01103-4)。

モデルへの入力・出力を評価する仕組みが実装され、設置例として単体GPU等も説明する。**100件の研究データ評価を、院内全患者での本番稼働実績と取り違えない**。小さな別評価での非識別化性能を一般化しない。PDF1～4頁、Methods、評価手順が重要。

### 2.3 Multimodal Anonymizer：複数形式と再検査を組み合わせる

**The Multimodal Anonymizer: a fully local multi-agent AI system for medical data deidentification**（2026年5月初稿、取得v2は9月14日、査読前）では、施設内の複数AI、専用の認識処理、規則による変換、反復検査を組み合わせる。文章だけでなくPDF、画像の文字、顔、ファイル名、付随属性、音声等も対象とする。[公開原稿](https://www.medrxiv.org/content/10.64898/2026.05.28.26353952v2.full)。

250人分のMIMIC-IV由来データに人工的な識別情報を加えた資料と、他の研究用・施設内データ等で16構成を評価。最良の施設内構成はQwen3-VL-235B-A22B-Thinkingで、著者の患者単位指標で98.80%の検出感度を報告する。**全患者から全識別情報を完全に消せたという保証ではない**。小型PCで同じ性能が出るとも推定しない。PDF3～7頁の評価資料と処理構成、結果・補足を参照。

### 2.4 横須賀共済病院：外部送信を避けた医療文書作成

TXP Medicalの導入事例では、患者の診療情報から退院要約・紹介状等の下書きを作る仕組みを、院内GPUサーバーで運用すると説明する。医療者の声として、外部インターネットを経由しない構成、医学用語や出力品質の調整が記載される。[提供者の事例](https://www.txpmedical.jp/case-study/sbir-ai-1-ai/)。

施設内モデルを実際の業務へ組み込む国内例。ただし提供者による紹介であり、権限設定、全記録の保持、事故試験、第三者監査まで公開されているわけではない。オンプレミスという設置方式だけから管理策全体を評価しない。

### 2.5 Imperial College Healthcare：保護環境内のAzureによる退院要約

**Real-World Implementation of Large Language Models for Writing Clinical Discharge Summaries Within a Secure Data Environment: Development and Expert Evaluation Study**（JMIR AI、2026年）は、非識別化した記録、管理された仮想ネットワーク、Azure OpenAIを使い、医師と入力・質問文を設計して評価した。患者識別番号で関連記録を検索する構成も記載する。[論文](https://ai.jmir.org/2026/1/e88816/)。

一方、前処理で日付・場所を削除したため出来事の時系列整理が難しくなる等の限界がある。**検索の患者番号指定は、それだけで利用者の閲覧権限を保証するものではない**。医師による評価と、本番導入時に必要な版管理・継続監視は区別する。出版社の直接取得は空応答だったが、[PMC全文](https://pmc.ncbi.nlm.nih.gov/articles/PMC13379688/)と42頁の受理原稿を別経路で取得し、構成・限界の本文を確認した。受理原稿は出版社の最終組版PDFとは区別する。

## 3. 元論文と現行の公開実装を区別する

**Deidentifying Medical Documents with Local, Privacy-Preserving Large Language Models: The LLM-Anonymizer**（NEJM AI 2025、DOI: `10.1056/AIdbp2400537`）は、施設内モデルで医療文書の個人識別情報を検出・削除する研究。最終論文の直接取得が403だったため、本報告では未取得の最終本文に基づく性能の断定をしない。[最終論文](https://ai.nejm.org/doi/full/10.1056/AIdbp2400537)。

[KatherLab/deidentifier](https://github.com/KatherLab/deidentifier)は関連する公開ツールだが、READMEは**元論文で評価したコードとは異なる独立した再実装**と明記する。論文の性能をこのツールの性能として引用しない。

固定したコミット `d50cfd821774050fde3e3449a77bc47d0d348322` のREADME、設定、記録処理、評価説明を静的に確認した。実データを投入した動作試験や、実装全体の安全性監査は行っていない。

| 実装・説明で確認した管理策 | 根拠と限界 |
|---|---|
| 規則とLLMの検出、削除後の再検査、画面上で人が確認 | READMEと評価説明。検出精度は施設ごとの正解付き資料で検証する必要がある |
| 原文をファイルへ永続保存せず、メモリー上で処理 | READMEの方針。**メモリーに結果を一定時間保持する処理はある**。設定の初期値は15分で、一切の保持がないとは言えない |
| 本文・質問文・ファイル名・結果取得用識別子等を記録から除く | `backend/src/utils/safe_logging.py` の禁止項目を確認。項目名で除外する処理であり、別の項目やメッセージへ原文を混ぜた場合も防げるという証明ではない |
| 本番設定で危険な内容記録設定を拒否 | `backend/src/core/config.py` の起動時検査を確認。開発設定と区別する |
| 応答に `Cache-Control: no-store`、外部解析・追跡部品を入れない | READMEの方針。全通信を監査した結果ではない |
| モデル・文字読取先を設定可能、外部接続なら画面で警告 | READMEの説明。**警告と外部送信の強制禁止は違う**。実運用には通信先制限も必要 |
| 正解データに対する文書単位・文字／範囲単位の評価 | 評価用の処理を公開。機能があることと、対象病院で必要な性能を達成することは別 |

「周辺制御を固める」際には、このように宣伝上の保証ではなく、コードの処理と設定、実測を分けて確認することが重要。

## 4. 新しい論文が示す前処理の限界

**Leveraging Large Language Models for Temporal PHI De-identification in Real-World Clinical Notes**（2026年9月23日公開、査読前）では、30人の肉腫患者の1,148記録、28,431の日付等の注釈を用いる。外部GPTは施設が承認したAzure経由、他のモデルも比較。日付の表記を保つことは容易でも、置換日付を正しくずらし出来事の順序を維持することは難しかった。[原稿](https://www.medrxiv.org/content/10.64898/2026.09.22.26360316v1.full.pdf)。PDF2～5頁に資料・処理条件、結果以降に誤り分析。

PHI（Protected Health Information）は米国法上、個人に結び付く保護対象の健康情報。日本の法的な区分と同一ではない。日付の変換はLLMに任せきりにせず、検出と、規則による日付計算・整合性検査を分ける設計が有用だと考えられる。これは本調査の設計上の推論である。

**Privacy-by-Design Framework for Large Language Model Chatbots in Urology**（2025年）は、泌尿器科の機微な情報を想定し、施設内非識別化、閲覧範囲を守る検索、出典、監査等を整理する。[全文](https://pmc.ncbi.nlm.nih.gov/articles/PMC12688312/)。**設計を論じる総説であり、記載した全対策を実装・検証した本番事例とは扱わない**。

**“Small” Large Language Models in the Hospital: Evaluation Study on Real-World Data in a Resource-Constrained Setting**（JMIR、2026年9月9日）は、フランス語の実際の病院データで小型モデルを評価する読み候補。[論文](https://www.jmir.org/2026/1/e86453/)。非識別化、医療情報抽出等の評価を含むが、本調査の直接取得は空応答。取得できた原本と同じ深さの確認をしたとは扱わない。

## 5. 事例から組み立てる周辺制御

以下は共通点を基にした設計案であり、全項目を一つの病院が実装したという主張ではない。

| 場所 | 制御する内容 | 主な根拠 |
|---|---|---|
| データ取得 | 利用目的・研究審査・利用者と患者単位の権限を確認して必要範囲のみ抽出 | Stanfordの研究審査、厚労省の認証・認可と責任分界 |
| 施設内の前処理 | 本文、画像の文字、顔、ファイル名、付随属性を検出。対応表を隔離 | Multimodal Anonymizer、現行KatherLabツール |
| 外部送信判断 | 未処理・未検証の資料は送信しない。送信先を承認APIに限定 | Stanfordの専用接続。警告だけではなく制御として実装するのは本調査の提案 |
| モデル呼出し | 使用モデル・版、契約、保持、学習への利用、地域、外部機能を固定・記録 | Stanford、Imperialの構成と変更監視の限界 |
| 結果の検査 | 所定の構造に合うか、別患者の混入、日付、単位、薬剤・用量、根拠との一致を確認 | LLM-AIxの出力評価、日付非識別化研究 |
| 送信・確定 | 非識別化結果を再検査。臨床文書の下書きは医療者が確認して確定 | 現行KatherLabツール、Imperialの医師評価 |
| 記録 | 処理者、処理目的、資料の参照番号、モデル・規則の版、結果の採否を残す。原文は通常の診断記録へ混ぜない | 監査設計、KatherLabの記録処理。ただし必要な医療記録の保存とは区別する |
| 失敗・変更 | 外部の別モデルへの自動代替送信を避ける。モデル更新時に同じ評価資料で再検証する | 原本の送信範囲を守る設計とImperialの継続監視の指摘 |

非識別化の評価では、平均的な識別語の検出率だけでなく、**一件でも識別情報が残った文書の割合**、再識別の容易さ、医学的内容を壊す率を別々に見る。非識別化が完了したとAI自身が答えるだけでは受入条件にならない。

## 6. 国の資料と制度上の位置づけ

日本は厚労省の[医療情報システムの安全管理に関するガイドライン第7.0版](https://www.mhlw.go.jp/stf/shingi/0000516275_00006.html)を確認した。企画管理編PDF15～20頁は委託・再委託を含む責任分界とクラウド事業者への確認、システム運用編は認証・権限・証跡等を扱う。これは一般的な医療情報システムの管理指針であり、特定のLLMを承認する資料ではない。概説編、企画管理編、システム運用編、2026年9月Q&Aを保存した。

米国HHSの[非識別化指針](https://www.hhs.gov/hipaa/for-professionals/special-topics/de-identification/index.html)は、定めた識別情報を除く方法と、適切な専門家が再識別リスクを判断する方法を区別する。氏名を削除しただけで、法的に非識別化が完了したとは扱わない。本調査では指針PDFの直接取得は403だった。

契約で保護される処理、研究倫理上の承認、非識別化の判定、臨床的な安全性は別の確認である。ローカルモデルだから自動的に適法・安全になるとも、専用外部APIだから自動的に利用可能になるとも説明しない。
