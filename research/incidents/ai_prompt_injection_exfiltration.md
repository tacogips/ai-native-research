# 業務AIへの指示混入による情報流出：7事例の深掘り

本書の用語：

- **指示混入（プロンプトインジェクション）**：AIが読む文章に命令を埋め込み、AIに利用者の指示として実行させる攻撃。メールや課題票など、AIが後から読む資料に埋め込む形を**間接指示混入**と呼ぶ。
- **持ち出し経路**：AIが集めた情報を攻撃者の通信先へ送る手段。画像の自動取得、リンク、公開コメントなどがこれに当たる。
- **CVSS**：共通脆弱性評価システム。脆弱性の深刻度を0〜10点で示す。**CNA**はCVE番号を採番する組織を指し、本書の事例ではMicrosoftが自社製品の採番を担う。**NVD**は米国国立標準技術研究所の脆弱性データベースで、CNAとは別に独自の点数を付けることがある。
- **MSRC**：Microsoft Security Response Center。Microsoftの脆弱性受付と公表を担う窓口。

## このグループの要点

- 7事例は**すべて研究者による実証**である。実際の攻撃者による悪用や、顧客被害が確認された事例はない。Microsoftは2件のCVEの両方で「悪用なし」と登録した。他のベンダーの悪用状況は、公開資料では確認できなかった。
- 共通の構造は3つの要素の組合せである。第1に、外部の者が書ける入力（メール、URLの引数、Webフォーム、公開の課題票）がある。第2に、AIが利用者の権限で社内データを読める。第3に、ベンダーが許可した通信先や公開書込みが持ち出し経路になる。
- ベンダーの修正は**持ち出し経路を塞ぐ**ものが中心だった。Salesforceは許可URLの強制を入れ、GitHubは公開先への書込みを機密ラベルで止める機能を追加した。Atlassianは、URLの引数から指示が自動実行される動作を止めた。Microsoftは、技術的な修正内容を公表していない。
- **CVEが採番されたのはMicrosoftの2件だけ**だった。Salesforce、Atlassian、GitHubの4件にはCVEが見当たらない。ForcedLeakの「CVSS 9.4」は研究者自身による評価である。
- 報告から公表までの期間は、短い事例で約2か月、長い事例で約8〜9か月だった。ForcedLeakは約2か月、Repromptは約4.5か月、EchoLeakは約5か月かかった。RovoBlastは、Bugcrowdでの公開まで約8か月、Varonisの公表まで約9か月かかった。
- 同種の後続事例は続いている。NVDで「M365 Copilot」を検索すると、2025-06〜2026-09に17件のCVEが公開されており、うち10件が情報漏えいである。GitHub Agentic Workflowsでは、2026-08〜09に重大度「高」以上の勧告が9件公開された。
- 既存記述の訂正候補は9件ある。内訳は、事実の食い違いが6件、補足が3件である。主な内容は、報告日の欠落、原因の単純化、研究者による評価をCVEの評価のように書いた箇所である。

#### 3. 侵入経路と技術的原因

研究者の主張（Invariant）を、欠けていた統制の水準でまとめる [I1]。

- **入口の統制不足**：誰でも書ける公開リポジトリの課題票を、エージェントが利用者の依頼と同じ文脈で読んだ。外部由来の内容を区別する仕組みが無かった。
- **権限の範囲**：エージェントに渡した認証情報は、非公開リポジトリも読める広さだった。作業対象を越える読取りを妨げる仕組みが無かった。
- **出口の統制不足**：外部から見える公開操作への書込みが、利用者の個別承認なしに行われた。実証では「常に許可」の運用が前提だった。
- Invariantは、これをGitHub MCPサーバのコード欠陥ではなく、エージェントの構成全体の問題と位置づけた。そのため、サーバ側の修正だけでは解消できないと述べた。
- 実証のモデルはClaude 4 Opusだった。確定事項と推定：この構成が研究者の環境で成立することは確認された。実際の攻撃者による利用は確認されていない。

#### 4. 影響

実証では、研究者のデモ用アカウント（ukend0464）について、非公開リポジトリの名前、転居計画、給与が公開PRに書き出された [I1]。実在する組織の被害は報告されていない。影響が及び得たのは、公開リポジトリの課題票を読ませ、同時に非公開リポジトリを読める認証情報を渡していた利用者である。

#### 7. 再発防止策とその実施状況

- **研究者の推奨** [I1]：1回の作業で扱えるリポジトリを1つに制限することを勧めた。実行時の方針検査と、接続の継続監視も挙げた。

#### 9. 企業AI基盤への教訓（本調査の推論）

- **認可**：AIエージェントに渡す認証情報は、作業対象のリポジトリだけに限定する。ツール側の内容フィルタは補助にすぎず、認可の代わりにならないとGitHub自身が述べている。
- **承認**：「常に許可」の運用では、公開先への書込みも確認なしで実行される。公開PRや公開コメントなど、外部へ見える書込みは、個別の承認を残す対象として分ける。
- **監査記録**：エージェントが1回の作業で複数のリポジトリを読んだ記録を、検知の材料として残す。

#### 3. 侵入経路と技術的原因

Aim Labsの原報告 [A1] は、Microsoftが備えていた4つの防御が、いずれも境界として機能しなかったと述べた。欠けていた統制の水準で整理する。具体的な注入文、記法、持ち出しURLの構成は、本書では扱わない。

1. **指示混入の分類器**：外部文書に紛れた指示を検出する分類器（XPIA分類器）があった。人間宛ての依頼文を装った指示を見分けられなかった。
2. **外部リンクの除去**：応答から外部リンクを除去する処理があった。別表現の記法が除去対象から漏れていた。
3. **自動取得への対策不足**：利用者のクリックを要しない自動取得の経路が残っていた。
4. **通信先の許可リスト（CSP）**：ブラウザの画像取得先を限定する設定（CSP）があった。許可先の一部が、外部への取得をサーバ側で代行する機能を持っていた。そのため、許可リストが持ち出しの境界にならなかった。

RAG（検索拡張生成、質問に関連する文書を検索してAIの入力に加える方式）の検索に攻撃メールが拾われやすくする補助手段と、出典表示を抑える指示も報告された。本書では手口の詳細は扱わない。

Aimは、この現象を「LLM Scope Violation（範囲逸脱）」と名付けた。社外から届いた権限の低い入力が、AIを介して社内の権限の高いデータを参照させる現象を指す。

Microsoftが直した具体的な箇所は公表されていない。MSRCは「完全に緩和済み」とだけ記載した [M1]。報道によれば、Microsoftの広報担当者は製品を更新したと述べ、追加の多層防御も進めると述べた [N2]。

#### 4. 影響

Aimによれば、持ち出せる範囲はCopilotの文脈に入る情報すべてである [A1]。会話履歴、Microsoft Graph（Microsoft 365の各サービスのデータを横断して扱う仕組み）経由で取得したメール、OneDrive、SharePoint、Teamsの内容が含まれる。攻撃者の条件は、被害者へメールを1通送れることだけだった。実被害は確認されていない。

#### 3. 侵入経路と技術的原因

Varonisの主張 [S1] を、欠けていた統制の水準でまとめる。

- **入口（P2P）**：企業向け検索のURLの引数が、Copilotに指示として実行された。Varonisは、企業向けの追加の防御があるはずの環境で、個人向けと同じ入口が通ったことに驚いたと書いている。
- **検査の時点**：AIの応答を無害化する処理が、生成の完了後に行われた。逐次表示の途中では無害化が間に合わず、外部取得の要求が先に出てしまった。
- **通信先の許可リストとサーバ側取得**：通信先の許可リスト（CSP）に、外部URLをサーバ側で取得する機能を持つ許可先が含まれていた。この経路がサーバ側リクエスト偽造（SSRF、サーバに指定先へ通信させる現象）として働き、ブラウザ側の許可リストを境界にしなかった。

Microsoftが何を直したかは公表されていない。MSRCは「完全に緩和済み」とのみ記載した [S2]。

#### 3. 侵入経路と技術的原因

Nomaの主張 [L1] を、欠けていた統制の水準でまとめる。

- **構成**：問題のワークフローは、課題票を契機に起動し、題名と本文を読み、コメントで返信した。組織内の他のリポジトリ（公開・非公開の両方）を読める権限を持っていた。3つの要素（公開の入力、非公開を読める権限、公開への書込み）が同時に揃う構成だった。
- **入口の統制不足**：攻撃者は認証情報を持たない。公開リポジトリの課題票という誰でも書ける入力を、エージェントが指示として読んだ。
- **防御の限界**：GitHubは投稿前に出力を検査する脅威検出を備えていた。Nomaによれば、1語の言い換えで、この文面ベースの検査が回避された。本書では回避の言い回しは扱わない。
- **出口の統制不足**：非公開リポジトリの内容が、公開コメントとして投稿できてしまった。読取り時の機密区分が、公開への書込みで止められなかった。

GitHubの修正PRは、攻撃の流れを機密ラベルの観点で整理している [L4]。非公開リポジトリの読取りでAIに機密ラベルが付き、公開先への書込みをその機密ラベルで止められなかった点を中核としている。

補足として、公開されている実証の実行（run 23909666039）は、課題票の割当てではなく手動起動だった [L3]。現在の定義ファイルは claude-opus-4-6 を指定しているが、実証時点の設定と同じかは未確認である。 （2026-10-08 再検索: NomaのGitLost原報告の開示欄とGitHubの公開実証・勧告記録を再確認したが、本項目の追加確定情報は確認できなかった。）

#### 7. 再発防止策とその実施状況

GitHubの修正内容（一次資料：GitHubのPR）：

1. **出力側の制御（sink-visibility）** [L4]：書込み先が公開であれば、書込み先の機密ラベルを空にする。そのため、非公開データを読んで機密ラベルが付いたエージェントは、公開先へ書き込めなくなる。これは分散情報フロー制御（DIFC、データに機密ラベルを付けて追跡し、ラベルの付いたデータが許されない先へ流れるのを止める方式）による阻止である。2026-07-08に統合された。
2. **入力側の制御（forcePublicRepos）** [L5]：公開リポジトリで動くとき、すべての読取り方針を「公開リポジトリのみ」に強制する。既定で有効である。ただし、APIの失敗時やトークンが無い場合は制限をかけずに続行する（フェイルオープン）と明記されている。2026-07-08に統合された。
3. **明示的な許可の設定** [L7]：公開と非公開をまたぐ流れが必要な場合は、`private-to-public-flows: allow` を書く。2026-07-12に追加された。
4. **CLI経路の穴埋め** [L8]：`gh` コマンドの代理経路は、既定で全リポジトリを読めていた。MCP経路には制限があったが、この経路には無かった。GitHub自身の試験で、公開リポジトリから非公開リポジトリが読めることが確認された。2026-07-13に修正された。

研究者の推奨 [L1]：利用者が書いた内容を指示として扱わない。権限を最小にする。公開の投稿を制限する。入力を指示の文脈から隔離する。

実施状況：上記はgh-awとgh-aw-mcpgのリリースとして配布された。利用者がどの版を使っているか、設定で許可を広げていないかは、利用者側の確認事項として残る。

## 共通する原因と教訓

### 共通する原因（一次資料で確認できた範囲）

1. **外部の者が書ける入力が、AIへの指示として扱われた**。入口は、メール（EchoLeak）、URLの引数（Reprompt、SearchLeak、RovoBlast）、Webフォーム（ForcedLeak）、公開の課題票（GitHub MCP、GitLost）だった。ベンダー各社は指示混入の分類器や出力検査を備えていた。それでも、人間宛ての依頼や作業を装った指示に対して、文面ベースの検査が境界にならなかった。
2. **AIは利用者の正当な権限で読んだ**。認可を迂回した事例は無い。正当に読める情報が、そのまま持ち出しの対象になった。SearchLeakの研究者は、攻撃者が認証なしに被害者のアクセス権を引き継ぐと表現した。
3. **ベンダー自身が許可した経路が出口になった**。許可されたTeamsの中継（EchoLeak）、期限切れの許可ドメイン（ForcedLeak）、Bingの画像検索（SearchLeak）、画像の取得と外部調査機能（RovoBlast）、正規の公開PRや公開コメント（GitHub MCP、GitLost）がこれに当たる。
4. **出力の検査が、送信より後になっていた**。SearchLeakでは、逐次表示中の描画が無害化処理に先行した。Repromptでは、保護が最初の要求にしか効かなかった。

### ベンダーの修正の型

| 型 | 事例 | 内容 |
|---| ---|---|
| 出口の制限 | ForcedLeak、GitLost | 許可URLの強制、機密ラベルによる公開先への書込み阻止 |
| 入口の自動実行の停止 | RovoBlast | URLの引数から指示を自動実行しない |
| 読取り範囲の制限 | GitLost、GitHub MCP | 公開リポジトリで動くときは公開リポジトリだけを読む（GitLostは既定で有効、MCPのlockdown modeは任意） |
| 内容非公表の修正 | EchoLeak、Reprompt、SearchLeak | Microsoftは「完全に緩和済み」とのみ公表した |

### 企業AI基盤への教訓（本調査の推論）

- **認可**：読取りの認可が正しくても、漏えいは防げない。AIが読んだ情報の機密区分を、出力、道具の引数、リンク、書込み先へ引き継ぐ。「非公開を読んだ後は公開へ書かない」を、文面の判定ではなく機械的な規則で強制する。GitHubの修正はこの方式である。
- **入力の出所の記録**：URL、フォーム、外部メール、公開の課題票から来た内容に、外部由来の目印を付ける。その目印を画面と監査記録の両方に残す。外部から始まった会話は、利用者が確認するまで実行しない。
- **通信先の許可リスト**：許可リストは、ドメインの所有、有効期限、中継機能の有無まで審査する。CSPを持ち出し対策の境界として扱わない。
- **検査の時点**：検査は、描画、外部取得、書込みの前に置く。2回目以降の要求も、後続の自動要求も、すべて検査する。
- **経路の網羅と失敗時の既定値**：同じ権限で動く経路（MCP、CLI、HTTP）をすべて洗い出す。確認に失敗したときの既定値が「厳しい側」になっているかを、経路ごとに試験する。
- **委託先管理**：SaaSのAI機能は、報告から修正まで約4〜8か月かかった例がある（EchoLeak、Reprompt、RovoBlast）。利用者が自分で止められる手段を確保しておく。無効化、接続範囲の制限、記録の取得である。CVEが採番されない修正も多いため、ベンダーの報奨金制度の公開記録やリポジトリも監視対象に含める。
