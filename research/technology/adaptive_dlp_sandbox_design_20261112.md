# 機密情報検知サービスの隔離実行設計

設計日：2026年11月12日。[DLPサービス設計](adaptive_dlp_service_design_20261111.md)の実行境界を具体化する。sandboxは、処理がアクセスできる資源と操作を制限する隔離環境を指す。本稿の構成・数値は採用する設計案であり、構築・侵入試験・性能測定の結果ではない。

**原文の取得、危険なファイルの解析、GPU推論、学習用知識の更新、通知を別の権限に分ける。原文を読む解析処理には外向き通信を与えず、結果の保存と外部操作は管理側で認可する。** 検知が成功したかどうかを、隔離の成立条件にしない。DLPが機密を見逃しても、禁止した送信先へ到達できない構成にする。

## 採用する配置と隔離単位

初期の本番構成は顧客環境内のLinuxを前提に、CPUで行うファイル解析と検知にはgVisorを第一候補として適合試験を行う。試験に不合格なら実行を停止し、Kataまたは専用仮想機械向けに別途承認した実行定義を使う。通常のコンテナへ自動的に戻さない。gVisorの採用は互換性・性能・受入試験の合格を本番投入条件とし、製品名だけで隔離を認定しない。[R1][R5]

GPU推論は解析用の実行環境へGPUを渡さず、顧客専用の計算機に配置した別サービスへ管理側から要求する。初期版では異なる顧客のGPU同時共有・推論要求の混合処理を認めない。これは専有費用を伴う選択であり、GPU自体の完全な情報消去を保証するものではない。顧客を切り替える再割当には機種・ドライバーごとに検証した初期化手順が必要で、未検証なら再割当しない。[R3]

Docker Composeは合成資料だけを扱う単一顧客の開発環境の起動管理に利用できる。本番と同等の隔離を証明する手段にはしない。Kubernetesは環境数が増えた場合の管理手段として選択できるが、実行方式・通信制限・認証情報の非配布を受付時にも強制する。FirecrackerやeBPFを導入の必須条件にはしない。[R1][R3]

| 処理領域 | 分離単位と入力 | 許可する操作 | 与えないもの |
|---|---|---|---|
| 管理部 | 顧客と作業の認可、検査計画 | 環境作成、停止、版の配布、状態確定 | モデルからの任意コード実行、解析結果に基づく権限拡張 |
| 保存先接続部 | 顧客×接続先。取得対象IDと版 | 登録したDrive等から必要範囲を読取り | 原本の削除・共有変更、文書指定の任意URL取得 |
| 抽出部 | 一つの顧客・一つの原文版・一回の試行 | 読取り専用入力、専用一時領域、上限付き出力 | IP通信、DNS、GPU、接続先の資格情報、台帳接続 |
| CPU検知部 | 顧客×作業。抽出済み文字と必要な定義 | A/Bなどの固定検知器、原文位置付き候補の出力 | 任意通信、他作業の入力、許可規則の変更 |
| GPU推論部 | 顧客専用。管理側が送った対象断片・承認例 | 固定モデルの推論、当該要求への応答 | 外向き新規接続、道具実行、顧客横断の状態共有 |
| 検索・改善部 | 顧客×目的×資料集合の固定版 | 認可した確定例の検索、候補版の生成 | 本番への適用、採用試験の正解取得、通信規則変更 |
| 評価部 | 候補版と評価計画、独立した評価資料 | 比較結果を管理部へ提出 | 改善部への試験正解の返却、許可登録 |
| 結果取込・台帳・通知部 | 管理部が確定した顧客と作業 | 出力検証、顧客内台帳への記録、認可した通知 | ワーカー指定の保存先・受信者・任意URLへの送信 |

独立したモデルを使っても同じ顧客内の計算機障害は共有し得る。検知方式の独立性と実行基盤の故障分離を別に管理する。管理部・ホスト・仮想化部・GPUドライバー・鍵管理・結果取込部は信頼対象として更新・監査する。クラウド管理者からも原文を秘匿する要件は、機密計算の別評価が必要であり、通常のsandboxだけでは満たしたことにしない。[R4]

## 原文の搬入と結果の搬出

1. 管理部が顧客、利用目的、実体ID、内容版、必要検知器、適用規則、実行期限を確定する。接続部は読取りに必要な資格情報を外側の保管領域から取得し、原文を顧客別の短期領域へ保存する。資格情報や保存先全体の権限を解析部へ渡さない。
2. 通信・共有領域・権限・資源制限の検証が成功してから、当該原文だけを読取り専用で渡す。ホストのホーム、Docker管理用接続口、クラウドの認証情報取得先、管理API、他作業の領域は公開しない。認可前の準備済み環境には原文も資格情報も入れない。
3. 抽出部は文字・画像・位置対応・処理範囲を専用出力領域へ書く。管理側がプロセス停止と出力確定を確認し、固定した複製を検査してから後段へ渡す。検査中の出力差替えを許さない。
4. 取込部は通常ファイル以外、領域外を指すリンク、絶対パス・親への遡及、機器ファイル、容量超過、不正な文字列構造を拒否する。出力をシェル命令として解釈しない。JSON等の構造検証に加え、作業ID・原文版・範囲・件数を検査する。画像の再解析も隔離した処理へ戻し、取込部自身で危険な形式を展開しない。確認画面は抽出文字を文字列として表示し、埋込みHTML・スクリプト・外部画像を実行または自動取得しない。
5. GPU推論要求は管理側が対象・入力量・要求ID・モデル版を固定して送る。GPU処理に原文取得用URLを指定させない。応答の帰属は接続の認証と管理側の要求記録から決め、応答内の `tenant_id` を信用しない。
6. 候補を全件台帳へ記録し、許可と通知を別処理で評価する。取込側が信頼する顧客・作業の識別子を付与する。検知候補・抽出文字・理由・失敗記録はすべて機密として扱い、通知へは原文を含めない。

取込形式が正しくても、侵害された解析部が誤った本文を返す可能性は残る。既知ページ数との照合、空結果の異常検出、画像と文字の別経路、無作為全文監査で検出を補う。形の検証を内容の正しさや無害性の証明にしない。sandboxは許可された出力経路への機密混入を自動的に防ぐものではないため、出力先も同じ顧客の認可領域に閉じる。

## 通信と外部APIの契約

解析・CPU検知はIP通信と名前解決を禁止する。GPU推論は管理側からの認証された要求と応答だけを受け、外向きの新規接続は拒否する。内部の環境変数による代理設定だけに依存せず、ホストまたは外側の通信設備で直接経路を閉じる。IPv4/IPv6、TCP/UDP、名前解決、クラウドの機械情報取得先、ホストへの接続を試験する。[R2]

外部モデル、外部の埋め込みAPI、秘密鍵の有効性照会は、個別に許可された場合だけ専用の代理部から実行する。代理部は送信先の組織・アカウント・モデル・操作・項目・量・期限を確定し、認証鍵を外側で付加する。文書やモデルが渡す任意URL・認証ヘッダー・転送先は受け付けない。顧客が外部送信を禁止した場合、検知結果が陰性でも送信禁止を解除しない。

許可したサービスでも別組織の保存先への送信は拒否する。接続先の名前解決と接続を代理部で一貫して行い、私設アドレスや機械情報取得先など禁止先へ到達させない。HTTP転送は既定で拒否する。通信取消時は継続中の接続も終了し、再試行を拒否する。代理部障害時は直接接続へ戻さない。[R2]

外部への送信許可は「DLP検査を通った」だけでは出さない。未検知の機密や符号化された情報もあり得るため、宛先・主体・目的・対象データの許可を前提とする。原文を外部推論へ送った場合、内部処理をsandbox化したことを根拠に「原文は外へ出ない」と表示しない。

## 実行定義と資源制御

実行定義は管理側だけが変更でき、内容識別値で固定した配布物、検知構成、通信規則、共有領域、権限、CPU・記憶・出力量・時間の上限を一組で版管理する。特権実行、ホストのプロセス・通信空間共有、不要な機器、管理用接続口、汎用の環境変数継承を禁止する。通常コンテナを使う領域でも、非管理者実行、追加権限の除去、権限昇格禁止、OS呼出しの制限であるseccomp、ファイル操作の制限を適用する。[R3][R6]

初期のCPU抽出枠は2 vCPU、記憶4 GiB、子プロセス64、処理時間5分、一時領域1 GiB、出力256 MiB、圧縮展開深さ3・総件数1,000を開始値とする。許容入力サイズと形式ごとの上限も実行前に固定する。これらは負荷試験用の設計値で、検査可能な文書の保証値ではない。上限超過時は読み取れた範囲と未検査部品を記録する。大容量用の別枠へ再投入できるが、解析部の要求だけで上限を引き上げない。

GPUはモデルごとに必要記憶量・入力長・同時要求数・最大出力量・処理期限を測定して別定義にする。推論中断時の資源回収まで監視し、HTTP要求が終了しただけで計算も停止したとは扱わない。顧客単位の上限と全体上限で待ち行列を制御する。期限超過やメモリー不足を「検知なし」へ変換しない。

## 作成から破棄までの状態管理

`planned → provisioned → isolation_verified → input_attached → running → output_sealed → imported → destroying → destroyed` を管理部が記録する。入力搬入前に隔離を検証する。失敗時には `blocked / timed_out / cancelled / isolation_failed / cleanup_pending` と理由を記録し、既存の `Coverage.failed / partial` へ対応付ける。作業の成功と機密状態の破棄完了を別項目にする。

実行記録には `job_id / attempt_id / tenant_id / object_revision / release_id / runtime_profile_id / image_digest / isolation_policy_version / authorization_generation / deadline / destruction_state` を持つ。環境の内部には管理権限を持つ署名鍵を渡さない。CPU抽出枠の試行を再送した場合は新環境を作り、同一結果の台帳取込は冪等にする、すなわち同じ結果を複数回取り込んでも重複しない。

取消・権限喪失・期限切れでは、管理側が新規処理と結果取込を拒否し、外側から停止して短期資格情報を失効させる。停止できない計算機は通信を遮断して隔離し、再利用しない。遅れて届いた結果は現行の許可を再確認し、取消済み作業へ採用しない。失効中に実行済みだった外部送信は取り消せないため、送信直前の再認可を必須にする。

原文・一時領域・出力は初期設定で終了後直ちに削除し、障害調査用に残す場合でも顧客の明示設定した上限内、標準の最大24時間までとする。業務上保持する検知証拠・確定例は別の保持規則に従う。暗号化した作業別領域を使い、複製・鍵・保存先を管理する。削除命令の成功だけで媒体からの完全消去を保証せず、暗号鍵の破棄とバックアップの期限・削除伝播を記録する。破棄不能は `cleanup_pending` として通知し、当該領域を次の顧客へ再利用しない。

原文投入後のメモリー状態保存・複製・顧客間再利用は初期版では禁止する。高速起動用の共通雛型は、原文・資格情報・推論の途中状態を入れる前に作る。GPUの途中計算を再利用するキャッシュも顧客をまたいで共有しない。顧客内でも原文版・認可・構成版・期限が一致したときだけ結果を再利用する。将来の再開機能は再認可、鍵の再発行、期限と取消の反映、保存状態の暗号化を満たす別の機能として審査する。[R4][R7]

## モデル更新と自己改善の境界

モデル・依存部品・実行用イメージは機密を扱わない構築環境で取得し、出所・利用条件・内容識別値・依存関係・脆弱性を確認する。承認した配布物を読取り専用で事前配置し、本番処理中の追加取得・計測送信・任意コードの取得を禁止する。モデル形式や追加読込み機構がコードを実行する場合も審査対象にする。[R3]

改善器は指示文・例示・規則の候補だけを出力する。通信規則、実行方式、資格情報、管理API、採用試験、資源上限を変更できない。独自コードの検知器は通常の指示文改善と分離し、署名・審査・隔離試験を経た配布物として扱う。解析の互換性問題を解決するために自動で特権を追加しない。

推論・確定例検索・候補作成・評価すべてに同じ顧客境界を適用する。改善部が読めるのは目的に合致する承認資料だけであり、本番保存先の資格情報を再利用しない。採用試験の正解は評価部に留める。監査記録は管理側へ保存し、標準出力・例外文・性能追跡に原文、鍵、指示文全文を無加工で残さない。診断記録も事前の項目許可と容量制限で制御し、モデルに伏字化させるだけで保護しない。

## 本番投入前の受入試験

以下は実施予定の試験契約であり、合格済みという意味ではない。架空の機密値を含む合成文書と、専用の試験用保存先を使う。実行方式・OS・GPUドライバー・解析器・通信規則の変更時に影響範囲を再試験する。

| 試験 | 合格条件と証拠 |
|---|---|
| 原文搬入前に通信規則・実行方式を適用失敗させる | 入力未搬入、作業停止、理由の監査記録。制限なしの代替実行が起きない |
| ホスト・別顧客・別作業・機械情報取得先へのアクセス | ファイル・通信双方で拒否。ホスト側の記録と合成値が流出しないことを照合 |
| IPv4/IPv6・UDP・DNS・代理を無視する直接通信 | すべての禁止経路で失敗。内部での「送信していない」という自己申告に依存しない |
| 許可先の別アカウント、転送、任意URL、継続中接続 | 代理部が拒否し、取消後に継続送信できない。管理側に拒否理由だけを残す |
| 出力にリンク・親経路・巨大データ・偽顧客ID・入替えを混ぜる | 取込拒否または正しい顧客へ固定。管理部で命令・画像解析が実行されない |
| 壊れたPDF・画像・圧縮爆弾・無限処理 | 他顧客へ波及せず外側から停止。未処理範囲が陰性・完了にならない |
| GPU処理に取消と大量要求を与える | 要求の帰属が維持され、期限・容量が強制される。遅延応答の誤取込がない |
| 顧客切替・停止・再作成・破棄失敗 | 以前の合成値・キャッシュ・資格情報を取得できない。未検証の再割当は拒否 |
| 原文に指示注入、改善候補に通信規則の緩和要求を混ぜる | 本番設定と権限が変わらない。検知精度の試験は隔離試験と別に採点 |
| 構築時通信と本番通信を比較する | 本番の追加取得・計測送信が遮断され、必要モデルを事前配置して正常処理できる |
| 通常・大容量・日本語OCR文書の比較 | 必須形式の抽出範囲が保たれる。隔離なしの試験基準との差、待ち時間、費用を記録 |
| 記録・一時領域・証拠・バックアップの削除伝播 | 合成値の残存先を説明でき、期限外に通常参照・再利用できない |

隔離試験と検知精度試験の両方に合格した構成だけを本番へ配布する。実装担当は実行定義、通信経路一覧、認可契約、資源測定、試験結果、破棄手順を同じ構成版に結び付ける。未確認項目が残る構成は合成資料での試験に留める。
