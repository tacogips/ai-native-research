# LLMを使わず端末内で機密性を判定する設計

更新日：2026年10月16日。今回の判定器は、端末内で動くLLM以外の機械学習を前提とする。判定後の業務処理では、規則に従って外部AIへ原文を送る場合もある。以下は公開手法を組み合わせた設計案であり、完成した常駐製品や実測性能の報告ではない。

[2025〜2026年のBERT系論文と到達点](local_non_llm_sensitive_data_papers_20261016.md)を追加。TF-IDFを比較基準とし、日本語BERTによる箇所検出と、ModernBERTによる文書分類を追加評価する方針。論文の高い評価値と独立文書での誤警告、端末への適合を区別する。

[PII検出の公開テストデータと開発用サンプル](pii_test_and_development_data_20261016.md)：日本語合成資料、銀行口座・カードの公式テスト値、Go/.NETの生成器、評価資料の設計を整理。

## 初期構成

第一候補は **文字単位のTF-IDFと線形分類器**。TF-IDFは文書中の文字列や単語を、その頻度と珍しさに応じた数値へ変換する方法。線形SVMは分類境界を学習し、ロジスティック回帰は分類用の重みを学習して確率形式の値を返す。後者の値も、そのまま正しさを保証する信頼度ではなく、検証が必要。

日本語の初期案では、文字を数文字ずつ切り出す方法を比較対象にする。単語の区切りを事前に決めず扱える利点があるが、最適な長さや性能は実データで決める。scikit-learnにはTF-IDFと線形分類器等を比較する公式例がある。その一般文書分類の結果を、機密分類の精度として転用しない。[公式例](https://scikit-learn.org/stable/auto_examples/text/plot_document_classification_20newsgroups.html)。

| 判定対象 | 初期候補 | 限界・追加要件 |
|---|---|---|
| 顧客名簿、給与、人事、契約、未公開業績などの文書種別 | TF-IDF＋線形SVM／ロジスティック回帰 | 組織の分類基準で正解を付けた学習資料が必要。公開資料も同じ話題を含みうる |
| 氏名・住所などの該当箇所 | 固有表現抽出用の小型モデル | 個人名などの範囲を検出する処理。文書全体が機密かどうかとは別。日本語用モデルとラベルの適合を確認 |
| カード番号、特定形式の識別番号、秘密鍵など | 正規表現・辞書・検査数字などの規則 | 機械学習ではないが併用する。桁数や形式だけで実在・機密を断定しない |
| ファイルの保存場所、分類ラベル、情報の出所 | 属性に基づく規則 | 本文の分類結果と組み合わせる。単独で内容の機密性を確定しない |

固有表現抽出の候補にはspaCyの日本語モデルがある。LLMを使わない条件では、モデルごとの構成を確認し、小型の非生成モデルを選ぶ。[日本語モデル一覧](https://spacy.io/models/ja)。Presidioは規則や自然言語処理モデルを組み合わせる個人情報検出の枠組みであり、機密文書全体の汎用分類器ではない。LLMや外部サービスを呼ぶ検出器を組み込まず、日本語用のモデル・検出規則を設定して検証する。[Analyzer仕様](https://presidio.dataprivacystack.org/analyzer/)。

fastTextも非生成の文書分類候補。独自ラベルで学習できるが、配布される一般的な事前学習モデルが、そのまま機密分類器になるわけではない。元のfacebookresearch/fastTextは2024年3月19日に読み取り専用化されているため、新規採用では保守を確認する。初期案はscikit-learnとし、比較候補として扱う。[教師あり分類](https://fasttext.cc/docs/en/supervised-tutorial.html)、[公式リポジトリ](https://github.com/facebookresearch/fastText)。

## 判定の流れ

1. 対象ファイルや送信内容を、端末内で文字へ変換する。画像の文字認識やPDF解析も端末内で実行する。
2. 形式・辞書による検出、固有表現抽出、文書分類を実行し、情報の種類と根拠を得る。
3. 保存場所・送信先・利用者の権限・操作と組み合わせ、許可・警告・遮断・要確認を規則で決める。
4. 中央管理には必要な分類結果、規則、モデルの版、操作情報を送る。原文や検出した氏名・番号は初期設定で送らない。ファイル名やパスにも個人情報が入りうるため記録内容を絞る。

**情報の分類と、操作の許可は分ける。** 同じ顧客名簿でも、許可済みAIの会社契約環境への送信と、個人用クラウドへの送信では判断が異なる。本文分類器だけでAIの会社・個人アカウントを識別することはできず、別の連携が必要。

**端末内処理でも判定器は通常、平文を読む。** 暗号文のまま分類する秘密計算とは異なる。今回の狙いは、判定のための原文を端末外へ送らず、LLMも使わないこと。

## 精度と常駐監視の評価

- 自動的に「LLMより精度が高い／低い」とは決めない。決まった書式・分類では線形分類器を基準に比較し、長い文脈や未知の秘密情報の判断は別途評価する。
- 正解付き資料は、文書の改訂版や同じ様式の複製が学習用と評価用へ混ざらないよう、元文書・案件・時期などで分離する。TF-IDFの語彙も学習用だけで決める。
- 単純な正解率だけでなく、機密の見逃し率、誤警告率、種類別の検出率、端末負荷、送信時の待ち時間を測る。
- 読めない暗号化ファイル、未対応形式、文字認識の失敗、検査上限、時間切れは「問題なし」とせず「検査不能」として記録する。
- 分類器の低い点数だけで非機密を確定しない。要確認の扱いと、規則による優先判断を設ける。
- 学習は管理された自社環境で行い、端末へは版と配布元を検証できるモデルを配る構成も可能。学習済みモデル・語彙にも機密由来の情報が残りうるため公開しない。

ファイル更新を検知する常駐処理と、送信を事前に止める処理は別。保存後に機密と判定できても、送信済みでは間に合わない。ブラウザー・USB・メール・API等の操作を捕捉して保留・遮断する部分は、分類器とは別に実装・評価する。

本稿では非公開の学習資料を取得・掲載していない。実装、学習、実機検証は未実施。

## Go・C#の実行ファイルとして配布する場合

追加確認：2026年10月16日。**実行するPCにPythonを入れず、GoまたはC#からBERTを動かせる。** ONNXはモデルの交換形式、ONNX Runtimeはその計算を実行するライブラリ。学習・変換工程のPythonと、利用者PCでの推論を分ける。BERT系の全モデルが無条件で変換できるわけではなく、使用演算・圧縮方式・出力の対応を確認する。

| 配布要件 | C# | Go |
|---|---|---|
| Pythonなしで端末内推論 | 公式のMicrosoft.ML.OnnxRuntimeを使用できる | ONNX RuntimeのC API等を呼ぶ構成で可能 |
| 実行ファイルと依存物をまとめて配布 | 自己完結型.NETアプリ、ONNX Runtime、モデル・語彙等 | Goアプリ、ONNX Runtime、モデル・語彙等 |
| 配布物を1ファイルにする | 単一ファイル配布を構成できる。ただしネイティブライブラリを起動時に展開する場合がある | 埋め込み・起動時展開、または別途静的結合する設計が必要 |
| 展開も共有ライブラリもない厳密な単一ファイル | 標準の単一ファイル設定だけでは保証できない | 一般的なONNX Runtimeラッパーを使うだけでは実現しない |

C#の公式APIは[ONNX Runtime公式説明](https://onnxruntime.ai/docs/get-started/with-csharp.html)を参照。.NETの`PublishSingleFile`、`SelfContained`と、ネイティブライブラリを束ねて展開する`IncludeNativeLibrariesForSelfExtract`は別の設定。配布は1ファイルでも実行時にはディスクへ展開する場合があり、OS・CPU別の配布物が必要。[Microsoftの単一ファイル仕様](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)。

Goの例である[yalue/onnxruntime_go](https://github.com/yalue/onnxruntime_go)は第三者製で、cgoとOS・CPUに対応する共有ライブラリを必要とする。通常のビルドだけで純Go・依存物なしの実行ファイルになるとはいえない。

**日本語の前処理も移植する必要がある。** 推論エンジンは、文章を学習時と同じ数値列へ変換する処理や、出力を文字位置へ戻す処理を自動的に代行しない。氏名の伏字位置を得るなら、文字位置との対応も保持・検証する。

具体的に[ssl-jp/pii-ja-ner-onnxの設定](https://huggingface.co/ssl-jp/pii-ja-ner-onnx/blob/main/tokenizer_config.json)は`BertJapaneseTokenizer`、`word_tokenizer_type=mecab`、`subword_tokenizer_type=wordpiece`。語を切り出すMeCabと、その後の細分化・語彙対応を学習時と合わせる。[配布ファイル](https://huggingface.co/ssl-jp/pii-ja-ner-onnx/tree/main)には`model.onnx.data`もあり、計算定義の`model.onnx`だけで重み一式が揃うとは扱わない。今回は公開ファイル一覧・設定を確認し、Go/C#での実行は試していない。

初期の実装案は、Windows中心ならC#＋公式ONNX Runtime、既存Go製の常駐処理へ組み込むならGo＋C APIラッパー。どちらも最初は実行ファイル・推論ライブラリ・モデル・前処理資産を一括導入し、更新しやすい構成で評価する。単一ファイル化は、その後に配布要件として検証する。CPU実行であればGPU関連の追加依存物を避けられるが、負荷・応答時間は実測する。

2026年10月16日にHugging Faceの公開ファイル情報（`/api/models/{repo}?blobs=true`）を確認。以下はファイル容量で、実行時メモリーではない。MiBは1,048,576バイト。

| モデル・配布形式 | 容量 | 注記 |
|---|---:|---|
| ssl-jp/pii-ja-ner-onnx：`model_quantized.onnx` | 105.45MiB | INT8圧縮済みの配布ファイル |
| 同：`model.onnx`＋`model.onnx.data` | 合計419.98MiB | 非圧縮側の計算定義と外部重み。上の圧縮済みファイルと両方を導入する前提ではない |
| ModernBERT-Ja-30M：`model.safetensors` | 140.67MiB | 公式表では実パラメーター数37M |
| ModernBERT-Ja-70M：同 | 268.00MiB | 同70M |
| ModernBERT-Ja-130M：同 | 505.48MiB | 同132M |
| ModernBERT-Ja-310M：同 | 1,202.81MiB | 同315M |

[PIIモデルのファイル](https://huggingface.co/ssl-jp/pii-ja-ner-onnx/tree/main)、[ModernBERT-Jaの公式系列表](https://huggingface.co/sbintuitions/modernbert-ja-310m)。ModernBERT側は公開基盤の保存形式で、機密分類への追加学習後・ONNX変換後の容量ではない。必要なのは選択したモデルに加え、推論ライブラリ、語彙・辞書、アプリ。実行時メモリーは入力長・同時処理数・実行環境で変わるため、モデル容量だけから確定しない。今回、重みのダウンロードや実行時メモリー測定は行っていない。
