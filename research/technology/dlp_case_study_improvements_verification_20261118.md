# 事例調査の改善案を DLP の検知精度と是正フローに取り込む検証

報告日：2026年11月18日。[企業の取り組み事例の調査](enterprise_sensitive_data_detection_case_studies_20261116.md)で共通していた6つの改善案を、既存の[検知精度の検証（v3）](workspace_dlp_v3_extended_detection_report_20261116.md)と[是正フローの試験設計](workspace_dlp_benchmark_review_response_20261116.md)に取り込めるかを確かめた。コードは[`scripts/workspace_dlp_benchmark/improvement/`](../../scripts/workspace_dlp_benchmark/improvement/README.md)。

- 是正：検知の後に、共有の制限、ラベルの付与、削除などで状態を変えること。
- 適合率：検知したもののうち、本当に機微だった割合。再現率：本当に機微なもののうち、検知できた割合。
- 保留資料（ホールドアウト）：規則を作るときに見ていない、評価専用の資料。

**この報告の数値は、Google 実環境での測定ではない。** 検知は RE2（Google の正規表現の方式）によるローカル検査、フローは前提値に依存するモデル計算である。実環境の測定結果はこのリポジトリに載せない。

## 1. 結論

6つの改善案はすべて現行の Workspace の機能と、規則の外側の小さな追加処理で取り入れられる。効果の確かさは案ごとに異なる。

| 改善案 | 取り入れ方 | 検証の種類 | 結果 |
|---|---|---|---|
| 1. 共有状態の棚卸しを先にする | 公開リンク・外部共有で1年更新のないファイルを、内容の検知を待たずに可逆に解除 | モデル計算 | 棚卸しを外した場合と比べ、機微ファイルの露出の累積（ファイル数×週）が約44%減。代わりに非機微ファイルの共有解除が約1,140件、再共有の申請が約49件 |
| 2. 文脈で精度を補う | 見出しの書き方を広げ（T1）、値の形と「人」の語をANDで組合せ（T2）、業務番号や解説文をNOTで外す（T3） | ローカル実測（独立資料） | 再現率 0.41 → 0.68、適合率 0.93 → 0.97（グループ単位） |
| 3. 検知結果は「提案」、確定してから是正 | 所有者が確定したものだけを制限し、削除は4週の猶予後。所有者不在は上長へ | モデル計算と状態遷移の試験 | 猶予なしの削除が約1,020件から0件、所有者不在で止まる案件が約139件から0件、管理者の作業時間が約304時間から約164時間 |
| 4. ラベルは少数、既定は安全側 | 利用者向けに4段階の「機密区分」を1つ置き、新規ファイルの既定を「社内限」にする | モデル計算と公式仕様の確認 | 新規の機微ファイルの外部露出が約27件から約1件（既定ラベルを外すと約15件） |
| 5. 生成AIの前に過剰共有を直す | 棚卸しの対象に「組織全体に共有」を加える | モデル計算 | 社内の誰でも届く機微ファイルが約375件から約156件 |
| 6. 段階的に導入する | 監査のみ → 担当者だけに通知 → 本人へ提案 → 自動是正。次の段階へ進む条件を数値で決める | 設計のみ | 移行条件を4.3節に定義。実環境で測る必要がある |

**検知の改善とフローの改善は、組み合わせて初めて効く。** 現行フローのまま検知だけを改善すると、管理者が確認すべき件数が増えて作業時間が約244時間から約304時間に増え、確認待ちが滞留する。改善フローでは、検知の改善が「所有者への誤った依頼の減少」（約1,068件から約618件）と露出の減少に直接つながる。

**新しく生じる危険もある。** 所有者が機微なファイルを誤って「該当なし」とする件数が、モデル上で約107件生じる（所有者の誤判定を5%と置いた場合）。却下の抜き取り確認（10%）だけでは足りないため、高機微のグループは却下に理由の入力と上長の承認を求める設計にする（4.2節）。

## 2. 検知精度：文脈で補う規則の検証

### 2.1 方法

| 項目 | 内容 |
|---|---|
| 比べる規則 | 既存の独自正規表現（v3、31項目）と、文脈で補う規則（v4-context） |
| 規則の作り方 | 既存v3の385資料だけを見て作り、評価資料が届く前に内容を固定した（SHA-256 `d73d9496…`、`frozen.json`） |
| 評価資料 | 規則の作者とは別の担当が、規則と既存資料を見ずに作った架空資料340件。陽性186、陰性124、判断保留30。書き方は見出し付き・文中・タブ区切りの表・帳票（見出しと値が別の行）・チャット・表記ゆれ（英語見出し、全角数字）の6種、陰性は同じ形の別番号・一般説明・空欄や伏字・業務文書 |
| 判定の単位 | ファイル単位。Workspace の規則と同じく、AND・NOT はファイル全体で評価する |
| 主な指標 | 分類ラベルを付ける単位である7グループ（G1〜G7）の判定。判断保留は除外 |
| Workspace の制約 | 独自正規表現92個（規則で参照できる上限100）、最長213文字（上限1,000）。すべて RE2 で動く |

### 2.2 結果

| 資料 | 規則 | 適合率 | 再現率 | F1 | TP | FP | FN |
|---|---|---|---|---|---|---|---|
| 独立の評価資料 340件 | 既存 v3 | 0.926 | 0.411 | 0.570 | 88 | 7 | 126 |
| 独立の評価資料 340件 | 改善 v4（T1+T2+T3） | 0.967 | 0.678 | 0.797 | 145 | 5 | 69 |
| 既存 v3 資料 385件（開発用） | 既存 v3 | 0.940 | 0.494 | 0.648 | 218 | 14 | 223 |
| 既存 v3 資料 385件（開発用） | 改善 v4 | 1.000 | 0.984 | 0.992 | 434 | 0 | 7 |

- 開発用資料の結果は、その資料に合わせ込んだ値である。性能の根拠には独立資料の行だけを使う。
- 独立資料での再現率の95%区間（Wilson 法）は、既存 0.35〜0.48、改善 0.61〜0.74 で重ならない。
- ファイル単位（どれかの項目で検知できたか）では、再現率 0.46 → 0.74、適合率 0.92 → 0.97。

### 2.3 どの手法が効いたか（独立資料）

| 構成 | 適合率 | 再現率 |
|---|---|---|
| 既存 v3 | 0.926 | 0.411 |
| T1 書き方を広げる | 0.955 | 0.598 |
| T1＋T3 除外条件 | 0.970 | 0.598 |
| T1＋T2 見出しのない値 | 0.954 | 0.682 |
| T1＋T2＋T3 | 0.967 | 0.678 |

- 最も効いたのは T1（区切りにタブ・改行を含め、英語見出し・全角数字を足し、空欄・伏字を除く）。
- T2 は見出しのない値を拾い、再現率をさらに 0.08 上げる。代わりに誤検知が少し増える。
- T3 は誤検知を減らすが、陽性を1件外した。

|---|---|---|
| G1 公的番号・本人確認 | 0.92 / 0.29 | 0.97 / 0.76 |
| G2 金融・資産 | 0.87 / 0.43 | 0.95 / 0.70 |
| G3 経歴・勤務・家族 | 0.86 / 0.48 | 0.91 / 0.80 |
| G4 健康・医療 | 1.00 / 0.39 | 1.00 / 0.72 |
| G5 要配慮（健康以外） | 0.90 / 0.50 | 1.00 / 0.61 |
| G6 認証情報 | 1.00 / 0.58 | 1.00 / 0.67 |
| G7 連絡先・基本属性 | 1.00 / 0.37 | 0.97 / 0.57 |

| 書き方（主項目の陽性） | 既存 検知 / 見逃し | 改善 検知 / 見逃し |
|---|---|---|
| 見出しと値が同じ行 | 28 / 3 | 28 / 3 |
| 文中 | 20 / 11 | 25 / 6 |
| タブ区切りの表 | 10 / 21 | 21 / 10 |
| 帳票（見出しと値が別の行） | 7 / 24 | 22 / 9 |
| チャット・メール・箇条書き | 11 / 20 | 18 / 13 |
| 表記ゆれ（英語見出し・全角数字） | 8 / 23 | 22 / 9 |

陰性側では、空欄・伏字の誤検知が6件から3件、業務文書が1件から0件に減った。同じ形の別番号は0件から1件に増えた。

### 2.5 残った誤り

| 種類 | 例 | 正規表現での対処の可否 |
|---|---|---|
| 見逃し：列見出しと値が別の行にある表 | 1行目に「氏名　個人番号」、2行目以降に値 | 列の対応は正規表現では取れない。値の形と「人」の語のANDで一部を拾うだけ |
| 見逃し：氏名（23件） | 見出しのない氏名、ローマ字の氏名 | 正規表現では困難。標準検知器 `Name occurrence` の日本語での動作を実測する |
| 見逃し：略記・空白入りの全角数字 | 「免許証No.」「ＳＫ ４０１９ …」 | 規則を足せば拾えるが、新しい評価資料で測り直す必要がある |
| 誤検知：記入例・選択肢欄 | 「XX00000000XX（記入例）」「□中学 □高校」 | 「記入例」「□」を除外語に足す候補 |
| 誤検知：法人の金額 | 「受注残高」 | 「受注」を資産の除外語に足す候補 |

上の対処はまだ規則に反映していない。反映すると、この評価資料はもう独立ではなくなる。反映した後は、別の担当が新しい評価資料を作って測り直す。

### 2.6 この検証の限界

- **資料が短い。** 評価資料は2〜6行で、実務の文書より短い。長い文書では「人」の語や除外語が偶然現れやすい。そのため、T2 の誤検知と T3 の見逃しは実務ではここより増えると考える。
- **作者は別でも、同じ種類の生成方法である。** 評価資料は言語モデルの担当が作った。人が書いた実務の文書とは表現の分布が違う。
- **Workspace の標準検知器と組み合わせた効果は測っていない。** 実運用では、標準検知器（確度高）と独自規則（確度中）を併用する設計である。
- **文字コードとファイル形式は TXT（UTF-8）だけ。** Office、PDF、画像を文字認識した場合の結果は、別途 Workspace で測る。

## 3. 是正フロー：提案と確定を分けたフローの検証

### 3.1 比べた2つのフロー

| 段階 | F0 現行案 | F1 改善案 |
|---|---|---|
| 着手前 | なし | 共有の棚卸し：公開リンク・外部共有で1年更新のないファイルを、内容の検知を待たずに可逆に解除。所有者へ通知し、理由を付ければ戻せる |
| 最初の2週 | 監査のみ | 監査のみ（同じ） |
| 検知後 | 管理者が全件を確認（週300件まで）し、機微なものだけ作成者へ削除・修正を依頼 | 優先度（機微度×露出範囲）の順に、所有者へ「確認してください」と提案。管理者は全件を見ない |
| 所有者不在 | 誰も対応せず残る | 上長へ回す。1週間応答がなければ上長へ |
| 確定後 | 作成者が削除（50%）か共有解除 | ラベル「機密」と外部共有の制限。4週の猶予後に削除（50%） |
| 却下 | — | 10%を管理者が抜き取り確認し、誤りなら再提案 |
| 新規ファイル | 既定なし | 既定ラベル「社内限」で外部共有を制限。理由を付ければ下げられる |
| 通知の中身 | 規定なし | ファイルID、グループ、露出範囲だけ。一致した値は載せない |

状態遷移（検知 → 提案 → 確定／却下／上長へ → 是正 → 削除／復元／終了）をコードで実装し、禁止した遷移は例外にした。単体試験で次の3点を確かめた。

- 確定と猶予を経ない削除がない。
- 未完了の案件にはすべて担当者がいる。
- 通知に一致した値を含めない。

### 3.2 前提値

| 前提 | 値 | 根拠・注意 |
|---|---|---|
| ファイル数・期間 | 2万件、12週 | 1部門規模の仮定 |
| 機微ファイルの割合 | 15%（感度分析で30%） | Metomic の自社調査は Drive の40%に機微情報があると報告。検出器に依存するため低めに置いた |
| 共有状態 | 制限68%、組織全体17%、外部12%、公開リンク3%（感度分析で外部5%・公開1%） | Metomic・DoControl の事例は外部共有が多いと報告。ベンダーの数値なので幅を取った |
| 1年以上更新なし | 45% | 仮定 |
| 所有者不在 | 6%（感度分析で15%） | 仮定 |
| 所有者の応答 | 週50%（感度分析で30%・80%） | 仮定。両案で同じ値を使う |
| 管理者の確認容量 | 週300件（感度分析で100・1,000件） | 仮定 |
| 検知性能 | 2章の独立資料のファイル単位の値。既存は検知率0.46・誤検知率0.06、改善は0.74・0.03 | ローカル実測の値。実環境の値ではない |
| 所有者の誤却下 | 5% | 仮定。F1だけに生じる |
| 作業時間 | 確認4分、依頼2分、上長へ回す10分、再共有申請8分、F0の未完了案件の追跡は週0.5分 | 仮定 |

### 3.4 どの構成要素が効いたか（F1×改善検知から1つずつ外す）

| 外したもの | 外部から読める機微 | 露出の累積 | 新規の機微の露出 | 社内の誰でも届く機微 |
|---|---|---|---|---|
| 何も外さない | 79 | 1,489 | 1 | 231 |
| 共有の棚卸し | 142 | 2,678 | 1 | 291 |
| 既定ラベル | 94 | 1,590 | 15 | 245 |

- 棚卸しは、検知を待たずに露出を早く減らす。
- 既定ラベルは、新しく作られるファイルの露出を防ぐ。
- 提案と確定の分離（F1の骨格）は、管理者の滞留と所有者不在の停止をなくす。

### 3.5 感度分析（F0×改善検知 と F1×改善検知）

| 条件 | F0 外部露出 | F1 外部露出 | F0 管理時間 | F1 管理時間 |
|---|---|---|---|---|
| 基本 | 193 | 79 | 304 | 164 |
| 管理者の容量 週100件 | 390 | 79 | 102 | 164 |
| 管理者の容量 週1,000件 | 157 | 79 | 320 | 164 |
| 所有者の応答 週30% | 233 | 80 | 322 | 282 |
| 所有者の応答 週80% | 171 | 79 | 292 | 61 |
| 外部共有が少ない（5%・1%） | 96 | 29 | 304 | 160 |
| 所有者不在が多い（15%） | 220 | 74 | 312 | 194 |
| 機微ファイルが多い（30%） | 631 | 152 | 318 | 277 |
| 棚卸しに組織全体共有を含める | 193 | 73 | 304 | 170 |

- どの条件でも、F1 の外部露出は F0 より少なかった。

### 3.6 このモデルの限界

- 前提値は仮定で、特定の組織の実態ではない。
- 所有者の誤却下率、応答率、作業時間は、実運用で測って置き換える。
- 管理者の作業には、規則の保守、例外の審査、問い合わせ対応を入れていない。
- Workspace の検知・記録・ラベル付与の遅延（数時間から1日以上）は入れていない。週単位で丸めている。

## 4. Workspace での実装案

### 4.1 検知規則とラベル

| 層 | 中身 | Workspace の機能 |
|---|---|---|
| 検知ラベル（管理者向け） | 既存設計の `PII-G1`〜`PII-G7` と確度（確度高＝標準検知器、確度中＝独自規則）。DLPが自動で付ける「提案」 | DLP 規則のラベル付与 |
| 機密区分（利用者向け） | 1ラベル・4択：極秘／機密／社内限／公開。新規ファイルの既定は「社内限」 | [既定の分類](https://knowledge.workspace.google.com/admin/security/apply-default-classification-labels-to-new-files-automatically)。新規作成と所有者変更のときだけ付き、DLP 規則が付けたラベルが優先される |
| 是正規則 | 機密区分が「極秘・機密」なら外部共有を遮断、「社内限」なら外部共有時に警告 | ラベルを条件にした別の DLP 規則 |
| 確定の操作 | 所有者が提案を確認し、機密区分を「機密」にする（確定）か、「該当なし」と理由を入れる（却下） | 利用者の操作、または Drive API `files.modifyLabels` を使う追加処理 |

- 文脈規則の独自正規表現は92個で、上限100に近い。標準検知器のある項目は標準検知器を主にし、独自規則は G3・G5 など標準検知器がない項目に絞ると余裕ができる。
- 既定の分類は既存ファイルに遡って付かない。既存ファイルは共有の棚卸しと DLP 規則で扱う。

### 4.2 是正フローの運用ルール

1. **共有の棚卸し：** 公開リンク・外部共有で1年更新のないファイルの共有を解除し、所有者へ通知する。解除は可逆にし、理由を付けた再共有の申請を受ける。
2. **提案：** 優先度は機微度×露出範囲とする。高機微（G1・G4・G5・G6）かつ外部共有を最優先にする。通知には一致した値を載せない。
3. **確定と却下：** 高機微の却下は理由の入力と上長の承認を必須にする。それ以外の却下は10%を抜き取って確認する。
4. **所有者不在：** 退職・異動者のファイルは上長へ回す。1週間応答がなければ上長へ、2週間応答がなければ管理者へ回す。
5. **削除：** 確定から4週の猶予後だけ削除する。猶予中は「機密」ラベルと共有制限で守る。
6. **追跡：** 状態と担当者を台帳で管理し、DLP の記録（監査ログ）と突き合わせて「新規・解消・未解消」を週ごとに集計する。

### 4.3 段階導入と、次の段階へ進む条件

| 段階 | 期間の目安 | 次へ進む条件（案） |
|---|---|---|
| 0 共有の棚卸し | 1〜2週 | 再共有の申請が解除件数の10%未満 |
| 1 監査のみ | 2週 | 抜き取り確認で、グループ単位の適合率が0.9以上 |
| 2 担当者だけに通知 | 2〜4週 | 誤検知による提案（所有者が正しく却下したもの）が提案の20%未満。抜き取りで見つかる誤った却下が5%未満 |
| 3 本人へ提案 | 継続 | 所有者の週あたり応答率が50%以上、上長へ回す件数が提案の20%未満 |
| 4 自動是正 | 高機微の確度高だけ | 確定と猶予を経ない削除がないことを、台帳で毎週確認 |

数値はこのモデルと事例調査を参考にした目安で、実環境で測って決め直す。

## 5. 次に実環境で確かめること

1. 文脈規則（v4-context）を Workspace に作成し、LIGHT（実務に近い長さの架空資料）と v3 の資料で、標準検知器との併用を含めて測る。長い文書で T2・T3 の誤りが増えないかを見る。
2. 既定の分類を試験用の組織部門で有効にし、新規ファイルに「社内限」が付くこと、DLP 規則のラベルが優先されることを確かめる。
3. ラベルを条件にした是正規則（極秘・機密は遮断、社内限は警告）の動作を、是正の状態遷移表（R06・R13）に加えて測る。
4. 提案から確定までの追加処理（台帳、通知、上長へ回す処理）を試験用の組織部門で動かし、所有者の応答率と誤却下率を測ってモデルの前提を置き換える。
