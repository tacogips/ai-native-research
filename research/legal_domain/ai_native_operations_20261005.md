## 調査範囲

2026年10月5日の Apple Notes のコンソール写真にある④法務への適用・評価、⑥業務への適用設計、⑦再調査時の確認点、⑧業務アプリ、⑨自律度・自己改善・運用、⑩経営・対外発信を扱う。①〜③は[共通基盤](../technology/ai_native_company_platform_20261005.md)、⑤は[企業事例](../benchmarks/ai_native_companies_20261005.md)。写真が参照する別 repo の全文は取得しておらず、写真から確認できる範囲と一次資料による再調査を区別する。

公開製品の機能は**公開資料の確認**、以下の社内構成・業務フロー・段階移行は**設計案**である。KIRIN / Totoro の社内仕様、接続権限、社内 playbook、実データ性能は確認できていない。写真の名称から同名の公開製品へ推測で結び付けない。

## ④ 法務への適用・評価

### 内製事例と legal-tech の比較

Harvey 自社法務の例は、vendor review の workflow、Word 内の修正、契約データの構造化等を示す。「専門家が使う仕組み」が参照点であり、会社の法務判断が全て自律化した証拠ではない。[自社法務の公式事例](https://www.harvey.ai/blog/how-harveys-legal-team-uses-harvey-to-work-smarter)

| 分類・候補 | 一次資料で確認した内容 | 内製との境界・評価すること |
|---|---|---|
| 契約 review / LegalOn・LegalForce | playbook による review、Word 内の修正を説明 | 自社ルールとの差、原文への変更履歴、比較版の特定、例外の扱い。[国内公式](https://www.legalontech.com/jp/legalforce)、[global 公式](https://www.legalontech.com/) |
| 法務 research / Legalscape | 法情報からの要約、参照元・原典への到達を説明 | 日本法の網羅性、施行日、引用の支持、書籍利用・export の権利。[公式](https://www.legalscape.jp/) |
| 国際法務・bulk review / Harvey | legal model と Vault 等。森・濱田松本との2024年提携で API 利用が説明される | 特定事務所の契約を自社も使えると推定しない。日本語、日本法、現在の API・データ条件は個別確認。[提携当事者資料](https://www.morihamada.com/en/news/articles/2024/159.html) |
| 一般モデル + 社内 RAG + workflow | 今回の内製案。社内案件・規程・承認系と接続できる | 出典検証、版、監査、connector、評価・保守の責任を自社が負う |

買う/作るの判断は、機能の数よりも**日本語・日本法の正答、データ所在地、保持・学習利用、API、持ち出し条件、版と承認証跡、運用費用**で行う。公開ページだけでは見積り、リージョン契約、ZDR、bulk export、監査 API の自社利用条件を確定できない。

**推奨案:** 一般的な法情報と Word の編集体験は専用製品を比較し、社内案件受付、証跡、承認・権限、締結後管理との接続は共通基盤で持つ。特定ベンダーを採用済みとはしない。専用 UI の承認と共通基盤の承認が同じ evidence を参照できるかを PoC で確認する。

### 指針・法令を設計の確認事項にする

| 一次資料 | 今回確認できる範囲 | 設計への反映案 |
|---|---|---|
| 総務省・経産省 AI 事業者ガイドライン | 公式掲載では第1.2版（2026年4月1日更新）、チェックリスト等を提供 | 開発・提供・利用それぞれの責任、データ利用、説明、監査、リスク管理の確認表に結び付ける。[掲載ページ](https://www.meti.go.jp/shingikai/mono_info_service/ai_shakai_jisso/20260331_report.html) |
| 個人情報保護委員会の生成 AI 注意喚起 | 個人情報の入力・利用とサービス側の取扱いを確認するための資料 | 入力目的、委託・第三者提供・外国処理の整理、学習利用、削除を案件・契約単位で点検。[原文 PDF](https://www.ppc.go.jp/files/pdf/230602_alert_generative_AI_service.pdf) |
| 法務省の弁護士法72条関連指針 | 2026年8月21日の新指針の本文・概要を取得。2023年指針を補完・拡充するが、基本的解釈を変更するものではない | 自社内の支援と外部への法務サービス提供を区別し、設計・機能・実際の用法に照らして専門家が適用を確認する。[法務省掲載](https://www.moj.go.jp/housei/shihouseido/housei10_00134.html)、[新指針本文](https://www.moj.go.jp/content/001469040.pdf) |
| EU AI Act | Regulation (EU) 2024/1689 の公式文書を特定。今回取得できた本文は不十分 | EU 展開では対象行為、provider/deployer、risk 分類、適用日程を別途確認する。単なる法務支援を自動的に high-risk と断定しない。[EUR-Lex](https://eur-lex.europa.eu/eli/reg/2024/1689/oj/eng) |

国内 AI ガイドラインの最新版番号は掲載情報で確認したが、本調査で新しい法令・指針の全条文に適合するとの結論は出さない。法令上の最終判断をモデルへ委任できるという根拠としても扱わない。

新指針の第2は、利用者が入力する形でも、提供者の設計・機能・用法によっては提供者の行為と評価され得ると説明する。「ユーザーがクリックした」という理由だけでサービス提供者の責任を消せない。第3は、弁護士による実質的な設計関与、利用範囲の説明、参照元表示、重大な違反時の利用停止などを挙げる。一律の出力制限は今回の推奨事項として明記せず、今後の検討課題としている。これらを、利用目的の確認、画面表示、機能の境界、停止手順のレビュー項目へ反映する。個別の適法性を本レポートで判断したものではない。[新指針・本文3〜4、16〜21頁](https://www.moj.go.jp/content/001469040.pdf)。判断枠組み・具体例・推奨事項・出力制限の検討経緯・ロードマップの全体は[法務省指針の内容要約](../disclosures/moj_ai_legal_services_72_summary.md)を参照。

### 効果測定と評価データ

法務 RAG の preregistered 研究は、2024年当時の対象製品に17〜33%の hallucination を報告する。日本語・現行製品・自社契約で同じ率という意味ではなく、RAG と引用リンクの存在だけでは正しさを保証できない証拠である。[論文](https://arxiv.org/abs/2405.20362)

**評価案:** 法務担当者が①要件、②正しい結論、③根拠箇所、④許容可能な代替案、⑤人へ返す条件をラベル付けする。評価セットは NDA / 委託 / 個人情報 / 例外条項 / 改訂 / OCR / 引用誤りを含め、同じ取引先や案件を学習と評価に混ぜない。judge model の採点は人の確定ラベルとの一致率を測り、唯一の承認者にはしない。

| 指標 | 定義案 |
|---|---|
| 業務品質 | 重大な見落とし・誤許可・偽引用・法域/施行日誤り・最終成果物の不備率 |
| 手戻り | 修正が必要な案件割合、修正時間、差戻し回数と原因 |
| 時間 | 作業時間と待ち時間を別計測。median / p95、案件受付から完了まで |
| 自律度 | eligible 案件のうち、人の作業・修正なしで正しく完了した割合。全案件を分母とする値も併記 |
| 費用 | inference、embedding、ASR、再試行、review、運用、ライセンス、障害対応の合計 |
| 定着 | 継続利用率、取りこぼし、担当者の理解度、削減時間の再配分先 |

人のみ、AI 下書き、AI + 承認、限定自律の群を案件難度で揃えて比較する。単に成功した案件だけを測らず、棄却・timeout・例外処理も分母に含める。許容不備率・品質非劣性の条件は業務 owner が先に決める。

## ⑥ 業務への適用設計: 共通基盤 + SDK

### 各部門がアプリを作れる形

SDK は `Case / Evidence / Policy / Approval / Action / Outcome / Exception` の型、version、idempotency key を提供する案。各部門は業務規則と UI を作り、runtime は閲覧認可、操作認可、IFC、承認一致、モデル route、監査を共通に強制する。SDK を使わない呼び出しでも強制点を通ることが条件。[基盤構成](../technology/ai_native_company_platform_20261005.md)

KIRIN / Totoro への接続は、API catalog、所有者、データ辞書、ID、更新頻度、認証方式、ACL、read/write、rate limit、監査、削除・保持、停止経路を確認してから adapter を決める。公開情報から内部アクセス権や既存基盤の能力を推定しない。

### 法務業務のモデル化

| 工程 | 発生条件・入力 | 作業・成果物 | 完了条件 / 人の判断 |
|---|---|---|---|
| 相談 | 依頼、取引先、目的、契約 draft | 不足項目収集、案件分類、利益相反・緊急性の検査候補 | 必須項目と担当が確定。曖昧な前提は質問へ戻す |
| 検証 | 案件と文書の版、適用 playbook | 条項照合、根拠検索、差分と論点の下書き | 引用支持と版が確認され、例外・未判断箇所が明示される |
| 決裁 | 検証結果、金額、相手、提示案 | 業務承認の申請 | 権限を持つ承認者、内容 hash、期限、scope を確定 |
| 締結 | 承認済み文書、署名者・宛先 | 署名依頼準備、本人・版の照合 | 締結権限と実際の署名結果を照合。署名・契約成立を準備作業と区別 |
| 回収保管 | 署名済み成果物、原本の所在 | 回収催促、証明書・履歴・保持登録 | 当事者・版・保存先・期限が一致し、監査証跡が揃う |

この表は写真から復元した工程を使う一般的な設計案。実際の社内工程、承認権限、例外の割合は聞き取りと履歴分析が必要。内部作業を「AI が既に実施している」とは記述しない。

### 狭い PoC の選定

| 候補 | 期待する価値 | 初期の自律範囲 | 完了を証明する evidence |
|---|---|---|---|
| 検証申請準備 | 不足情報の往復と入力を減らす | 必須項目チェック・案件登録・下書き | 原文から全項目を支持、誤案件登録ゼロ、欠落時は返却 |
| 電子署名準備 | 宛先・版・権限の照合を省力化 | 送信前準備まで | 承認版 hash と準備版一致、署名者 master との一致 |
| 原本回収追跡 | 未回収案件と期限を可視化 | 内部タスク更新・通知下書き | 回収状態が署名サービス・文書庫と一致、誤完了ゼロ |

候補は未選定。最初の比較では検証申請準備を優先する案だが、案件量、手戻り、data access が揃わない場合は別候補にする。年内実現という写真の目標に対して、納期を保証する材料はない。

## ⑧ 業務アプリの設計

| 領域 | 設計案 | 共通基盤に必要な機能 | 個別に確認すべきこと |
|---|---|---|---|
| 規程・マニュアル | `document_id / version / effective_from / effective_to / owner / approved_by / supersedes` を持つ規程 registry。改訂差分から通知候補を作る | 版、施行日、ACL、引用、配布履歴 | 旧規程の適用、経過措置、周知対象・責任者 |
| 財務経理 | 請求書の証憑照合、締切判定、不備回収を自動化候補にする | 金額・通貨の型、重複検知、承認、監査、冪等性 | 申請→承認→支払→消込の職務分離。送金は独立 gate |
| IT サポート・資産 | 問い合わせ分類、手順案、inventory 照合、許可操作の実行 | device ID、所有者、短命権限、停止、ticket 証跡 | MDM / IdP と実際の端末状態の一致、物理作業、wipe 等の例外 |
| 部門横断 | 申込→与信→契約→請求を共通 case ID と event で接続 | 状態遷移、schema version、重複排除、例外 queue | 部門ごとの正本、与信判断、取消・補償処理、責任の引き継ぎ |

ゼロタッチ設定の例として Intune の Apple ADE は事前登録や token・MDM 設定を必要とする。ソフトウェア側の登録自動化は、開封・配送・配線・修理を含む全作業の無人化の証拠ではない。[公式資料](https://learn.microsoft.com/en-us/intune/device-enrollment/apple/setup-automated-ios)

社内規程の改訂と学習モデルの更新を分離し、新規程は版・施行日を検索に反映する。財務の計算・締切・状態遷移は決定的コードで実施する案。LLM に全社の帳簿・与信・支払の確定権限をまとめて持たせない。

### 既存ツールとの連携

Word Add-in の JavaScript API は文書の body、paragraph 等を扱えるが、client ごとの requirement set を確認する必要がある。[Microsoft](https://learn.microsoft.com/en-us/office/dev/add-ins/word/word-add-ins-programming-overview)

**設計比較:** Workspace/Gmail は既存の依頼・通知・原文に接続し、Word は変更履歴と review、Excel は照合表・数値検証、Chrome は既存 web UI へのアクセスを担う。API は安定 ID・証跡に適し、UI は導入負荷が低い一方で画面変更・再実行に弱い。専用 UI は案件状態・承認差分を一体で表示できるが、移行と教育コストがある。併用する場合も evidence と承認の正本を一つにする。

Chrome に対する具体的な自動操作権限や Excel の live 接続は今回試験していない。API のない操作を画面自動化する際は、送信前の版照合・結果取得・誤クリック時の復旧を受入条件にする。

## ⑨ 自律度・自己改善・運用

### 段階移行

| 段階 | AI の担当 | 人の担当 | 昇格条件案 |
|---|---|---|---|
| Shadow | 過去・現行案件で候補を作る | 現行業務を継続し比較する | evidence の支持と失敗類型を把握 |
| 下書き | 抽出・案の作成 | 全件 review と確定 | 重大不備が許容条件内、review 時間を含む改善 |
| 承認付き実行 | 承認済み版の型付き Action | 業務承認・例外 | 差し替え拒否、停止、冪等性、監査が実証される |
| 限定自律 + 事後確認 | eligible な可逆操作を完了 | sampling、例外、監督 | eligible 条件と品質 gate を満たし、逸脱は自動停止 |
| 範囲拡大 | 検証済み task を増やす | 承認範囲・責任を見直す | 新しい task を別評価。過去の合格を包括許可にしない |

Human on the Loop は単に事後に画面を見るだけでなく、処理の上限・除外・停止・sampling・介入 SLA が定義された監督の設計である。不可逆な操作に事後確認だけを適用するかは、事前の業務・法的判断が必要。

### 自己改善の変更管理

**設計案:** `修正 experience → 分類 → 候補変更 → review → 非公開の固定評価 → canary → 配布 → outcome 監視 → rollback`。知識更新（原文と index）、ルール更新（policy/playbook）、事例追加（評価/学習データ）、モデル更新（weight/route）を別リリースにする。稼働エージェントが自分の評価・承認条件を変更できないよう分離する。

安全性・状態攻撃の詳細は[既存のリスク調査](../technology/autonomous_agent_risks_papers_incidents.md)を参照。今回、この repo に自己改善システムを実装したわけではない。公開 memory 製品の自動編集を、そのまま企業の本番ルール改訂に使えるとの証拠もない。

### 障害と責任

業務 owner は許容品質、例外、再開可否、外部説明を担当する。基盤 owner は identity、gateway、Workflow、model route、監査、復旧を担当する。どちらも owner 不在を許可条件にしない（設計案）。

停止 runbook は新規受付停止、実行権限失効、queue/in-flight 確認、外部結果の照会、担当者への移譲、原因・影響案件特定、固定版での再開を含む。rollback は model/policy の差し戻しと業務上の補償を区別する。署名・支払・対外公開はコードの rollback だけでは元に戻らない。

## ⑩ 経営・IR・広報への展開

### 観測 → 判断 → 実行 → 検証

**設計案:** KPI 定義、集計版、元 evidence、仮説、判断者、許可した施策、実行 ID、結果を decision log でつなぐ。経営データの抽出・説明案は自動化候補だが、資金配分、人事、与信、重大対外判断を同じ自律範囲にしない。相関の変化を施策の因果効果と断定しない。

### IR・広報

**設計案:** 数字の正本、単位・集計期間、公表済み/未公表、解禁日時、出典、承認版、channel、配信結果を対外発信 registry で管理する。社内情報から外部資料へ降格する操作は独立した承認 Action とし、draft agent と配信 credential を分離する。資料の訂正・再配信を監査できるようにする。

上場区分、取引所、重要事実、法定開示・適時開示の要件は未確認であり、この設計案から当該企業の IR 手続きに適合すると主張しない。広報の文章作成時間を短縮しても、開示の真実性・公平性・承認責任は別に確認する。

### 共通化の進め方

一つの PoC から着手し、次の二つ目の業務で再利用できた identity、approval、evidence、Action、状態・監査を SDK に抽出する案。規程・経理・IT・法務の専門判断を早期に一つの汎用 prompt にまとめない。部門ごとの品質と引き継ぎの測定を維持したまま共通化する。

## 調査の結論と未実施事項

法務から始める場合の参照点は、専門製品の根拠・Word 連携と、社内共通基盤の権限・版・承認・実行履歴の接続である。初期 PoC の評価と停止能力を先に定義する。自律度を上げる根拠は、導入社数や削減時間の宣伝より、自社 task での重大不備、例外、手戻り、運用費用の測定に置く。

社内接続、実データ評価、model training、製品契約、法務専門家による新指針の適用判断は、調査レポートの後に行う実装・導入検証であり今回の成果とは区別する。
