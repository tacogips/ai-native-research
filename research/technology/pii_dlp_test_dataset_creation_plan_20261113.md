# PII検知・DLPのテストデータセット作成計画

作成日：2026年11月13日。改訂：検出精度の検証を主目的とした敵対的レビュー反映版。状態：作成計画。データ本体の作成・取得・検知器の測定は未実施。

**複数種類の文章・表・画像を組み合わせ、個人情報を含むファイルと含まないファイル、その両方を配置したディレクトリを作る。** 主目的はDLPツールの検出精度の検証であり、取得・解析・文字認識・情報分類のどこで取りこぼすかを測る。送信・共有の制御試験は任意の補助評価へ分離する。DLPは情報の持ち出し等を制御する仕組み、PIIは本計画では検知対象とする個人に関する情報を指す。

本計画の件数・優先度・試験規則は設計案。実在者の非公開情報やログイン後の業務資料を使わず、公開の合成資料、公開説明に基づく独自の架空例、条件を確認した公開標本を元にする。完成した資料や性能を示すものではない。


**作成規模はLIGHT（600MB）、MEDIUM（2GB）、MAX（15GB）の3段階から選ぶ。** 具体的な配分と完了条件は11節。3〜10節の元文書1,200件・形式ごとの20件等はMAXの基準とし、LIGHT・MEDIUMでは11節の件数を優先する。対象情報・読取状態・検出精度の定義は全版で共通とする。

## 1. 目的と対象範囲

主評価は、①対象の情報を種類別に検知できるか、②含まれない資料を誤検出しないか、③形式・暗号化・権限・格納位置の違いで検出能力がどう変わるか、④ファイル・圧縮内の項目・ディレクトリを漏れなく検査できるか、⑤追加・更新後の結果が正しいか、の5点。位置を出力しない製品はファイル判定として評価し、位置抽出の得点を推定しない。操作制御のL群は検出精度の得点に合算しない。

対象項目は、氏名、メール、電話、住所、性別、生年月日、マイナンバー、会員ID、運転免許証、パスポート、カード番号、銀行口座、職歴、学歴、年収、家族構成、および本人に結び付く購買・予約・閲覧・検索・応募の情報、要配慮個人情報。項目の定義と出典は[22項目の調査](personal_information_dataset_creation_methods_20261113.md)を継承する。

**予約・購買等の業務の種類ごとに独立した大規模履歴集を作ることは必須にしない。** 氏名・連絡先・会員ID等を含む確認書・明細・通知・一覧表の一部として収録すればよい。本人に結び付かない商品一覧や予約枠は陰性例とする。家族構成・信条等は履歴書の必須欄へ加えず、別の申告・相談記録等で扱う。

|---|---|---|
| 重大 | 未対応・暗号化の陽性を分母から落とせば、ほとんど読めない製品でも高得点になる | 読めた資料の検出精度と、要求範囲全体の読取成功・失敗・未対応の件数を併記（2・10節） |
| 重大 | 暗号化・シート保護・共有権限を同じ「パスワード保護」にすると正解が誤る | 形式F群と保護K群を分離。Google Sheetsをクラウド資料として追加（6節） |
| 重大 | ファイル内に番号が残っていても、一つ氏名を検知すればファイル検出は成功にできる | ファイル検出・種類検出・全対象回収を別採点（10節） |
| 重大 | 陰性600件や各形式20件で低い誤警告率を証明できると誤解する | 旧件数を試作規模に限定。固定評価用の独立標本と信頼区間を別設計（10節） |

| 高 | PIIの意味分類と文字列検知が混在し、製品にない分類まで誤検出と判定する | 原子項目・本人への関係・文書種類の正解を分離。製品出力への対応表を固定（2節） |
| 高 | 本文以外をP1にすると非表示シート、画像、コメント等の主要な取りこぼしが残る | 非表示セル、数式、画像、属性、添付等をP0へ追加（6節） |

| 高 | 解析不能な陰性をすべて拒否する製品が、精度が高いように見える | 内容陽性・内容不明・形式警告・操作拒否の出力を分離（2・10節） |

| 高 | 感度調整後に同じ最終評価を繰り返すと未知資料の成績ではなくなる | 設定を事前固定し、調整資料・最終評価・公開参考資料を分割（10節） |
| 中 | 全組合せは膨大なのに、実施済み・未作成・未対応を管理していない | 必須の組合せ表と作成状態を成果物へ追加。未実施を0件成功としない（6・9節） |

## 2. 正解の分け方

合成情報は通常、実在者に関する法的な個人情報そのものではない。本計画では合成の氏名や病歴等を、検知・保護の試験対象として陽性にできるようにする。

| 軸 | 正解として記録する内容 | 混同しないこと |
|---|---|---|
| 作成由来 | 独自合成、公開合成、公開実標本、出典・版・条件 | 架空だから検知の陰性、公開だから送信可、とはしない |
| 検知対象 | 種類、値、文字位置／画像領域／表の位置、対象人物、関係・時点 | 氏名だけの検知と、本人に結び付く経歴・病歴等の検知は別 |
| 検査状態 | 完了、未対応、権限不足、復号不能、破損、時間・容量上限等 | 対象なしと未検査を分ける |
| 法的な分類 | 合成例で想定する分類、個人関連情報、非該当、要確認等 | データ提供者の分類を日本法上の確定正解へ自動変換しない |
| DLP規則 | 利用者、操作、送信先、対象範囲、許可期限、規則版 | 対象情報があることと、操作が禁止されることは別 |
| 操作結果 | 許可、拒否、保留、伏字後に許可、通知、監査記録 | 誤検知、真検知だが業務許可、通知抑制を分ける |

性別や学歴等の属性は、架空の本人に帰属する文脈で陽性を作る。一般的な説明、空欄の項目名、誰にも帰属しない統計を同じ正解にしない。会員IDによる別表照合を必要とするものは、照合資料と利用可能な範囲を試験条件へ付ける。


### 内容の正解と検査可能性を独立させる

暗号化前に陽性と確認した文書は、暗号化後も内容の正解は陽性である。鍵がない条件では、ツールに期待する出力が「内容不明・復号不能」になるだけで、陰性にはならない。陰性の暗号化資料も同数用意し、単に暗号化を警告する機能をPII検出として加点しない。

各対象の正解を、①原子項目（氏名、番号など）、②人物と属性の関係（誰の病歴か等）、③文書種類（免許証など）に分ける。番号のみ・氏名のみの検知で文書種類や病歴の検知も成功としない。法的分類は別の参考注釈で、単純な文字抽出器に法律判断を要求しない。診断の否定も健康情報になり得るので、一律の陰性ではなく、原子項目・否定・関係の正解を付ける。

対象製品ごとに、対応する分類名、必要な前後の語、最小検出件数、信頼度のしきい値、検査する場所、文字認識の有無、暗号鍵の供給方式を評価前に固定する。銀行口座番号、会員IDなど前後の情報がないと意味が曖昧な項目には、単独の値・見出し付き・名義等の関連情報付きの例を用意する。部分的な対応、文書全体の警告だけ、位置なしの出力を、完全な抽出に変換しない。最小検出件数が設定できる製品では、同じ値の反復と異なる値の複数出現を分け、しきい値の直前・同値・直後を作る。独自辞書や登録済みデータとの照合機能は、登録あり／なしを別条件にし、標準設定の成績と混ぜない。

検査範囲は二つ記録する。**要求範囲**は利用者が検査したい全資料・格納箇所で、製品の都合では縮めない。**製品の宣言対応範囲**は比較前に固定する。両者の差を未対応として報告し、部分範囲の完了を資料全体の完了と表示しない。

### 陽性群で必ず分散させる条件

- 一種類だけの情報、複数種類の情報、複数人物、同姓同名、本文と署名で別人物。
- 問い合わせ本文、末尾の署名、長文の中央、表の別列、改行をまたぐ値。
- 漢字・読み仮名・異体字、全半角、空白・ハイフン、和暦・西暦、住所の建物・部屋番号。
- 会員ID・注文番号・口座番号等が似た書式の例。検査数字の正否と、番号の意味の正解を分ける。
- 職歴・学歴・所得・家族構成は、単語の検知と本人への帰属を分ける。家族の病歴は「本人ではないから陰性」とせず、別人物の要配慮情報として扱う。
- 閲覧・検索・応募は、氏名・ID等を含む小さな文書内の記録として追加し、全5種類の行動情報の例を最低各10元文書に割り当てる。C01〜C03等に含め、別の600件へ加算しない。

## 6. 作成するファイル形式・保護方式・格納場所

### 6.1 形式の一覧

「形式 × 保護方式 × 格納場所 × 陽性／陰性 × 読取経路」を組合せ表で管理する。P0は初期必須、P1は拡張版。P0の各具体形式・必須条件に陽性・陰性各5元文書を使って試作し、重大な漏れを修正後に各20元文書以上へ広げる。これは動作確認の最低規模であり、精度保証の標本数ではない。同じ内容の形式変換は対にして比較するが、独立標本数は増やさない。列挙した形式は作成対象であり、全製品の対応を意味しない。

| F01 | TXT・Markdown | UTF-8・UTF-16・CP932、改行、長文。文字コードを個別に記録 | P0 |
| F02 | CSV・TSV・JSON・JSONL・XML | 先頭0、引用符内改行、ネスト、列の分離、値のみと見出し付き | P0 |

### 6.2 「パスワード付きGoogle Sheets」の扱い

Google Sheets標準のシート・範囲保護は編集制限であり、パスワードによるデータ保護はできない。したがって、存在しない標準方式を試験項目名にしない。[Google公式説明](https://support.google.com/docs/answer/1218656?hl=en)

代わりに、通常のSheets、編集制限付きSheets、共有権限で読取りを制限したSheets、クライアント側暗号化（端末側で暗号化しサービスへ渡す方式、CSE）付きSheetsを作る。Driveへアップロードしたパスワード暗号化XLSXは別のファイルであり、Google Sheets本体と同一視しない。CSEは対応する契約・管理設定・鍵基盤が必要で、環境がなければ未実施のまま残す。[CSEの利用条件](https://support.google.com/drive/answer/10519333?hl=en)

Googleの説明では、Google WorkspaceのDLP検査はCSE本文へアクセスできず、非暗号化の題名やラベル等は検査対象にできる。これはGoogle側の検査経路の制約であり、復号後の端末を検査する他製品へそのまま一般化しない。[Google Workspace CSE FAQ](https://knowledge.workspace.google.com/admin/security/client-side-encryption-faq)

Excelも開封用の暗号化、変更用パスワード、シート保護、ブック構造保護を分ける。編集保護だけで本文が復号不能になるという正解を付けない。[Microsoftの保護方式の説明](https://support.microsoft.com/en-us/excel/protection-and-security-in-excel)、[開封保護](https://support.microsoft.com/en-us/excel/get-started/protect-an-excel-file)

### 6.3 保護条件の一覧

下記は原則として同じ陽性・陰性の元文書に重ねる条件。保護された資料を一律に陽性にはしない。ここでいう権限は画面を操作する利用者ではなく、実際に検査するサービスや端末の主体に対する権限を指す。パスワードを受け取る機能がない製品には、評価器が裏で復号したものを渡して「製品自身が復号した」と報告しない。

| ID | 保護・資格情報の条件 | 期待する確認結果 | 優先 |
|---|---|---|---|
| K01 | 保護なし | 内容の陽性／陰性を通常検査。保護付きとの比較基準 | P0 |
| K02 | 編集・構造保護のみ | 読取り可能な内容は検出。編集できないことを復号不能としない | P0 |
| K03 | 暗号化、正しい鍵を製品の対応経路へ供給 | 復号・抽出・検知を確認。非対応はそのまま記録 | P0 |
| K04 | 暗号化、鍵を供給しない | 本文は不明・復号不能。暗号化検知とPII検知を分離 | P0 |
| K05 | 暗号化、誤った鍵を供給 | 復号失敗。対象なし・検査完了と報告しない | P0 |
| K06 | 外側と内側で異なる鍵、一部だけ供給 | 読めた部分と未読部分を項目ごとに報告 | P0 |
| K07 | クラウド資料の読取権限あり | 実際の検査主体が取得できる範囲で内容検出 | P0 |
| K08 | クラウド資料の読取権限なし・取消 | アクセス拒否または列挙不能を記録。空フォルダ扱いしない | P0 |
| K09 | CSE資料、復号権限のないサービス経路 | 本文不明。平文の名前・属性だけの検出は別に記録 | P0 |

| K11 | 匿名リンク・組織限定・指定利用者、権限変更 | 公開／非公開と内容陽性／陰性は独立。取得範囲・更新時間を測る | P0 |

### 6.4 読取経路と必須の組合せ

ローカル保存ファイル、同期フォルダ、クラウド接続API、ブラウザー／端末で復号後の内容、出力ファイルを別の経路として記録する。単なるクラウド資料への参照ファイルを読んでも本文を読んだことにはしない。元のクラウド資料に対応する版・時点・全シート一覧と、取得した資料の対応を固定する。

Google DriveのCSV・TSV出力は先頭シートだけなので、それだけの取得を全シートの検査として採点しない。出力物自体の正解と、元資料に対する取得の網羅性を二つ出す。[Google Drive出力仕様](https://developers.google.com/workspace/drive/api/guides/ref-export-formats)

最低限、①各具体形式の平文陽性／陰性、②ZIP・7z・暗号化XLSX・開封保護PDFにK03〜K05、③Excel編集保護にK02、④SheetsにK07〜K09・K11、⑤F28の内側だけ陽性／全陰性／内側復号不能、⑥F09・F13・F14・F27の各格納場所だけ陽性、⑦上限境界の直前・同値・超過、を必須の組合せ表へ登録する。各試験の対には同じ構造の陰性を用意する。K10は端末経路の評価を行う場合に必須とする。

全組合せは不要だが、残る組合せは二条件の組をできるだけ覆う選び方とし、省略した条件を一覧に残す。入れ子深度、圧縮前後サイズ、項目数、ページ数、行数、最大セル位置、本文中の対象位置（先頭・中央・末尾）を記録する。制限値が非公開なら段階的な測定で境界を推定し、推定と明示する。

### ディレクトリ集計の正解

集計は「対象があるか」と「検査が完了したか」の二軸にする。

| 対象の発見 | 検査の完了 | 表示・期待値 |
|---|---|---|
| あり | 完了 | 対象あり、検査完了 |
| あり | 未完了 | 対象あり、残りに未検査あり |
| なし | 完了 | 検査範囲内に対象なし |
| なし | 未完了 | 対象未発見、判定未完了 |

ディレクトリの対象有無は、宣言した範囲の子孫の検知結果等から集計する。親の名前が「機密」だから全子ファイルを陽性にする、という採点は行わない。ファイル名・親ディレクトリ名自体の識別情報や、場所に基づくアクセス制御は、それぞれ独立した根拠として記録する。

## 8. 任意の補助評価：DLPの操作試験

主目的の検出精度測定の完了条件にはL群を含めない。L群のP0／P1は操作試験を実施する場合の優先度である。同じファイルに、利用者・操作・宛先等の条件だけを変えた試験を重ねる。以下は試験専用の規則であり、一般の個人情報保護法や全製品共通の動作を表すものではない。接続先は管理するローカルの受信先等とし、本番の外部送信を必要としない。

試験規則の初期設定：対象情報ゼロ・検査完了なら許可。対象ありは認可された内部利用者・内部保存先に限定して許可し、認可のない外部への操作は拒否。検査未完了は保留。伏字後の許可は、その規則を明示して有効にした試験だけで使う。種類・宛先・例外の優先順位と期限を規則版に固定する。

| ID | 試験条件 | 初期規則での期待結果 | 優先 |
|---|---|---|---|
| L01 | 陽性ファイルを認可された内部利用者が内部へ転送 | 許可。真検知は残し、誤検知登録で消さない | P0 |
| L02 | 同じ陽性ファイルを許可のない外部へ転送・添付 | 拒否。拒否理由・対象・適用規則を記録 | P0 |
| L03 | 陰性・検査完了のファイルを内外の試験先へ転送 | 許可。誤った遮断を測る | P0 |
| L04 | 要配慮情報を含むファイルを許可のない先へ送る | 拒否。一般PIIと種類を分けて記録 | P0 |
| L05 | 必要な全対象を伏字にしてから外部へ送る | 原文を拒否し、再検査合格後の生成物だけを許可する規則で確認 | P1 |
| L06 | ディレクトリ一括送信に陽性が一つ混在 | P0は一括操作を拒否。陰性ファイルの単独送信とは分けて評価 | P0 |
| L07 | 陽性の一部に明示した業務許可がある | 指定した人物・項目・場所・操作・期限の範囲だけ許可。その他の対象へ波及させない | P0 |
| L08 | 許可済みファイルへ別の対象を追加、外部共有へ変更 | 再検査・再認可し、既存許可の対象外なら拒否 | P0 |
| L09 | 許可取消・期限到来・利用者の権限変更 | 変更後の規則で拒否。過去の許可を使わない | P0 |
| L10 | ファイルが変化して、検査時と送信時で内容が異なる | 版・内容の対応を確認し、不一致なら送信前に再検査または保留 | P0 |
| L11 | 暗号化・解析失敗・時間切れ・容量超過 | 検査未完了として保留。対象なしで許可しない | P0 |
| L12 | 通知抑制や対応済み登録がある同じ対象を再送信 | 通知の集約と、送信可否の規則を独立して適用 | P0 |
| L13 | 同じ内容をコピー・名前変更・別ディレクトリへ移動 | 内容検知の結果と、場所・権限による再認可を分離 | P0 |
| L14 | 読取り、コピー、添付、アップロード、共有先変更 | 製品が対応する操作ごとに拒否／許可を検証。未対応操作を成功扱いにしない | P1 |

P0ではL01〜L13のP0条件を各5例以上で確認する案。ファイル例を操作条件ごとに再利用した場合は、操作試験数と独立したファイル数を別に数える。送信前に拒否できる方式と、送信後に通知する方式を同じ漏えい防止成功率で比較しない。

## 9. 保存する成果物と配置

試験対象と正解を別のルートへ置く。正解JSONや人物の設定が検査対象へ混入すると、陰性ディレクトリも陽性になるため、検知器へ渡す入力範囲を固定する。

```text
pii-dlp-testdata/
  inputs/
    files/                 # ファイル単体の入力
    trees/                 # ディレクトリ構成D01〜D16
  ground_truth/            # 対象の位置・人物・検査状態の正解
  manifests/               # 配置、版、ハッシュ、出典、条件
  cloud_recipes/           # 架空のSheets等の作成仕様。実環境の認証情報は含めない
  coverage/                # 必須の組合せ・実施状態・要求と対応の差
  policies/                # 試験用の許可・拒否・保留規則
  scenarios/               # 操作、更新、取消等の時系列と期待値
  generation/              # 乱数の初期値、ひな形版、作成手順
```

上は設計上の構成例。評価用パスは`case-001/file-001.pdf`等の中立な名前にする。`positive`や`negative`の名前が答えになる配置は開発用だけとし、最終評価には使わない。D01等の識別子は正解側の配置表で管理する。ファイル名やパスの情報を評価する専用試験は例外として明示する。

| 成果物 | 必須の内容 |
|---|---|
| ファイル台帳 | ファイルID、相対経路、実形式、SHA-256、元文書ID、派生元、出典・条件、版 |

採点で原文の値を表示する場合も試験用の架空値に限定する。公開実標本を含める必要がある場合は、利用条件・由来の確認を行い、配布可能な独自合成群と混ぜて一律の条件にしない。

生成前の文章だけを正解にしない。生成後に対象アプリでの描画と、生成器とは独立した抽出方法を照合し、文字消失・計算結果・描画外の文字・伏字の残存を確認する。画像の座標は変換後に付け直し、画像に存在しない値を正解へ残さない。正解を作る担当には評価対象製品の検出結果を見せず、不一致は別担当の確認で裁定する。

このリポジトリには公開資料に基づく設計と独自の架空例の仕様を保存する。将来クラウド環境を操作して得る非公開の識別子・画面・設定・測定ログは、リポジトリへ追加しない。

初期1,200元ファイルは作成規模の案。全量を最終評価とするのではなく、開発・調整・固定評価へ重複を避けて割り当てる。22項目・各形式の評価数が不足すれば追加する。人数、元文書数、派生数、ディレクトリ配置数、操作試験数を一つの件数へ合算しない。

### 10.1 評価資料の分割と合成資料への偏り

1,200元文書は試作・作成基盤の規模とする。最終評価の標本数を満たすとはみなさない。人物、元文書、ひな形の系統、公開資料の由来、形式違い・暗号化違いをまとめた単位で開発・調整・最終評価を分ける。同じ値をPDFへ変換しただけのものを別の未知資料として採点しない。

最終評価には、公開資料の再利用群と独自作成群を区別し、未知のひな形、別の作成方法、人が書いた架空文書の群を含める。公開資料が製品の学習に使われたか不明なら「学習への混入は不明」と記録する。「架空」「サンプル」、同じ住所、同じメールドメイン、同じ透かしを陽性だけに入れると手掛かりになるため、そうした表示の有無を陽性・陰性に偏らせない。見本の本人確認書類は見本である旨を維持したまま、周辺条件を揃えて採点する。

番号は、①公式試験値、②書式と検査数字が整合する独自試験値、③検査数字が不正な値、④似た一般の番号、を分ける。既知の試験値を除外する製品に対して①だけで能力を推定しない。書式が正しくても実在・発行済みとは限らず、試験値を実サービスで照会しない。独自試験値は意図せず実在値と一致する可能性もあるため、実在性の保証は付けない。

日本語だけの文書に加えて、日本語と英字の氏名・住所・項目名が混在する群を設ける。合成資料の成績を実在資料全体の成績と主張しない。実在資料の外部検証を行う場合は、公開・利用条件を満たす別群として結果を分ける。

### 10.2 採点の単位・分母・照合規則

検知対象の種類と試験入力の版を固定し、結果を次の粒度で報告する。採点用の正解は製品へ渡さない。

| 指標 | 分母・成功条件 | 歪みを防ぐ規則 |
|---|---|---|
| ファイル検出再現率 | 内容陽性のファイルのうち、正しいPII警告を少なくとも一つ得た割合 | 暗号化・形式警告や操作拒否だけは成功にしない |
| ファイル・種類別再現率 | その種類を持つファイルのうち、その種類を検出した割合 | 氏名だけの警告を口座・病歴等の成功にしない |
| 対象単位の再現率・適合率 | 正解の個々の出現と検出結果を一対一に照合 | 同じ値の反復も場所別。重複警告は集約規則を事前固定 |
| 全対象回収率 | 正解のすべての対象を拾えた陽性ファイルの割合 | 位置を返さない製品は算出不能。ファイル警告から推定しない |
| 陰性ファイル誤警告率 | 確定陰性ファイルのうち、誤ったPII警告を得た割合 | 内容不明の通知・暗号化通知・操作拒否とは別集計 |
| 列挙・取得・解析・文字認識の網羅性 | 各段階の要求対象のうち完了した割合 | 入れ子内項目、シート、ページ、添付、格納箇所の欠落も含める |
| 不明・失敗率 | 全投入資料のうち検査未完了の割合 | 陽性／陰性別、原因別、形式別を併記 |
| ディレクトリ検出・誤警告 | 配下の内容正解と集計出力を照合 | 一つ発見できた割合と、全陽性を回収できた割合を分ける |

主結果は、**読めた資料における検出精度**と、**要求範囲全体の読取状態**を分けて報告する。読めない文書の結果は「読めなかった」であり、PIIの検出漏れや陰性とはしない。検出精度の分母には読取完了した資料だけを使い、全投入件数、読取完了件数、読取失敗件数、未対応件数、未実施件数を必ず併記する。失敗理由は権限不足・復号不能・破損・容量超過・時間切れ等に分ける。これにより、読取り可能な範囲が狭い製品の高い検出精度を、全資料への対応力と誤認させない。

一部だけ読めた資料は「部分読取」として別集計する。読めた部分の対象は部分読取群の検出精度として採点できるが、資料全体の検査完了とはしない。読取完了の判断は製品の成功表示だけに頼らず、正解側のページ・シート・添付等の取得範囲と照合する。内容を取得できたのにPIIを見逃した場合は検出漏れとする。読取失敗を後から検出漏れに振り替えたり、その逆を行ったりしない。製品間の検出精度の直接比較には、両製品が読取完了した共通資料群の結果も添え、各製品の読取範囲は別に示す。

さらに、抽出の切り分け用として、同じ資料から人手確認した正規の文字列を直接渡す比較を設ける。製品に直接入力経路がある場合だけ実施し、通常のファイル読取りの成績へ混ぜない。これにより、画像から文字を取り出せないのか、取り出した文字を分類できないのかを分ける。

位置採点は、正規化前のUnicodeコードポイントに基づく開始・終了位置、セル番地、ページと領域などを形式ごとに定義する。完全一致と緩和一致を分け、緩和一致の範囲重なり基準・種類一致・正規化規則は採点前に固定する。製品の抽出順序に依存する位置は元資料へ対応付ける。対応不能なら位置得点を算出せず、ファイル得点だけを報告する。

各種類・形式・保護・格納場所・経路別の件数と結果を示す。全対象を合算した平均と、種類ごとに等しく重みを置く平均を併記する。実務の出現率が不明なら、600対600の均衡資料から現場の適合率を推定しない。低混入率のD06は列挙・負荷の試験であり、その複製を独立標本へ水増ししない。

### 10.3 必要件数と信頼区間

精度の受入目標は、固定評価の実行前に、種類・形式ごとの許容見逃し率と許容誤警告率として定める。最終結果を見てから合格基準を緩めない。製品と運用条件が未指定なので、現段階では合否の数値を確定しない。

目安として、独立な陰性600件で誤警告0件でも、片側95%の二項分布による上限は `1 - 0.05^(1/600)`、約0.50%である。誤警告率0.1%以下を同じ方式で示すには、誤警告0件で少なくとも2,995件の独立陰性が必要になる。各形式20件で見逃し0件でも、同じ上限は約13.9%である。これらは独立同分布を仮定した設計上の例で、実務分布への保証ではない。

したがって、初期1,200件と形式ごとの20件を「高精度の証明」と呼ばない。性能を主張する種類・形式ごとに追加の独立標本を確保し、標本が足りない群は参考値と明記する。派生資料は元文書・ひな形系統単位でまとめて再標本化し、信頼区間の水増しを避ける。複数製品は同じ固定資料・同じ事前条件で比較し、対応範囲と製品固有設定を別表にする。

### 10.4 実行条件と完了条件

製品版、規則版、分類しきい値、検査の最大件数・容量・階層、文字認識の設定、復号経路、使用機器、試験の観測期限を記録する。更新後の検出は、その期限内に新しい版の正しい結果が出たかを測る。初回と再検査で保存済み結果の使い回しがある場合は別条件にする。非同期・非決定的な処理は回数を固定して繰り返し、ばらつきと未完了を残す。

完了条件は、①対象22項目の定義と製品出力への対応表、②F・K・格納場所・経路の必須組合せ表、③生成物で確認した正解、④重複を避けた固定評価資料、⑤読取状態と検出結果の分母を区別する採点器、⑥条件別の件数・精度・未対応・未実施の報告、を揃えること。環境未準備のCSE等を含む場合は「ローカル部分のみ完了」等と範囲を限定し、全計画の完了とはしない。

L群を追加実施する場合は、意図しない許可、過剰な拒否、保留、伏字後の残存、許可失効後の判定、監査記録を別報告する。重大な操作試験で意図しない許可が1件あればその規則・経路を不合格とする案だが、0件でも現実の漏えい率0を保証しない。

LIGHTでもTXT、表形式、メール、DOCX、XLSX、XLS・XLSM・XLSB、PPTX、文字PDF、画像PDF、PNG・JPEG・TIFF、ZIP・7z・TAR系、Google Sheetsとその出力物を対象に残す。XLSB等の実形式の作成環境がなければ未作成と記録し、拡張子変更や別形式への置換で完了にしない。

正しい鍵・鍵なし・誤った鍵の試験は同じ暗号化ファイルを再利用できるため、鍵条件ごとに別ファイルを複製する必要はない。権限変更も同じクラウド資料の状態を変えて実施し、状態・時点ごとに正解を記録する。これにより、容量を抑えて条件の幅を維持する。

D06の陰性999件は、小さな陰性資料の実コピーを使い、正解上は複製として記録する。PIIあり／なしの単体ファイルと、陰性だけ・陽性だけ・混在・部分読取のディレクトリは全版で残す。

### 11.4 容量予算

下表は通常ファイルとして展開した評価用一式の予算。元文書は単体ファイル枠に含め、二重に数えない。1件の平均サイズは設計仮定で、生成後の実測で調整する。

| 内訳 | LIGHT | MEDIUM | MAX |
|---|---:|---:|---:|
| 文字・表・Office等 | 700件×50KB＝35MB | 2,000件×50KB＝100MB | 5,000件×50KB＝250MB |
| 画像・画像PDF等 | 200件×0.8MB＝160MB | 700件×0.8MB＝560MB | 2,000件×2MB＝4,000MB |
| 試験対象のZIP等・複合資料 | 100件×1.5MB＝150MB | 300件×2MB＝600MB | 1,000件×5MB＝5,000MB |
| 正解・台帳・生成仕様 | 35MB | 60MB | 250MB |
| ディレクトリへの実コピー | 100MB | 480MB | 4,000MB |
| 調整用の余裕 | 120MB | 200MB | 1,500MB |
| 合計上限 | **600MB** | **2,000MB** | **15,000MB** |

容量は入力ファイル、正解、台帳、独自の生成仕様、ディレクトリ配置に含まれる全ファイルの論理バイト数の合計で検査する。OSのファイル管理領域、生成用ソフトウェア、モデルの重み、一時描画画像、実行ログ、クラウドサービス側の保存領域はこの上限に含めず、別記する。配布用ZIPを評価用一式と同時に保存すれば、その分のディスク領域が追加で必要になる。

試験対象のZIP等のファイル自身は上限に含める。その内部を検査中に展開した作業領域は別途必要であり、台帳に展開後のバイト数も記録する。圧縮ファイルを除く通常資料をまとめた配布ZIPの小ささを、評価用一式の小ささとして報告しない。

クラウドの出力物をローカル評価用一式に同梱する場合は、上表の対応する形式枠に含める。Google Sheets本体のクラウド保存量はローカル上限と別管理し、4／12／40資料という数で上限を管理する。CSE環境がなければクラウド部分は未実施で、ローカル部分だけ完成したと報告する。

### 11.5 容量を守るための作成方針

- 文書は短い帳票・数ページの資料を中心にし、長文・多ページ・多数行の条件は専用の少数例へ集約する。LIGHTでも先頭・中央・末尾に対象がある例を残す。
- 画像の基準群は日本語の小さい文字を人が読める品質に保つ。容量のために全画像を低画質化すると文字認識の評価が変わるため、基準群と劣化群を分ける。画像が予算を超えた場合はまず同条件の派生数を減らす。
- 画像は形式に適した圧縮を使う。ただしTIFFや無圧縮の試験など、形式自体が評価対象なら圧縮方式を勝手に変更しない。
- 同じ元文書を必要な形式だけへ変換し、全元文書×全形式×全保護条件の全展開は行わない。正解には値の共通定義と各ファイルの位置対応を保存し、同じ画像を正解側へ重複保存しない。
- ディレクトリの陰性複製には小さな実ファイルを使う。リンクを追えない製品でも試験できるよう、必須の配置をシンボリックリンクで代用しない。
- 作成後に実バイト数を集計し、上限超過時は余裕枠を使い、次に冗長な派生を減らす。必須条件・正解・陰性対を黙って削除しない。削除できなければ計画差異として未完了を報告する。
- 実際の製品制限がLIGHT等の容量上限を超える場合、その境界試験は「容量枠外」として別作成にする。小さい代用品を実際の境界試験の合格とはしない。

### 11.6 作成順序と受入条件

1. 全版で共通の正解仕様、人物・文書・形式変換の識別子、乱数初期値、形式別の作成器、状態記録を実装する。
2. LIGHTの240元文書を作り、まず形式ごとに1組を生成して、実形式・描画・読取り・暗号化と容量を検証する。その実測平均から残りの容量見積りを更新する。
3. LIGHTの必須条件を埋め、600MB以内で保存できること、全22項目、PIIなしのファイルとディレクトリ、読取不能条件の正解を確認する。正解未確認のファイルは完成件数に含めない。
4. MEDIUMは元文書を600件へ増やし、P0を厚くしてP1を追加する。MAXは1,200件と全形式群へ広げる。LIGHTのファイルを複製しただけで元文書数を増やさない。
5. 各版の完了報告には、実バイト数、独立元文書数、形式派生数、配置数、圧縮内部項目数、実施／未実施条件を載せる。計画上限と実測値を区別する。

同じ元文書の派生は一つの分割に固定する。LIGHTからMAXへ増やす間に検知器の調整へ使った資料は、MAXの未知資料としての最終評価には使わない。各版の固定評価は、まだ調整に使っていない人物・ひな形系統から確保する。評価対象製品の精度改善を繰り返す場合は、既存固定評価とは別に新しい留保資料を作る。

この3段階の容量予算には、全種類で低い誤警告率を統計的に証明するための大量の独立文書の追加は含めない。誤警告率等を数値保証する評価は、10.3節に従って必要標本数を別に設計する。

## 12. この計画で作らないもの

初期版はデータ本体と検査・制御の試験条件を作る計画。実在者の非公開資料の収集、実際の決済・送金、本人確認の突破、証明書の真贋を保証する評価、採用可否等の判断用モデルの作成は対象に含めない。音声・動画・手書き文字の大規模評価は、必要に応じ別版で追加する。
