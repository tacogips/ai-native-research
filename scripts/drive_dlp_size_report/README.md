# Drive DLP 検知 × ファイルサイズ抽出（スプレッドシートと Apps Script のみ）

Google Drive の DLP（Data Loss Prevention、機密情報の検知・保護）規則に一致したファイルのうち、サイズが n バイト以上のものを Google スプレッドシートへ一覧にする。定期実行し、前回の実行以降に新しく検知されたファイルだけを追記する。外部のサーバーやサービスアカウントは使わない。必要なのはスプレッドシートと、そこに紐づく Apps Script だけである。

## 仕組み

```
DLP規則(複数条件)  ──検知──▶  監査ログ(Reports API, applicationName=rules)
                                   │ content_matched イベント
                                   ▼
              Apps Script(時間主導トリガー)
                 1. 前回の終了時刻 − 重ね幅 〜 今 の期間を取得
                 2. 規則名で絞り込み(OR / AND)
                 3. 記録済みのファイルIDを除外
                 4. Drive API でサイズを並列取得し、n 以上だけ残す
                 5. 「検知結果」シートへ追記し、透かし(処理済み時刻)を進める
```

- **DLP の複数条件**: 条件の組合せは DLP 規則の側で設定する（例：`本文に「社外秘」を含む` かつ `クレジットカード番号の検知器に一致`）。さらに、スクリプトの `RULE_NAMES` に複数の規則を指定できる。`REQUIRE_ALL_RULES=TRUE` にすると、指定したすべての規則に一致したファイルだけを記録する（規則をまたぐ AND）。一致が別々の実行にまたがった場合も、非表示の `_部分一致` シートに途中経過を保持して判定する。
- **サイズ条件**: Drive API の `size`（バイナリの容量）を使う。Google ドキュメント形式のファイルは `size` を持たないため、`取得失敗` シートに「サイズなし」として記録する。
- **差分の取得**: 処理を終えた期間の終了時刻をスクリプトのプロパティに保存する。次回はその時刻から `OVERLAP_MINUTES` だけ遡って取得し、監査ログの到着遅れによる取りこぼしを防ぐ。重ねて取得した分は、記録済みのファイル ID を除外して重複させない。
- **数十万件への対応**: 1回の実行が `MAX_RUNTIME_SECONDS` を超えそうになったら、Reports API のページ位置を保存して終了する。1分後に一度だけ実行される続きのトリガーを登録し、次のページから再開する。サイズは `UrlFetchApp.fetchAll` で並列に取得し（既定50件ずつ）、シートへはまとめて書き込む。
- **全体に及ぶエラー**: 認証切れ、API の無効化、速度制限などのエラーではファイルを処理済みにしない。実行を中断し、期間もページ位置も進めないので、次回に同じ範囲をやり直す。

## 監査ログのイベント名について

[Rules 監査アクティビティの公開文書](https://developers.google.com/workspace/admin/reports/v1/appendix/activity/rules)には `rule_match` などのイベントが載っている。しかし、2026年11月20日に試験用テナントで Drive DLP の監査のみの規則を観測したところ、内容の一致は `content_matched`（`rule_type=DLP`、`data_source=DRIVE`、ファイル ID は `resource_id`、規則は `rule_name`／`rule_resource_name`）として記録され、`rule_match` は0件だった。そこで既定値を `content_matched` にし、設定の `EVENT_NAME` で変更できるようにした。

## 導入手順

1. 新しいスプレッドシートを作り、「拡張機能 → Apps Script」を開く。
2. `src/Code.js` を `Code.gs` に、`src/appsscript.json` をマニフェストに貼り付ける（マニフェストは「プロジェクトの設定 → 『appsscript.json』マニフェスト ファイルをエディタで表示する」で表示される）。マニフェストでは Admin SDK Reports と Drive v3 の高度なサービスを有効にする。高度なサービスを有効にすると、既定の Cloud プロジェクトでも Drive API が使えるようになる。
3. エディタで `setup` を実行して権限を承認する。`設定`・`検知結果`・`取得失敗`・`実行履歴` の各シートが作られ、定期実行のトリガーが登録される。
4. `設定` シートで値を変える。`TRIGGER_INTERVAL_MINUTES` を変えたときは `setup` を再実行してトリガーを登録し直す。

実行者は監査ログを読める管理者である必要がある（`admin.reports.audit.readonly`）。

| キー | 既定値 | 意味 |
|---|---|---|
| `MIN_SIZE_BYTES` | 1048576 | この値以上のファイルだけを記録する |
| `RULE_NAMES` | 空 | 対象とする DLP 規則の表示名（改行またはカンマ区切り）。空ならすべての Drive DLP 規則 |
| `REQUIRE_ALL_RULES` | FALSE | TRUE なら、指定したすべての規則に一致したファイルだけを記録する |
| `INITIAL_LOOKBACK_DAYS` | 7 | 初回の実行で遡る日数 |
| `OVERLAP_MINUTES` | 180 | 前回の終了時刻から重ねて再取得する分数 |
| `TRIGGER_INTERVAL_MINUTES` | 60 | 定期実行の間隔（1, 5, 10, 15, 30 または 60 の倍数） |
| `MAX_RUNTIME_SECONDS` | 300 | 1回の実行で処理する上限の秒数（Apps Script の上限は6分） |
| `DRIVE_FETCH_BATCH` | 50 | Drive API を並列に呼ぶ件数 |
| `EVENT_NAME` | content_matched | 取得する Rules 監査イベントの名前 |

## 制約

- **他のユーザーのファイル**: サイズの取得は実行者の権限で行う。実行者が読めないファイルは `取得失敗` に「Drive API 404」として記録される。組織全体を対象にする場合は、ドメイン全体の委任を設定したサービスアカウントのメールアドレスと秘密鍵を、スクリプトのプロパティ `DLPSIZE_SA_EMAIL`・`DLPSIZE_SA_PRIVATE_KEY` に保存する。そうすると、監査ログの所有者として `drive.readonly` で取得する。この経路は署名処理を Apps Script 内で行うが、今回の動作確認には含めていない。
- **割り当て（クォータ）**: `UrlFetchApp` の1日あたりの呼出し回数には[上限](https://developers.google.com/apps-script/guides/services/quotas)がある。数十万件をまとめて初回処理すると上限に届くことがあるため、`INITIAL_LOOKBACK_DAYS` を短くするか、数日かけて取り込む。記録済みのファイルや同じページ内の重複は、Drive への問合せの前に除外される。
- **シートの容量**: 詳しくは下の「API とスプレッドシートの制約の評価」を参照する。
- **判定の単位**: 1ファイルにつき1行。一度記録したファイルは、後で別の規則に一致しても追記しない。行を消せば、次の検知で再び対象になる。
- **監査ログの遅れ**: 監査ログの到着時刻は保証されない。`OVERLAP_MINUTES` より遅れて届いたイベントは取りこぼす可能性がある。試験では、アップロードから約30秒でイベントを取得できた。

## 試験

```sh
node --test scripts/drive_dlp_size_report/test/
```

Apps Script のサービス（スプレッドシート、プロパティ、トリガー、Reports API、UrlFetchApp）を Node.js で模擬し、`Code.js` をそのまま実行する。

| 試験 | 内容 | 結果（2026年11月20日） |
|---|---|---|
| 規模と継続 | 20万ファイル、30万イベント（対象外の規則と Gmail 由来を含む）。時間切れで4回に分けて処理 | 81,924件。期待値と完全に一致し、重複は0件 |
| 差分 | 2回目に新しい検知50件、到着が1時間遅れたイベント、記録済みファイルの再検知を追加 | 新しい検知のうちサイズ条件を満たす25件と、遅れて届いた1件だけを追記 |
| 規則をまたぐ AND | R1 と R2 の両方が必要。片方の一致は次の実行まで保留する | 両方がそろったファイルだけを記録 |

## 実環境での動作確認（2026年11月20日）

試験用の Workspace テナントで、架空の内容（テスト用カード番号、`example.co.jp` のメールアドレス、埋め草の文章）を使って確認した。DLP 規則は監査のみとし、次の2つを作成した。

- 規則A：本文に試験用の対照語を含む **かつ** 「社外秘」を含む **かつ** クレジットカード番号の検知器（POSSIBLE 以上）に一致
- 規則B：本文に対照語を含む **かつ**（メールアドレスの検知器に一致 **または** 「取扱注意」を含む）

n = 1,000,000 バイトとした。

- 1回目（手動、24時間を遡る）: rules 監査イベント213件のうち、対象の規則に一致したもの7件、候補のファイル6件。記録4件、サイズ未満2件、取得失敗0件。
- 2回目以降は 10分間隔の時間主導トリガーで実行した。第2陣を追加した後の最初の実行では、記録が2件（A2、AB2）、サイズ未満が3件（重ね幅の範囲で再評価した小さいファイルを含む）だった。その次の実行では記録0件で、重複行は出なかった。

- 初回の試行では、Apps Script の既定の Cloud プロジェクトで Drive API が無効だったため、403 エラーになった。マニフェストに Drive の高度なサービスを追加して解消した。この経験から、全体に及ぶエラーではファイルを処理済みにしない処理を加えた。

架空のファイル、規則、テナントの識別子は公開しない。

### 1時間ごとの定期実行（2026年11月20日）

`TRIGGER_INTERVAL_MINUTES=60` にして `setup` を実行し直し、トリガーを1時間ごとに登録し直した。その後、約2時間にわたって5分ごとに `実行履歴` シートを読み、実行の時刻を記録した。

| 実行開始（日本時間） | 契機 | 結果 |
|---|---|---|
| 21:28:05 | 10分間隔（変更前） | 完了。追記0件 |
| 21:38:05 | 10分間隔（変更前） | 完了。追記0件 |
| 22:08:16 | 1時間ごと | 完了。追記0件（新しい検知なし） |
| 23:08:16 | 1時間ごと | 完了。追記0件（新しい検知なし） |

- 変更後の自動実行は、ちょうど60分おきだった。21:38 を最後に10分間隔の実行は止まり、2つの実行の間に余分な実行はなかった。トリガーは `runDetection` の1個だけである。
- スプレッドシートを開いていない間も、スクリプトの所有者（管理者）の権限で実行された。
- 起動は毎時0分ちょうどではなかった。Google 側が決めた毎時の時刻（この例では毎時8分ごろ）に起動した。`everyHours` で作る時間主導トリガーは、起動時刻の分を指定できない。
- 間隔を変えるときは、`設定` シートの `TRIGGER_INTERVAL_MINUTES` を変えてから、メニューの「初期設定」（`setup`）を実行する。`setup` は既存の定期トリガーを削除してから作り直すので、トリガーが二重にはならない。停止するときは、Apps Script エディタの「トリガー」画面から削除する。

## API とスプレッドシートの制約の評価

### 今回の検証で上限に達したか

達していない。今回の実環境での確認は小規模である。

- 1回あたりの監査イベントは最大287件。
- 1回あたりの Drive API 呼出しは最大9件。
- 実行は12回。
- 結果は6行。

上限に関わったのは、試験の準備の段階だけである。

- 試験の準備で使った OAuth クライアントの Cloud プロジェクトと、管理者のユーザー設定で、Apps Script API が無効だった。
- Apps Script の既定の Cloud プロジェクトで、Drive API が無効だった（403）。マニフェストに Drive の高度なサービスを追加して解消した。

いずれも割り当て量の上限ではなく、設定の問題である。

### 数十万件で当たりうる上限

上限の数値は[Apps Script の割り当て](https://developers.google.com/apps-script/guides/services/quotas)（2026年11月20日に確認、Google Workspace のアカウントの場合）による。模擬試験の数値は実測ではなく計算上の値である。

| 上限 | 値 | 本実装での扱い | 評価 |
|---|---|---|---|
| 1回の実行時間 | 6分 | `MAX_RUNTIME_SECONDS`（上限330秒）で打ち切り、ページ位置を保存して続きを実行する | 対応済み。打ち切りの判定はページやバッチの区切りで行うため、1回の API 呼出しが長引くと超える余地はある |
| UrlFetch の呼出し | 100,000回/日 | Drive のサイズ取得に1ファイル1回使う。記録済みのファイルと同じページ内の重複は事前に除外する | **初回の大量取り込みで超える**。模擬試験の30万イベント・20万ファイルでは約15万回が必要になる。超えると実行が例外で止まる。処理済みのページは保存されるので翌日に再開できるが、それまで定期実行は失敗し続ける。対策は `INITIAL_LOOKBACK_DAYS` を短くして数日に分けること。上限に達したときに静かに待つ処理は未実装 |
| トリガーの合計実行時間 | 6時間/日 | 10分間隔なら1日144回 | 平常時は問題ない。初回の大量取り込みにかかる時間は、実際の API の応答時間に左右され、未測定 |
| トリガーの数 | 20個/ユーザー/スクリプト | 定期用と続き用の最大2個 | 問題なし |
| プロパティ | 1値あたり9KB、合計500KB | 処理済みの時刻と処理中の期間（1KB未満）だけを保存する | 問題なし |
| Drive API の速度制限 | 429 応答 | 指数的に待って4回まで再試行し、それでも失敗すれば実行を中断する（ファイルを処理済みにしない） | 対応済み。実環境での発生は未確認 |
| スプレッドシートのセル数 | 1ファイルあたり1,000万セル（空のセルを含む） | シートの作成時に列を減らしていない（既定は26列） | **未対応**。結果シートは1行あたり26セル分を占めるため、約38万行で上限に届く。不要な列を削除すれば、11列で約90万行まで入る |
| 記録済みファイルの読込み | — | 毎回の実行の最初に、結果シートのファイル ID の列をすべて読み込む | 数十万行での読込み時間は未測定 |
| AND 指定時の `_部分一致` | — | ページを処理するたびに、シート全体を書き直す | **大規模には不向き**。片方の規則だけに一致したファイルが数十万件たまると、1ページごとの書き直しで実行時間を使い切る。差分だけを書く処理に改める必要がある |

## 検証の再現手順

検証に使ったスクリプトは `verify/` に置いた。トークン、Workspace の識別子、ファイル ID、観測結果は、環境変数 `DLPSIZE_STATE_DIR` で指定したリポジトリ外の保存先に書き込む。

```sh
export DLPSIZE_STATE_DIR=/リポジトリ外の保存先
export DLPSIZE_OAUTH_CLIENT=/デスクトップ型OAuthクライアントのJSON
cd scripts/drive_dlp_size_report/verify
python3 oauth_flow.py 管理者のメールアドレス   # 表示されたURLをブラウザで開いて同意する
python3 create_rules.py --customer customers/C... --org-unit orgUnits/...
python3 create_project.py                      # スプレッドシートと Apps Script を作り、コードを送る
#   → Apps Script エディタで setup を一度実行し、権限を承認する(この操作は画面で行う)
python3 webapp.py action=setup
python3 webapp.py action=config MIN_SIZE_BYTES=1000000 "RULE_NAMES=DLPSIZE-20261120-card-AND-confidential,DLPSIZE-20261120-email-OR-handlewithcare" INITIAL_LOOKBACK_DAYS=1 TRIGGER_INTERVAL_MINUTES=10
python3 webapp.py action=setup                 # 間隔を変えたのでトリガーを登録し直す
python3 upload.py 1                            # 第1陣。監査ログには約30秒で記録された
python3 webapp.py action=run && python3 check.py --json
python3 upload.py 2                            # 第2陣。次の定期実行を待つ
python3 check.py --json
# AND の確認: action=config REQUIRE_ALL_RULES=TRUE → clear.py → action=reset → action=run → check.py
```

画面での操作は次の3つで、今回は Codex の画面操作と利用者の手で行った。

1. Apps Script API の有効化（OAuth クライアントの Cloud プロジェクトと、管理者のユーザー設定の両方）
2. OAuth の同意
3. Apps Script の初回の承認

Codex は、権限を付与する同意のクリックを行わなかった。そのため、同意は利用者が行った。
