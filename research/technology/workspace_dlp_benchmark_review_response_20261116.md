# Google Workspace DLP比較試験のレビュー対応と是正試験設計

公開仕様の再確認日：2026年11月16日。対象は `scripts/workspace_dlp_benchmark/`、`scripts/pii_image_dataset/` と関連設計である。DLPは機密情報の検知・保護、是正は検知後に共有制限や分類ラベル等を適用して状態を変えることを指す。この文書は公開資料と独自の試験設計だけを扱う。実アカウント、識別子、監査記録、実測値、ログイン後の画面は掲載しない。

## レビューの採用範囲

元の小規模試験は検知の準備と二値採点が中心で、所有者自身による権限の付与・取消を、製品の共有遮断成功として扱えないという指摘を採用する。改訂では、検知と是正の正解、観測、指標を分離する。公開コードの単体試験に合格したことは、Workspace上で是正に成功した証拠ではない。

最初の受入条件は次の5点である。

1. 検査を確認できない資料を `not_detected` にしない。資料固有の先頭・末尾の対照に加え、同じPII述語の否定規則も観測し、ファイル版・規則版・対象範囲・期間を照合する。対照だけなら保留にする。
2. 認証主体、マイドライブの所有者、共有ドライブの所属、規則の適用範囲をアップロード前に確認する。
3. 分類ごとに値を複数用意し、同じ値の文脈違いと独立した値の数を分ける。
4. 無効な検査数字、紛らわしい番号、分類名のない値等を加え、容易な陰性だけで適合率を評価しない。
5. 是正を「動作×事前共有状態×操作者×契機」の状態遷移として定義し、別の外部利用者による実アクセスを測る。

## 検知試験の改訂契約

### 正解と標本の単位

現行生成器では`value_id`と`family_id`が値の系列、`source_id`が表記・文脈の派生、`case_id`が配置ファイルを識別する。7分類で各6値の42値を開発用・評価用に分け、738資料へ展開する。`source_id`が異なることだけで独立した人物や元文書と認定しない。形式変換、同じ値の反復、複製配置を独立標本数へ加算しない。開発用と評価用の値を分離し、評価後に閾値を選び直す場合は、その評価集合を最終成績に再利用しない。

正解は少なくとも「情報の表現があるか」「検査数字等を満たす番号か」「今回の方針で保護すべきか」を区別する。無効な検査数字を持つ番号も、番号欄の表現としては陽性になり得る。型の表現を正しく拾った結果を、有効番号としての誤検出と無条件に同一視しない。発行済み・未割当・実在性は検査数字からは証明できない。

値だけの陽性、見出し付き、見出しなしの文章を基本集合へ入れる。全角、途中改行、ゼロ幅文字等は回避表現集合として別集計する。基本の再現率を回避表現込みの合算値だけで置き換えない。

### 検査対照と未検知の条件

先頭・末尾の文字列は資料ごとに異なり、PIIを含まず、正解表以外の台帳と対応付ける。HTMLの場合は可視本文の先頭・末尾へ配置する。既定は先頭・末尾それぞれの一意文字列を収めた2つの独自語句一覧検知器と監査規則にする。これは公開された語句一覧の作成例を使えるためで、正規表現検知器の内部JSONを未確認のまま推測して作成することを避ける。[S6][S7] 対照規則の一致だけをPII規則の成功には数えない。

対照規則の記録は「別の規則が当該ファイルを評価した」という証拠である。同じ内部走査ですべての本文・全PII規則が完全に検査されたことまでは証明しない。先頭・末尾の対照だけが揃った `conditional_not_detected` は主指標の陰性へ昇格させず、保留に残す。同じ述語の否定条件を持つ監査専用規則の一致記録も用意し、対象PII規則と対になる定義・版・適用範囲、ファイルの版、観測窓、内容指紋、前後対照を機械照合して初めて、条件付きの `not_detected` とする。先頭だけの一致、別版、別所有者、対象外の規則、規則変更前の記録は使わない。否定規則を足しても内部走査版の直接証明ではないという限界を指標へ併記する。

観測は資料×全規則×閾値の行列とする。分類違いへの反応も残す。監査原票と、原票から正規化した観測を分離し、同じ資料・規則の重複イベントを標本数へ加えない。人が書いた `evidence` だけで未検知を確定しない。

確信度・最小一致数・最小一意一致数は規則の設定組として事前固定する。現行計画は`UNLIKELY`・`POSSIBLE`・`LIKELY`の3閾値で、一致数・一意一致数はともに1である。同じ資料に監査専用規則を並走させ、閾値ごとに再現率・適合率・未判定率を出す。数値を見た後で最良の一点だけを選んで報告しない。

期待する監査動作の構造、分類ラベルのID・選択肢値、本文から除去する値は`plan-remediation --config`で事前固定する。観測に合わせて期待値を後付けしない。是正の観測は計画の指紋と、保存した原票・範囲・規則・前後状態・外部操作の参照指紋を持つ。合成書式は[test_remediation.py](../../scripts/workspace_dlp_benchmark/test_remediation.py)、監査対応表は[test_support.py](../../scripts/workspace_dlp_benchmark/test_support.py)を参照する。合成例はGoogle実応答の証拠ではなく、自由文の`evidence`だけで成功を作る書式でもない。

所有者と外部閲覧者は別認証にする。外部利用者はまず対象ファイルの内容を読めることを確認し、同じ認証で対象外の対照ファイルを読めることも保つ。403・404・認証失効・API未許可は、そのままDLP遮断成功にしない。所有者側の権限一覧、対象の現在版、規則の実行記録、外部側の読取結果を組にする。外部グループの所属や共有ドライブの継承を、直接権限の一覧だけで代用しない。

解除では元の動作完了記録と事前拒否を保持し、本文修復、規則無効化、規則削除の証拠を区別する。本文修復は旧版・現版の保存本文と事前固定値を照合し、無効化はACTIVEからINACTIVEへの更新、削除は完全な規則一覧からの消失を確認する。任意の画像・Officeを自動抽出してPII全体の不存在を保証する実装ではない。規則の動作原票で更新版が欠ける場合は、前後の同一設定による条件付き結合を`policy_readback_bracket`と記し、内部の評価版を直接観測した扱いにしない。

計画因子と実証拠は`case_context`で結ぶ。現行の契機接続は`source: "synthetic_fixture"`だけで、合成の計算検証を`evidence_domain: "synthetic"`として実測と別集計する。実際の作成・編集・規則変更を取得して照合する接続処理がない経路は`pending`で、合成の成功から製品の成功率を報告しない。この出所区分は署名による真正性保証ではない。

新規作成は対象自身の契機前状態を要求する現行処理と両立せず、専用接続が未実装のため実・合成とも`pending`である。新規共有で対象自体の可読を確認できない場合も保留にし、製品失敗としない。

是正の基本行は未実行も分母へ残す。合成の判定済み成功率は`by_evidence_domain.synthetic`で別掲し、実収集の接続が未実装の間は`full_plan_success_rate`と`product_measured_success_rate`を`null`にする。自作取消の実行証拠接続は`unsupported`、期待結果が未固定の迂回・競合等は`pending`であり、一覧へ含まれることと検証完了は別である。

## 時刻・是正指標・失敗の扱い

各試行で、事前状態確認、入力の作成／編集、規則変更要求・読み戻し、対照一致、対象検知、動作完了、監査取得、外部アクセス試行をUTC（協定世界時）の時刻で別に保存する。クラウド記録のイベント時刻と、手元でその記録を初めて取得した時刻を混ぜない。試験機の時計と観測間隔も記録する。作成収集器は要求開始～応答完了とGoogle側の作成・更新時刻を別々に保存し、時計の一致を未確認のまま単一の正確な契機時刻へ変換しない。編集・規則変更を含む実遅延の測定は未実施である。

| 指標 | 定義と必要な分母 |
|---|---|
| 是正成功率 | 事前に定めた最終状態と実操作を満たした陽性試行数／対象の陽性試行数。未検査・未完了・認証失敗を別掲し、判定済み部分の成功率だけを全件へ拡大しない |
| 是正までの時間 | 入力がPIIを含む版へ確定した時刻から、最初に是正を確認した時刻まで。既存ファイルへの規則変更は変更時刻起点も別に出す |
| 外部への露出時間 | 編集時刻からアクセス拒否まで。定期観測では最後の読取成功～最初の拒否の区間として出し、正確な発効時刻と偽らない。締切時に読める試行は継続中として残す |
| 残存した外部権限 | 是正前後に残る外部の直接・グループ・リンク経路を種類別に数える。権限行の残存数と、実アクセス可能な経路数を分ける |
| 過剰遮断率 | 不要な遮断・取得制限が起きた陰性試行数／判定対象の陰性試行数。通知・ラベルの過剰適用は別指標 |
| 解除成功率・時間 | 解除の前提を満たした試行のうち、期待する制限・ラベルの解除と実アクセスを確認した割合と所要時間。手動変更ラベルの例外を別集計 |
| 利用者への影響 | 警告の表示率、無視した続行率、固定管理者宛と作成者宛の通知到達、誤検知申告から解除までの時間を別々に測る |

実装の`exposure_interval`は可読から拒否、`release_interval`は拒否から可読の別の区間で、再露出・再拒否と観測期限での打切りを記録する。無動作の陰性を過剰適用なしと採点するには、同顧客・資料版・述語・範囲の条件付き`not_detected`を監査原票から再導出する必要がある。下表の利用者通知等の指標は設計上の測定対象であり、すべての収集器を実装済みという意味ではない。

露出時間には定期確認の間隔による幅がある。監査イベントの `action_complete` だけで外部アクセス不能を断定せず、外部の一回の失敗だけでも因果を断定しない。競合や規則対象外の一般共有設定が原因なら別に分類する。

## 既存設計と代替経路の位置付け

自作DLPサービスの本番初期版で、削除・隔離・共有変更を自動化しないという[既存のサービス設計](adaptive_dlp_service_design_20261111.md)・[API制御設計](adaptive_dlp_api_control_design_20261112.md)は維持する。一方、Workspace製品の是正動作を試験しない理由にはしない。このレビュー対応は専用資料と限定範囲の是正試験を追加するものであり、本番の自動是正を有効にしたことを意味しない。

Gmail・ChatやCloudの検査APIは予備比較として独立した結果表へ置く。ラベル経由の二段構成と自作権限削除も、同じ固定資料・事前共有状態・外部読取経路で比較する。ブラウザーからの貼付け・持出しをすべてDrive DLPだけの保証範囲にせず、Chromeの規則やアクセス制御を扱う試験には別の設定と指標を用意する。[S7]

## 運用Q&A

### 機微情報を指定したフォルダー配下だけに置けるか

Drive DLPの公開仕様では、親フォルダーIDや祖先階層を条件にして、保存先や移動先を強制する機能は確認できない。マイドライブでは所有者の、共有ドライブではそのドライブの規則が適用される。監査で指定先の外にあるファイルを見つけたい場合は、指定先の外にもDLPの対象範囲を広げる。 [Drive DLPの条件と動作](https://knowledge.workspace.google.com/admin/security/about-dlp-for-drive)

| 目的 | 構成 | 実装する範囲 |
|---|---|---|
| 日次の配置監査 | DLPで機微ラベルを付け、Drive棚卸しをBigQueryへ出力する。ファイルIDと親IDを使い、SQLで許可フォルダーの子孫をたどる | 標準出力の設定と定期SQLで構成できる。棚卸しは日次または週次で、対応契約と課金設定が必要 |
| 移動を早く把握 | Drive APIで親を取得し、`changes.list`で変更を追跡する。上位フォルダーが移動したときは配下も再判定する | 台帳の初期作成、差分取得、定期照合が必要 |
| 保存前に強制 | 管理された受付で書き込み前に検査し、機微情報を許可した共有ドライブやフォルダーにのみ書き込む | 受付処理と権限管理が必要。直接書き込み、移動、コピーは管理できる経路で制限する |

日次レポートではファイルごとに「許可配下」「範囲外」「確認不能」を記録し、範囲外の新規・解消・残件を集計する。棚卸しで親が欠落する場合や棚卸しが古い場合は「確認不能」とする。規則監査ログは検知履歴の補助に使う。保存後の監視には検知遅延、未検査、見逃しがあり、監視結果から組織全体の配置を常時保証することはできない。 [Drive棚卸しの出力設定](https://knowledge.workspace.google.com/admin/reports/export-your-organizations-drive-inventory)・[棚卸しの項目](https://knowledge.workspace.google.com/admin/reports/schema-and-example-queries-for-drive-inventory-exports-in-bigquery)・[Driveの変更追跡](https://developers.google.com/workspace/drive/api/guides/about-changes)

### ファイル作成からDLP検知までどのくらいかかるか

Googleの公開仕様には、個々の新規作成から検知までの期限は記載されていない。規則追加・変更後の既存ファイルの再検査は、件数等によって数時間、1日、またはそれ以上かかる場合がある。規則ログが管理画面に現れるまでの目安はほぼリアルタイムで、標準出力でBigQueryに活動ログが届く目安は通常10分以内である。後者の2つは、検知イベントが発生した後の時間である。 [Drive DLPの検査](https://knowledge.workspace.google.com/admin/security/about-dlp-for-drive)・[監査ログの反映時間](https://knowledge.workspace.google.com/admin/reports/data-retention-and-lag-times)・[BigQueryへの標準出力](https://knowledge.workspace.google.com/admin/reports/set-up-service-log-exports-to-bigquery)

実測では、ファイルの作成時刻かアップロード要求の開始時刻を起点として明示し、初回一致イベントの発生時刻までを測る。ログの取得時刻も別に記録する。検査の開始時刻が公開されない場合、初回一致までの時間を検査開始までの時間として扱わない。観測できた資料の中央値、95パーセンタイル、最大値に加え、対象数と観測期間内に一致を確認できなかった件数を示す。

### 修正依頼をgwsで送る場合、送信元は誰か

Drive DLPの検知ログを起点に、ファイルIDで対象を照合し、作成者や担当者を確定して修正依頼を送る構成を取れる。依頼メールはDLPの標準アラートとは別の処理で、Google Workspace CLIの `gws gmail users messages send` から Gmail API の `users.messages.send` を呼び出す。Gmail APIの送信権限には OAuth の `gmail.send` を使える。 [Google Workspace CLI](https://github.com/googleworkspace/cli)・[Gmail APIの送信仕様](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send)

通常の送信元は、送信認証に使うGmailメールボックスのアドレス。通知専用メールボックスを使う構成なら、そのアドレスを `From` にし、確認した担当者を `To` に入れる。別名を `From` に指定する場合は、そのメールボックスに登録され、利用可能な送信用エイリアスを使う。宛先を確定できないファイルは確認待ちとし、依頼本文には検知した値を載せず、ファイル参照と依頼事項を記載する。 [Gmailの送信元エイリアス仕様](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.sendAs)

### 業務番号の検知結果に設定条件を併記する

旧プレゼンの社員番号・契約番号の各100/100は、合成資料の旧試験における再現率。元の検知器定義と評価資料を照合できていないため、一般的な社員番号・契約番号の性能評価から外す。旧標準検知器のしきい値も設定の原票を確認できるまでは「未確認」とする。既存試験計画の値を旧試験の実行値には転記しない。

| 対象 | 再検証で固定する設定 |
|---|---|
| 標準検知器 | 検知器名と本文への適用を固定。既存計画の `UNLIKELY`・`POSSIBLE`・`LIKELY` を比較し、最小一致数1・最小一意一致数1を各規則で維持。同じ評価資料でしきい値ごとの件数と指標を報告 |
| 独自正規表現 | 可能性のしきい値は対象外。式、本文への適用、最小一致回数1を固定。過去の式を取得できた場合は同じ式で再検証し、改訂式の成績も別に記録 |
| 独自語句一覧 | 可能性のしきい値は対象外。語句一覧の版、最小一致数1・最小一意一致数1を固定 |
| 標準＋独自 | 条件の論理式を保存し、標準側だけのしきい値を明記。単独構成と同じ資料、観測窓、監査のみの動作で比較 |

本測定では有効な規則の設定を読み戻し、検知器、しきい値、最小一致数、正解表の版、検査対象と観測窓を結果と対応付ける。未観測を陰性にせず、ファイル単位と項目別のTP・TN・FP・FN、未判定数、適合率・再現率・正解率・F1を集計する。Googleは標準検知の可能性判定に正規表現と追加情報を用いると説明している。独自正規表現、語句一覧、標準検知器では指定できる設定が異なる。[Drive DLPのよくある質問](https://knowledge.workspace.google.com/admin/security/dlp-for-drive-faq)・[Cloud Identity Policy APIの条件仕様](https://docs.cloud.google.com/identity/docs/concepts/supported-policy-api-settings)

同じ番号が社員・契約・発注・請求のどれにも使われる条件を追加した。再生成手順とローカルでの比較結果は[試験手順](../../scripts/workspace_dlp_benchmark/README.md#業務番号の対照試験)に記載。

旧概要で再現率100%と表示された番号・連絡先については、同じ値を見出し付き、値のみ、別用途、入力例で比較する。検査数字の誤りと別表記も対照に含める。氏名・パスワード・病歴・診療・健診・人種や民族などを加え、本文の形式に合うことと、文書内で保護対象として使われていることを別々に採点する。再生成方法と、21項目・架空資料8,768件の再生成と手元での評価を[対照試験手順](../../scripts/workspace_dlp_benchmark/README.md#旧試験で再現率100と表示された項目の対照試験)に記載。

### 電話番号の検知は見出しでどう変わったか

Drive DLPの標準電話番号検知器を本文に適用した。可能性のしきい値は `POSSIBLE`、最小一致数と最小一意一致数はともに1、規則の動作は監査のみ。正解表には、合成した値の電話番号としての用途と、形式の妥当性を別々に記録した。

| 架空資料の本文 | 正解 | 検知／判定済み | 未判定 |
|---|---|---:|---:|
| `電話番号：` に続けて番号を記載 | 陽性 | 32／32 | 0 |
| 同じ番号を見出しや区切りのない連続した数字で記載 | 陽性 | 0／32 | 0 |
| `電話番号：` に続けて `080` で始まる桁不足の10桁を記載 | 陰性 | 61／61 | 3 |
| 同じ系列の10桁を `社員番号：` に続けて記載 | 電話番号としては陰性 | 0／63 | 1 |

見出し付きと数字だけを対にした32件では、見出しの有無で結果が分かれた。桁不足の対照では、電話番号の見出し付きで判定済みの61件がすべて誤検知だった。数字だけの未検知は、この資料と設定における結果であり、区切り付きの番号や別のしきい値に一般化できない。[Nodetto本編の31・32ページ](presentations/drive-dlp-sensitive-data-detection.jsonl)

| 同じ値を研修用の入力例として記載 | 0 | 32 | 0 | 32 | 0 | 0 | 0 |

**適合率100.00%（24／24）、再現率18.75%（24／128）、正解率53.57%（120／224）、F1値31.58%。** この資料の陰性96件に誤検知はなかった。陽性128件のうち104件を見逃した。

検知した24件はすべて、見出しと値をタブで区切り、値を引用符で囲んだ32件に含まれる。この32件では、英数字・記号の2系列と日本語を含む1系列が各8／8件、空白を含む系列が0／8件だった。区切りと引用符を一緒に変更しており、系列間で文字種やその他の特徴も異なるため、どの特徴が検知を左右したかはこの試験からは分からない。[Nodetto本編の30・36ページ](presentations/drive-dlp-sensitive-data-detection.jsonl)
