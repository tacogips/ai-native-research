# AWSの機微情報検知サービスとAPI連携の比較

調査日：2026年11月12日。[製品横断の117項目比較](sensitive_information_detection_item_matrix_20261112.md)を、AWSの5サービスについて同じ項目IDで拡張した。DLPは機密情報の漏えい防止、PIIは個人を識別する情報、PHIは米国の医療分野で用いられる保護対象の健康情報を指す。本稿のPHIという製品分類を、日本法の要配慮個人情報と同義には扱わない。

**日本語本文をAPIで検査する候補はAmazon Bedrock Guardrails、日本の識別番号を表形式データから探す候補はAWS Glue、S3内の保存データの探索はAmazon Macieである。Amazon Comprehendの専用PII検知は英語・スペイン語、Amazon Comprehend Medicalは英語が対象であり、日本語検知の標準部品として数えない。** [B1–B3,C1–C3,M1–M2,G1,A1–A3]

公開仕様の比較で、AWS環境への接続や精度試験は行っていない。APIはソフトウェア同士の呼出し口であり、公開されたAPIの存在と、対象組織での権限・契約・実行地域・性能の確認は別である。

## 用途と連携方法

| サービス | 主な対象と役割 | 連携の入口 | 自作する部分と限界 |
|---|---|---|---|
| Amazon Bedrock Guardrails | アプリケーションの本文中の個人情報・一部認証情報を検査、遮断・置換 | ApplyGuardrail。生成モデルを呼ばず単独で利用可能 | 本文取得、分割、版管理、位置対応、判定台帳、通知。DriveやS3全体を自動巡回しない [B1,B3,B4] |
| AWS Glue Sensitive Data Detection | 行・列を持つデータの検知、伏字化、削除、照合値への変換 | EntityDetector.detect／classifyColumns、独自種類の作成、StartJobRun | データの読取りと実行処理を準備。文書全文を渡す軽量な同期検査APIとは異なる [G1–G5] |
| Amazon Macie | S3内の機密データ探索と保存領域の危険な設定の検出 | 検査ジョブ、ListFindings／GetFindings等 | S3外のデータ搬入、対象・完了状態の照合、許可管理。標準の自動探索は標本検査 [A1–A5] |
| Amazon Comprehend PII | 英語・スペイン語の本文から識別情報の種類・位置・信頼度を抽出 | DetectPiiEntities。非同期の検査・伏字化も別途用意 | 原文抽出、実行制御、判定・通知。専用PII APIに独自の形式規則を渡す仕様とはしない [C1,C2] |
| Amazon Comprehend Medical | 英語の医療文書から識別情報や病名・薬剤等を抽出 | DetectPHI、DetectEntitiesV2 | 医療項目と人物の関係の確認、位置保存、伏字化等。日本語は対象外 [M1–M4] |

連携のしやすさは用途に依存する。本文を渡してすぐ評価したい場合はGuardrails、表の大量処理ならGlue、既存S3の探索ならMacieが対応する入口を持つ。これは公開された入出力からの設計判断であり、導入工数や速さの実測順位ではない。

## 日本語と日本固有の項目

| 項目 | Bedrock Guardrails | AWS Glue | Macie | Comprehend PII | Comprehend Medical |
|---|---|---|---|---|---|
| 日本語の意味を使う専用検知 | 機密情報検査は日本語を「調整・試験済み」と明示 | 人名などの日本語の個別保証は未確認 | 氏名はラテン文字。住所・電話は対応国に制約 | 専用PIIは英語・スペイン語 | 英語のみ |
| 日本語氏名・住所 | NAME／ADDRESSと日本語対応を確認。精度は要試験 | 汎用PERSON_NAMEを日本語保証としない。住所全体も未確認 | 日本語向け標準検知として数えない | 日本語の専用PII処理として数えない | 日本語として数えない |
| 日本の電話番号 | 汎用PHONE。国内表記等の対応は試験 | PHONE_NUMBERは米国・カナダと明記。日本は独自規則候補 | 日本は独自規則候補 | 日本専用の種類は未確認 | 日本専用の種類は未確認 |
| マイナンバー | 日本専用の標準種類は未確認。独自規則候補 | JAPAN_MY_NUMBER | 独自規則候補 | 日本専用は未確認 | 日本専用は未確認 |
| 日本の口座・免許・旅券 | 国固有の標準種類は未確認。汎用種類と区別 | JAPAN_BANK_ACCOUNT、JAPAN_DRIVING_LICENSE、JAPAN_PASSPORT_NUMBER | 日本専用の標準一覧にはない | 日本専用は未確認 | 日本専用は未確認 |

根拠は[B1,B2,G1,A1,C1,C3,M1,M2]。「日本語が入力できる」「日本語文脈の検査を明示」「日本固有の番号検知器がある」「日本語で実測精度が高い」は別々である。

ComprehendのAPI定義には注意が必要である。DetectPiiEntitiesのLanguageCodeの列挙値にはja等も出る一方、同じAPIの説明文、PIIの利用案内、機能別言語表はいずれも専用PIIを英語・スペイン語とする。**共通の列挙値だけから日本語PII対応とは判断しない。** 一般的な固有表現抽出の対応言語を専用PIIへ転記しない。[C1–C3]

## 117項目の検知比較

製品横断表と同じIDを使う。表の「未」は非対応の断定ではない。「規」は公開された独自の形式規則を使う設計案であり、実装・評価済みではない。文脈依存の項目では語句候補を拾うに留まり、本人の属性や機密性を確定しない。

| 記号 | 意味 |
|---|---|
| 標／標限定 | 標準検知を確認／対象国・近接種別・書式等に限定 |
| 標英西／標限定英西 | Comprehend専用PIIの対象言語である英語・スペイン語での標準検知／限定した候補 |
| 標英／標限定英 | Comprehend Medicalの英語医療文書での標準検知／広い種類や近接項目による候補 |
| 非日 | 日本語本文は当該専用機能の対象言語外 |
| 規 | 独自の正規表現・周辺語句などで候補検知を作る案 |
| 未 | 当該機能の標準対応を公開仕様で確認できない |
| 非 | 当該検知方式の入力・処理対象外。別の抽出処理は別評価 |
| 外 | 外部の事実や専用の照合が必要 |
| 不可 | 復号できない等、条件上本文へアクセスできない |
| 拡 | 自作の追加処理が必要 |

BG＝Bedrock Guardrailsの機密情報検査、AG＝AWS Glue Sensitive Data Detection、AM＝Macie、CP＝Comprehend専用PII、CM＝Comprehend Medical。BG列は拒否する話題の判定や一般の生成モデルによる独自分類を含めない。CM列はDetectPHIとDetectEntitiesV2を合わせた機能評価であり、DetectPHI単独で病名・薬剤を抽出するという意味ではない。

## 人の判定と通知を追加する場合

### Bedrock Guardrailsで記録だけを取得する

機密情報の設定には、遮断するBLOCK、種類名等へ置き換えるANONYMIZE、内容を変更せず検知情報を返すNONEがある。独自の正規表現でもNONEを設定できる。したがって「まず検知記録を保存し、人が判定し、場所や種類の許可に応じて自社側で通知する」入口にできる。[B1,B5]

ただし、NONEは自動的に永続台帳を作る機能ではない。ApplyGuardrailの結果を自社側で保存し、呼出しに使った原文の版・検査対象範囲・設定版・取得時刻を記録する。最上位のactionがNONEでも、検知なしとは限らない。配下のsensitiveInformationPolicyにあるpiiEntities／regexesとdetected等を確認する。[B4]

Comprehendの検知APIは開始・終了位置とScoreを返すが、確認したApplyGuardrailのPII応答定義は主にtype、match、action、detectedであり、同等の開始・終了位置やPII別のScoreは確認できない。同じ値が繰り返される本文で、matchを文字列検索した位置を検出器の正確な位置として確定しない。全箇所の監査に使うには、位置を補う設計か、別の箇所抽出器との併用が必要になる。[B4,C2]

伏字化を使っても、応答中のmatch等には原文値が含まれ得る。表示用の伏字本文と、証拠として返る値を分けて保持・閲覧権限を設計する。[B1]

### 自動検査の対象を取り違えない

Guardrailsの機密情報検査は文字本文を対象とする。通常のモデル呼出しにGuardrailsを付けただけでは、ツール呼出しの引数、ツールの戻り値、ツール定義の説明・入力形式の中身は検査されないと明記されている。対象に含めたい場合は、アプリが検査対象の文字列を取り出してApplyGuardrailへ渡す等の別経路を作る。画像の内容も、画像用の別の保護機能があることからPII検査まで対応と推測しない。[B1,B3]

これは独立APIの利点と責任を表す。Driveの内容、社内画面の入力、検索で得た文書なども、認可された経路で本文を取得すれば検査へ渡す構成を作れるが、取得・漏れの管理・文字数に応じた分割は自作である。

### GlueとMacieの全件検査を区別する

Glueでは各セルを検査する方法と、行の標本から機微情報を含む列を推定する方法を選べる。classifyColumnsの標本割合・判定割合を使った結果を、全行の検査済みの証拠にしない。detectによる箇所・行単位の結果と、列に付けた分類を別に管理する。[G2,G3]

Macieの自動探索は代表的な保存物を選んで検査する。特定の対象集合を詳しく検査したい場合は、対象を定めた検査ジョブを使い、権限不足、形式非対応、読取り失敗、容量や抽出制約を別記録にする。ListFindingsは主に識別子の一覧であり、詳細にはGetFindings等を使う。警告一覧が空でも、全S3内の本文に機微情報がないとは判断しない。[A3–A5]

## 企業秘密を意味で分類する追加案

個人情報の標準検知器だけでは、未発表の研究、価格交渉、設計上の工夫などを一般的に確定できない。AWS側の追加候補は次のとおり。

| 追加方式 | できること | この比較との境界 |
|---|---|---|
| Guardrailsの拒否する話題 | 定義した話題に本文が当たるかを判定。日本語はStandard側の対応表を確認 | 独自の機密文書分類の候補にはなるが、特定人の信条や法的な企業秘密を確定する専用検知器ではない [B2,B6] |
| Comprehendの独自文書分類 | 用意した分類例で学習し、文書の種類を判定 | 専用PIIとは別機能。現行の言語表では日本語は独自分類の対象に含まれない [C3,C5] |
| Comprehendの独自箇所抽出 | 学習例から独自の項目や業務固有語を抽出 | 専用PIIへの規則追加ではなく別モデル。現行の独自認識の対応言語に日本語は含まれない [C3,C6] |
| Bedrockで使う生成モデルによる独自分類 | 日本語の定義・例・反例を使った候補判定を実装する設計案 | 個々のモデル選定、出力検証、評価資料、費用、原文の保護を自分で設計。Guardrailsの標準検知として数えない |

機密文書の種類、秘密とする理由、場所や共有状態による許可を分離する。生成モデルが「機密らしい」と答えたことだけで、事実や業務許可の台帳を更新しない。[既存の適応型運用設計](adaptive_dlp_api_control_design_20261112.md)

| やりたいこと | Google側の候補 | AWS側の候補 | 判断 |

Google側の根拠と個別の標準種類は[製品横断表](sensitive_information_detection_item_matrix_20261112.md)を参照。日本語の自由文を中心に作るなら、AWS側の最初の比較候補はGuardrailsであり、日本の番号の不足をGlue・独自規則等で補う構成を評価する。S3中心ならMacieを既存資産の探索に使う。これらは用途に基づく構成案で、精度・費用の優劣を実証した結論ではない。

| 長文の分割 | 分割境界で名称・番号や前後の文脈を失わないこと。原文への位置対応 |
| 医療 | 英語の本人・家族・否定・過去の記述を区別。日本語を英語対応の実績に混ぜないこと |
| 表と保存物の探索 | 標本・全件・失敗・非対応を分離し、空の結果を全体の陰性としないこと |

合成資料で確認し、原文を取得できる実運用では権限と保持先を別途管理する。この公開リポジトリには実データや認証済み環境の結果を保存しない。
