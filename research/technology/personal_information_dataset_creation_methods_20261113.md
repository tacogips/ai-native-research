# 個人情報22項目を複数形式の資料で評価するためのデータセットと作成方法

確認日：2026年11月13日。日本語・日本の書式を優先する。未認証で読める公式資料・提供元の説明・公開実装を根拠とする。

**列挙された全項目について、既存資料の利用または追加作成による評価資料の用意が可能。履歴書、会員情報、証明書画像、支払資料、行動履歴、医療・相談文書を組み合わせればよく、一つの資料や一人の人物に全項目を集める必要はない。** ただし、既存の日本語資料だけで、全項目に検知位置・対象人物・日本法上の分類の正解が揃うとは確認できなかった。履歴・家族関係・要配慮情報の一部は、追加作成または注釈が必要になる。

本稿は入手候補と作成手順の調査であり、22項目のデータ本体の生成・一括取得・注釈・精度測定を実施した報告ではない。「既存」は公開説明で内容を確認した候補、「素材」は必要な属性等を持つが検知の正解集ではないもの、「作成案」は本調査による設計案を指す。

具体的な作成対象・陰性ファイル・ディレクトリ構成・持ち出し操作の期待値は、[PII検知・DLPのテストデータセット作成計画](pii_dlp_test_dataset_creation_plan_20261113.md)へ整理した。予約・購買等は、個人情報を含む文書の種類として組み込み、各業務の大規模履歴集を独立に作ることは必須にしない。

## 日本語の既存資料を選ぶ際の重要点

**Sumi**は日本語の氏名・連絡先・住所・生年月日・銀行口座・カード・マイナンバー形式・会員番号等の検知位置を持つ。陰性例と未知書式もあり、A・D群の出発点にできる。全体CC BY-SA 4.0、合成部分CC0等、元文章ごとの条件を保持する。カードとマイナンバー形式の検査数字が不正である点を採点条件へ反映する。[S02]

**Nemotron-PII-Japan**は日本語100,000文書、8分野・43文書種類。診断書、給与通知、入学申込、購入者の問い合わせ等の文脈を持つ。CC BY 4.0。本文の全対象を網羅する注釈とは限らず、所得・病歴等の文脈が本文にあることと、その部分に目的の正解があることを分ける。文書の種類ごとに必要な追加注釈を決める。[S03]

**Nemotron-Personas-Finance-Japan**は日本語の架空人物属性の素材で、CC BY 4.0。性別、教育水準、職業、所得区分、家族類型、続柄、世帯人数等を含む。完成した履歴書、家族全員の名簿、購買履歴、検知の位置正解は提供範囲と同一ではない。B群を作る際の設定として使い、足りない期間・金額・関係を追加する。既存人物資料と似た文章になるため、学習と評価の重複を管理する。[S05]

**SynthResume**は2,994件の合成履歴書を説明し、PDFと対応正解のディレクトリーを公開している。ひな形、生成モデルによる内容作成、別のモデルによる仮注釈、人手修正という作成例。リポジトリはApache 2.0表示だが、ひな形・画像等の由来も採用時に確認する。日本語版を公開しているとは確認していないため、日本語履歴書の完成品とは数えない。[S10]

日本の免許証は前稿の公開候補、日本の合成旅券は公開96行・CC BY-NC-ND 4.0の標本がある。前者はログイン後の取得と品質検査が未完了、後者は非商用・改変物の共有制限がある。独自作成に切り替える場合も、既存の制限付き画像を自由なひな形として流用できるとはしない。[S06・S07]

日本語の履歴書・職務経歴書を作る際は、厚生労働省の履歴書様式例とマイジョブ・カードの空欄様式が具体的な素材になる。PDF・Excelの入手先があり、架空の経歴を埋めた後で文章・画像へ変換する案がある。空欄様式は入力済みデータセットではなく、正解も別途作る。性別は任意記載で、家族構成や信条等の試験は履歴書への必須項目として追加せず、別の文書群で扱う。ひな形の加工・再配布条件は各サイトの条件も確認する。[S23・S24]

## 要配慮個人情報は医療以外も分けて作る

日本法上の要配慮個人情報は、個人情報であることを前提にした分類。完全に架空で実在人物に結び付かない資料については、ここでは「要配慮個人情報に相当する内容の検知試験」と呼ぶ。学歴はそれだけでは通則編の「社会的身分」ではなく、宗教書の購買等の推知情報だけでも直ちに要配慮個人情報にはならない。こうした境界も試験に含める。[S17]

| 通則編の対象 | 追加作成する文書・正解の例（設計案） |
|---|---|
| 人種 | 架空の本人の出自を明示した申告文と、国籍だけを記載した別の例 |
| 信条 | 本人の信仰・思想の記述と、書籍名や施設名だけの記述 |
| 社会的身分 | 通則編の定義に沿う架空の記述を法的観点で確認して作る。単なる役職・学歴を代用しない |
| 病歴 | 診断書・受診記録。病名の一般説明、否定、家族歴を別に付記 |
| 犯罪の経歴 | 有罪判決が確定した架空の本人についての記録。疑惑・逮捕とは分ける |
| 犯罪被害の事実 | 架空の被害相談記録。一般の事故相談と分ける |
| 心身の機能の障害 | 架空の本人の障害に関する記録。病名との重複を許しつつ分類を管理 |
| 健康診断等の結果 | 検査項目・結果・本人・検査日が対応する結果表 |
| 保健指導・診療・調剤の事実 | 架空の受診・調剤記録。自己判断の服薬等と区別 |
| 刑事事件に関する手続 | 被疑者・被告人として手続を受けた架空例。犯罪歴と分ける |
| 少年の保護事件に関する手続 | 架空の手続記録。本人の年齢・手続・時点を整合させる |

医療の既存素材にはMeddiesの日本語合成文書があるが、既存注釈は主に氏名・日付等で、病歴そのものの完全な正解ではない。CC BY-NC 4.0。Syntheaは架空の患者の病歴・検査・投薬等を構造化して生成するが、標準設定は米国の人口等に基づき、日本語化や日本法の正解付与が別途必要。コードはApache 2.0。[S15・S16]

TABは実判決文に機微属性等の注釈を持つ英語資料。日本法の11項目との対応や、実際に収録される例の範囲は確認が必要。医療以外の日本語の全項目に正解が揃う資料としては扱わず、追加注釈の方法を考える参考にする。[S20]

## 文章・画像・履歴を作成する具体的な方法

### 値を決めてから文章へ埋める

#### 文書作成の元にする架空人物資料

日本語の第一候補は[Nemotron-Personas-Finance-Japan](https://huggingface.co/datasets/nvidia/Nemotron-Personas-Finance-Japan)。公開画面の配布は100万行で、所得区分・職業・教育・家族類型等の列と、暮らしや経済的背景の文章を持つ。これを一人分の設定の元とし、必要な文書ごとに属性を選んで使う。[Nemotron-Personas-Japan](https://huggingface.co/datasets/nvidia/Nemotron-Personas-Japan)も100万行の日本語資料で、年齢・性別・婚姻・職業・教育水準・都道府県等を持つ。いずれもCC BY 4.0。複数種類の人物説明の数を、独立人物数として行数へ足さない。[S04・S05]

Personas-Japanの提供元は、構造化した姓名や合成住所等を公開版から除外すると説明している。人物の説明文に名前が現れる場合もあるが、完成した顧客名簿とは扱わない。氏名・メール・電話・番地・生年月日・会員ID・各種番号は、採用する列と不足を確認して別途付与する。Finance-Japanの所得区分から具体的な金額を設定する場合や、職業から経歴の日付を設定する場合は、既存値の抽出と新規生成を区別して記録する。

利用案は「元の人物IDと採用版を保持→必要な属性を抽出→不足する架空の値を付与→文書に応じて文章化→位置等の正解を記録」。医療文書を作る群では[Synthea](https://github.com/synthetichealth/synthea)の架空患者記録も元資料にできるが、日本語・日本の制度への変換は別作業。同じ人物の設定を展開した派生文書は、学習と最終評価へ分散させない。[S16]

一つの申込書や履歴書の中で整合性が必要な値だけを先にJSON等で用意する。氏名・連絡先はFaker等、性別・所得区分等は公開の架空人物資料または独自設定、番号は書式規則で生成する。メールにはIANAの例示用ドメインを使う。Faker日本語の住所例にも都道府県と市区町村の不整合があるため、自然な日本の住所を必要とするなら地理対応を検査する。[S01・S19]

文章化は二通りある。ひな形へ値を埋める方式は再現性が高く、挿入時に正解位置を計算できる。生成モデルを使う場合は値を直接自由生成させず、置換用の目印を含む文章を書かせ、確定済みの値を後で埋めて位置を記録する。Nemotron-PII-Japanは、属性・数値を先に決め、置換・整合性確認を行う公開事例。DataDesignerはこの種の生成処理を組む候補で、コードはApache 2.0。推論で生成モデルを使わない検出器でも、学習資料の作成には利用できる。[S03・S21]

職歴・学歴は日付の前後と年齢を、年収は年額・月額・賞与・対象期間を、家族構成は続柄と世帯所属を検査する。ランダムな値を独立に並べただけの資料を、自然な人物・経歴の資料と同一視しない。

### 履歴は「イベント」を時系列に作る

**今回の個人情報検知試験の陽性例は、履歴の内容と、本人を識別できる情報または容易に照合できる対応関係を組み合わせる。** 商品・予約枠の一覧や、誰にも結び付かない集計だけを、本人の購買・予約履歴と同じ陽性例にはしない。保護対象という設計上の判断、個人情報への法的該当性、要配慮個人情報への該当性は別の正解として管理する。[S17]

| 評価例 | 作成する資料 | 判定で確かめること |
|---|---|---|
| 同じ文書に本人の情報がある | 氏名・メール等を含む予約確認書、購入明細、応募通知 | 識別情報の箇所と、本人の行動を示す記述の範囲を両方記録 |
| 別表と照合すると本人が分かる | 会員ID付き履歴と、そのIDに対応する架空の会員名簿 | 対応表が利用できる条件で、本人との結び付きを検知。履歴だけの条件とも比較 |
| 本人を識別できないが個人の行動を記録する | 本人との対応を持たない操作単位ID・端末識別子付きの履歴 | 個人関連情報となり得る資料として別管理。「氏名がないから無条件に非機微」としない |
| 個人の行動に対応しない | 商品一覧、空き予約枠、個人に結び付かない件数集計 | 個人の購買・予約履歴という判定の陰性例。企業秘密等の別観点はこの正解に含めない |

法的な個人情報への該当性は、同じファイルに氏名があるかだけでは決まらない。他の情報との容易な照合で本人が分かる場合も含む。また、個人情報に該当しない閲覧・購買履歴でも、個人関連情報に該当する場合がある。購買内容が信条等を推知させるだけの場合と、本人の要配慮情報に該当する事実を記録する場合も区別する。ここでの架空の対応表は試験用の設定で、実在人物の対応を再現するものではない。[S17]

イベントとは、一件の検索、閲覧、注文、予約、応募等の操作記録。会員ID、操作単位のID、日時、対象、操作種類、状態を持たせる。例えば予約作成より前に取消が発生しないように、許される状態の変化を規則にする。購買・予約・閲覧・検索・応募の各群は、別人物・別ファイルでよい。

公開例ではYOOCHOOSEがクリックと購入の関係、MINDが人物に対応する過去クリック等、SDVの`fake_hotels`が宿泊客・ホテル等の複数表、RecSimが利用者と推薦対象の連続したやり取りを扱う。ただし、いずれも日本語の個人情報検知の完成した正解集ではない。[S11・S12・S13・S14]

日本語の検索・予約・応募履歴は、上記の構造を参考に、人工の操作と日本語の検索語・施設・求人等を作る方針が具体的。CSVやJSONだけでなく、同じ人工履歴から領収書、予約通知、検索履歴画面、応募状況一覧へ表示できる。利用者行動の現実の分布まで再現したとの主張は、別途検証が必要。

SDVは表の統計と関係を学んで新しい表を生成する選択肢。ただし通常は元データと表・列の説明が必要で、元データなしの生成機能はEnterpriseとして説明される。現在のSDVの条件はBSL 1.1で、第三者向けの合成データサービス等には制限がある。規則による人工履歴ならSDVの導入や実データの学習を必須にしない。[S12・S22]

MINDは研究用途の条件付き、YOOCHOOSEは現行の取得先・利用条件を採用前に確定する。RecSimはApache 2.0だが2026年4月に保管状態となり更新が停止している。新規実装へそのまま採用する推奨ではなく、模擬履歴の考え方の根拠として挙げる。[S11・S13・S14]

### 同じ内容を画像やPDFへ変換する

独自の履歴書、口座届出、健診表、予約一覧等をHTML/CSSやSVGで配置し、PDFまたはPNG/JPEGへ出力する。既に文字列と項目の位置を管理していれば、画像中の正解範囲も記録できる。文字認識の出力を正解の唯一の根拠にせず、描画時の値・位置を使う。日本語の改行、縦書き、異体字、表内の折返しは別確認が必要。

DocXPandは、ひな形・架空属性・顔等を組み合わせて身分証画像を作り、背景写真へ配置する公開実装。日本の証明書を標準提供するわけではないが、画像と注釈を同時に作る方法を参照できる。コードMITと付属資料CC BY-NC-SA 4.0は分ける。[S08]

画像に傾き・拡大縮小を加えたら正解座標にも同じ変換を適用する。ぼけ・反射・圧縮・部分的な隠れは、値が読めるかと、対象が存在するかを分けて正解に記録する。証明書の見本は「見本」と明示した評価素材として作成し、真贋判定の正解集を作ったとは扱わない。

## 正解形式と評価の組み立て

共通の巨大な資料へ統合する代わりに、元資料・版・利用条件を保持し、評価時に項目名と正解形式を対応付ける。

| 形式 | 保持する正解 | 評価で確認すること |
|---|---|---|
| 文章 | 分類、開始・終了位置、対象人物、値の出現ごとのID | 見逃し、誤警告、隠した文字範囲の不足 |
| 画像・PDF | ページ、分類、四角または多角形の範囲、文字列、対象人物 | 読み取り失敗と分類失敗、ページ全体の取り残し |
| CSV・JSON | 表・列・行またはJSONの位置、分類、行動の主体、対象、日時 | 単なる番号列と会員ID、列見出しと値の関係 |
| 経歴・家族・行動・要配慮情報 | 上記に加え、人物間関係、事実の種類、時点、否定・仮定・家族の事実等 | 本人の事実か、一般解説か、別人物の事実か |

文章の文字位置は先頭0・終端を含まない範囲等の規約を明示する。全半角変換やUnicode正規化、再描画、翻訳、文章の言い換えをしたら正解も更新する。生成モデルへ「正解位置も出して」と頼んだ結果だけで確定せず、本文との一致と人手確認を行う。

学習・調整・最終評価は、各資料の元人物・元券面・元文書・生成ひな形単位で分離する。22項目それぞれに陽性と陰性を用意し、形式・資料群ごとに見逃しと誤警告を測る。要配慮情報は上の11項目の不足も別に確認する。未知のひな形や実際の撮影条件を含む評価を残し、合成資料の高い成績を実資料の精度保証へ読み替えない。

初期採用案はA・D群にSumiとNemotron-PII-Japan、B群に公開人物属性からの独自文書、C群に既存画像と独自見本、E群に規則で作る日本語履歴、F群に医療素材と法的分類別の独自例。件数は用途と必要な精度差を決めてから算定し、本調査では根拠なく必要標本数を固定しない。
