# PII検出器向けの公開テストデータ・開発用サンプル

調査日：2026年10月16日。対象は、LLMを使わず端末内で個人情報や機密性を判定するシステムの開発・評価。公開された合成資料、決済会社の公式テスト値、データ生成器を調査した。データセット本体を一括取得・再配布する作業や、銀行・決済APIの呼び出しは行っていない。

## 結論

[追加データセットの拡張調査](pii_related_datasets_expansion_20261016.md)：業務メール・会話、秘密鍵・APIキー、日本語NER、画像・PDF、表・合成取引へ範囲を拡張。元資料との重複、PII正解の有無、独自条件・研究限定の資料を整理した。

**銀行口座・クレジットカードを含むデータはある。** ただし、次の3種類を使い分ける。

| 種類 | 向く試験 | 向かない判断 |
|---|---|---|
| 決済会社の公式テスト値 | 番号の形式検出、サービスの試験環境での成功・失敗処理 | その値が実在人物の秘密かの判断、一般銀行での動作保証 |
| 正解箇所付きの合成文書 | BERTの学習・評価、文脈・位置抽出、誤警告の比較 | 合成データの高得点だけで本番の精度を保証すること |
| ローカルのデータ生成器 | 件数追加、書式の揺れ、機械的な境界条件の試験 | 未割当番号の保証、文脈や正解位置の自動的な正しさ |

「番号に似ている」「検査数字が正しい」「実在する」「個人と結び付く」「送信禁止」は別の属性として記録する。例えば公式テストカードは、カード形式の検出では陽性でも、実在顧客のカード情報としての正解例ではない。既知テスト値の例外を認めるかは組織の規則で決める。

IBANは国際銀行口座番号、BBANは国内部分の銀行口座番号、CVCはカードの確認用コード。各国の形式は日本の銀行コード・支店・口座種別・口座番号と同じではない。

Sumiは、日本語特有の紛らわしさを調べる初期候補になる。「森」「林」が人名か一般名詞か、電話番号に見える注文番号、口座に見える請求番号などを含む。検査数字を厳密に検証する検出器がSumiの不正番号を拾わなくても、その条件だけで不具合とは判定しない。[固定版の説明](https://huggingface.co/datasets/NagaYu/sumi-ja-pii-corpus/blob/cb9a4717568f5b631317624b323625955ac76dfe/README.md)。

OpenPIIの`language=ja`だけで、日本語本文や自然な日本の書式が保証されるわけではない。公開プレビューには英語本文に`ja`が付いた例もあり、言語・住所・番号形式を抽出後に確認する。列にあるラベルや分割の宣言と、各行の品質を分けて評価する。[公式プレビューと説明](https://huggingface.co/datasets/ai4privacy/pii-masking-openpii-1.5m)。

SumiのCC BY-SAは改変資料を配布する場合などに同一条件が関係する。学習済みモデルへの適用範囲を本稿で断定しない。各資料の帰属表示、行ごとの出所、採用時の版を記録する。

## カード・口座の公式テスト値

**以下は各提供者の試験環境に対して公表された値。** ローカルの検出試験では文字列として利用できる。決済・振込動作の試験は当該提供者の試験キー・試験環境に限定される。

| 対象 | 公式テスト値の例 | 条件・出典 |
|---|---|---|
| Visa | `4242424242424242` | [Stripe](https://docs.stripe.com/testing)、[PAY.JP](https://docs.pay.jp/v2/guide/developers/testcards) |
| Mastercard | `5555555555554444` | 同上 |
| JCB | `3566002020360505` | 同上 |
| 米国の銀行口座 | 口座`000123456789`、routing `110000000` | StripeのACHテスト。ACHは米国の銀行間決済の仕組み。[公式](https://docs.stripe.com/testing) |
| **日本向け銀行口座** | 口座`0001234`、routing `1100000` | Stripe Connectの日本向け入金テストで成功。[公式](https://docs.stripe.com/connect/testing#japan) |
| 日本向けの不存在口座の再現 | 口座`1111116`、routing `1100000` | Stripe Connect内で`no_account`を再現。同上 |
| 欧州のIBAN | `NL98ABNA0410108103` | AdyenのSEPA Direct Debit試験例。SEPAは欧州の共通決済枠組み。[公式](https://docs.adyen.com/payment-methods/sepa-direct-debit/api-only/#test-and-go-live) |

日本向けの`routing`は上記APIの入力値であり、本稿で特定の実在銀行・支店へ読み替えていない。これらは日本の全銀行で未割当・送金不能と保証された番号ではない。先頭の0を保持するため、番号は整数へ変換しない。

同じテストカードが複数会社に載っていても、すべての試験番号・エラー条件が共通とは限らない。カードの期限・CVC等の入力要件は各公式資料を参照する。[PAY.JPの試験・本番の違い](https://docs.pay.jp/v2/guide/developers/testmode-livemode)。

銀行APIそのものを日本で試したい場合は、[GMOあおぞらネット銀行sunabar](https://gmo-aozora.com/pfbank/sunabar/index.html)もある。仮想銀行口座で操作する試験環境で、利用には同銀行の口座が必要。匿名で取得できるPII評価用CSVとは異なり、今回ログインや口座作成はしていない。

## 自分で件数を増やす生成器

| 生成器 | 言語・用途 | 確認した点と制限 |
|---|---|---|
| **[Faker](https://faker.readthedocs.io/en/stable/locales/ja_JP.html)** | Python。日本語の氏名・住所等と各種番号生成 | カード生成は形式・Luhn検査数字を扱う。日本語設定だけで日本の銀行口座専用形式や未割当保証が得られるわけではない。[カード仕様](https://faker.readthedocs.io/en/master/providers/faker.providers.credit_card.html)、[銀行情報](https://faker.readthedocs.io/en/master/providers/faker.providers.bank.html) |
| **[Bogus](https://github.com/bchavez/Bogus#api-support)** | C#/.NET。日本語を含む疑似情報、カード、口座、IBAN等 | 公式説明はカードのLuhn妥当性を明記。口座の一般的な乱数生成を、日本の銀行用の保証付き試験口座と扱わない |
| **[gofakeit](https://github.com/brianvoe/gofakeit)** | Go。氏名・住所・金融系等の値生成 | ローカルで件数を増やせる候補。日本語・日本の口座形式、検査数字、個別関数の保証は採用版で確認する |
| **[go-faker/faker](https://github.com/go-faker/faker)** | Go。カード形式等の値生成 | 確認時の[実装](https://github.com/go-faker/faker/blob/main/payment.go)は接頭辞と残りの乱数を連結し、Luhn検査桁の計算が見当たらない。Faker/Bogusと同じ保証とはしない |

Luhnはカード番号などの検査数字を確かめる計算法。有効な検査数字は、実在性や決済可能性の証明ではない。生成値も実在口座と絶対に一致しないとは保証しない。

Pythonを利用者PCへ配布しない条件でも、開発環境でFakerを使い、合成資料を事前に作ることは可能。端末で生成もしたいならGo/.NETの生成器を選ぶ。値の生成と、その値を自然な文書へ埋めて正解位置を付ける工程は別。

## このシステムの評価資料を作る案

初期の組み合わせは、**Sumiで日本語の紛らわしさ、Gretelで金融文書、公式テスト値でカード・口座の形式、日本語の自作様式で自社の処理経路**を確認する方法。日本語の追加学習にはOpenPIIの日本語行も候補とする。推論でLLMを使わなくても、資料の生成にはLLMを用いているデータセットがある。資料作成までLLM禁止なら生成器・手書き様式へ置き換える。

| 試験群 | 例・測定目的 |
|---|---|
| 正例 | 合成人物の氏名と口座を含む振込依頼、カード情報の問い合わせ |
| 既知テスト値 | 公式テストカードを記載した開発文書。形式検出と送信可否の期待値を分ける |
| 紛らわしい陰性例 | 注文番号・型番・金額・日付、一般名詞の「森」、口座を説明するだけの文章 |
| 書式の揺れ | 空白・ハイフン・全角数字、改行、表、文字認識の誤り、文書分割境界 |
| 妥当性の違い | 検査数字が正しい／不正、桁数過不足、番号だけ／名義・文脈付き |
| 操作規則 | 同じ合成文書を会社用AIへ送る場合と個人用へ送る場合。分類器ではなく送信制御も確認 |

学習用と評価用で文書のひな形や元の合成人物を分ける。Sumiの`ood`と`negatives`を含め、正例ばかりでなく実運用の陽性率に近い資料でも誤警告を測る。評価先を見て閾値を調整したら、その資料は最終評価用には使わない。

**Go/C#では文字位置の単位にも注意する。** Sumiの範囲はNFKC正規化後のPython文字位置で、終端を含まない。GoのUTF-8バイト位置やC#のUTF-16位置と無条件には一致しない。絵文字、異体字、結合文字、全角数字を含む例で正規化と位置変換を検証する。

公開された漏えいデータや、本物の銀行顧客資料を学習・開発資料として取得する必要はない。本調査では取得していない。
