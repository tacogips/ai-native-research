# 既存DLPのAPIを使う適応型運用サービスの設計

設計日：2026年11月12日。[自前の検知サービス設計](adaptive_dlp_service_design_20261111.md)から派生した別案。既存DLPを検知データの供給元とし、そのAPI（ソフトウェア同士の呼出し口）の上に、人の判定・許可・通知・知識蓄積・改善候補の評価を置く。既存製品を置き換えるのではなく、製品が公開する能力の範囲で連携する。

**実現可能。ただし、警告APIだけで改善できるのは主に対応判断と通知運用である。検知自体の見逃しを減らし、その効果を測るには、警告のない対象も列挙し、原文または十分な証拠を独立に検査する経路が必要になる。** 判定登録APIの存在を、製品内部のモデルが自動で追加学習する証拠にはしない。製品が公開しない指示文・学習データ・重みは変更対象にしない。

以下は公開資料に基づく設計案であり、契約済み環境での動作確認ではない。接続権限、契約、版、取得できる証拠、変更の波及範囲を導入時に確認する。実データ・認証情報・非公開の設定は本リポジトリへ保存しない。

## 成立条件と三つの導入方式

| 方式 | 接続するもの | できる適応的運用 | できないこと・制約 |
|---|---|---|---|
| A DLP APIのみ | 警告・検知記録・公開された設定と対応状態 | 事案の集約、確認優先度、担当振分け、判定支援、範囲を限定した許可、通知改善 | 取得できない原文・陰性・未検査は評価できない。全体の再現率や見逃し低減を保証しない |
| B DLP APIと資産情報 | Aに保存先の一覧・版・親・共有状態を追加 | 場所と属性の許可、移動・共有変更による失効、警告のない資産の抽出 | 一覧にあることは検査完了ではない。本文を確認できなければ見逃しの正解は得られない |
| C DLP APIと独立検査 | Bに認可された原文取得と補助検知・人手全文監査を追加 | 複数方式で候補を追加、全状態からの監査、独自種類、指示文改善、製品設定の比較評価 | 原文取得・抽出・保護・費用の追加運用が必要。上流製品の見逃し自体が直ったかは別測定 |

初期版はBで読取り連携と許可台帳を成立させ、Cを限定した保存先から追加する。Aしか認められない顧客でも導入できるが、画面では「DLPが返した結果の運用改善」と表示する。DLP自身が全資産・検査状態・十分な証拠をAPIで返すなら、別の保存先APIを使わずB/Cの一部を満たせる。ただし警告一覧からの推測では代替しない。

## 構成と責任分担

| 構成要素 | 責務 | 保持する権限 |
|---|---|---|
| DLP接続部 | 製品ごとの記録取得、ページ送り、状態変換、能力確認 | 顧客・製品別の読取り権限 |
| 資産接続部 | Drive等の実体ID・版・親・共有情報の取得。Cでは原文も取得 | 保存先ごとの最小読取り権限 |
| 正規化と全件台帳 | 元記録を保持し、共通形式に変換。履歴・不明状態・検査範囲を管理 | 自社台帳への書込み。原本への操作権限なし |
| 許可・通知処理 | 場所×種類×共有範囲×期限を評価。未解決事案と再発を管理 | 自社の通知先だけへの送信 |
| 人の確認画面 | 真偽、種類、見逃し箇所、業務許可を別操作で登録 | 担当が閲覧できる顧客・原文範囲のみ |
| 知識・改善処理 | 確定例・失敗知識の蓄積、補助検知の指示文や製品設定の候補作成 | 候補領域だけの書込み |
| 独立評価と適用管理 | 試験、並行検査、限定適用、停止、旧設定への戻し | 承認済みの変更計画だけを実行部へ渡す |
| 製品への変更実行部 | 判定・状態・対応可能な規則を変更し、反映を読み直す | 読取り鍵と分けた、許可された操作だけの書込み権限 |
| 補助検知部 | Cの原文抽出、規則・専用モデル・文脈モデル・例示検索 | [隔離実行設計](adaptive_dlp_sandbox_design_20261112.md)の制限内 |

主な流れは「DLP API→接続部→全件台帳→人の確認と許可→通知」。改善は「確定例→候補→独立評価→適用管理」へ進み、自前の補助検知の構成更新と、製品への限定した設定変更へ分岐する。変更結果は再び読取り接続から回収し、適用要求と実際の状態を照合する。

原本削除、共有解除、隔離、DLPの全体停止は初期版の変更対象から外す。接続先の管理画面や人による変更を上書きせず、差異を競合として扱う。

## APIの能力を接続ごとに宣言する

製品名だけで接続機能を決めない。同じ製品でも契約・版・アプリ・権限で能力が異なるため、接続時に次の契約を記録する。値は `verified`（対象環境で確認済み）、`documented`（公開仕様のみ）、`unsupported`（非対応）、`unknown`（不明）を区別する。本番の変更操作は `verified` になったものだけを有効にする。

| 能力 | 必須の確認内容 | 不足時の動作 |
|---|---|---|
| 検知取得 | 警告、候補、抑制済み、誤検知済みをどこまで取得できるか | 「取得可能な候補台帳」と表示し、全検知と称さない |
| 資産と検査範囲 | 全資産、内容版、最後の検査、処理範囲、打切り、エラー | 警告なしは `unobserved`。陰性にしない |
| 証拠 | 原文・伏字・標本・位置、元の版との対応、取得権限 | 証拠の十分性を付記。伏字から同じ値を推定しない |
| 設定変更 | 読取り・作成・変更・取消、対象範囲、競合検知、配布遅延 | 自社側だけで適用、または変更案を人へ提示 |
| 判定登録 | 個別か文書単位か、自動波及、学習利用、取消 | 自社台帳のみ。学習利用が不明なら効果を約束しない |
| 再検査 | 受付ID、対象ID、結果との対応、正常完了と失敗 | 受付済みを完了にしない。操作不可なら定期検査待ち |
| 通知抑制 | どの通知経路が止まるか、後続検知が残るか、解除条件 | 自社通知だけを抑制。製品側の通知は別扱い |

能力契約にはAPI版、契約条件の確認日、対象アプリ、権限範囲、取得限界、意味を確認した試験IDを持たせる。APIの応答項目が変わった場合は未知項目を保存し、必須項目の欠落を検知した接続の変更操作を停止する。

## 共通のデータ契約

| 記録 | 必須項目・考え方 |
|---|---|
| `ProviderObservation` | 顧客、接続、製品側ID、記録版または応答の照合値、発生・更新・取得時刻、元状態、証拠水準、取得理由 |
| `AssetBinding` | 保存先、実体ID、製品内ID、内容版、対応付けの確実性、親・共有情報と取得時刻。URLやファイル名だけでは同一視しない |
| `Finding` | 自社ID、製品由来の種類とその版、共通種類、元の候補ID、位置、証拠参照、補助検知の版、真偽判定 |
| `Coverage` | 実体版×種類版×検知経路。`complete / partial / failed / stale / unknown`、確認根拠。製品由来と補助検知を別記録 |
| `Review / Allowance` | 人の真偽・見逃し追加と、業務許可を分離。原文版、理由、担当、期限、評価世代を持つ |
| `ChangePlan` | 対象製品・設定ID、変更前の照合値、変更差分、影響範囲、根拠、評価、実行権限、戻し手順 |
| `Release` | 自社規則・補助検知の固定版、製品設定の観測版、能力契約版、評価資料の版、適用範囲 |

元の製品IDは文字列で保存し、巨大な整数IDを浮動小数点へ変換しない。証拠水準は `raw / redacted / sampled / metadata_only` とし、原文がない状態を補完生成しない。位置は文字・バイト・ページ等の単位を保存する。異なる製品の範囲を原文位置へ変換できなければ、無理に同一候補へ統合せず関連候補として束ねる。

同じ値の許可や再通知抑制には、認可された原文から作った顧客別の鍵付き照合値を使う。伏字の一致、氏名の一部、文脈の類似だけでは別ファイルへ許可を波及させない。原文を取得できなければ、製品候補IDまたは対象文書版の範囲でのみ判定を再利用する。

## 取得と同期の手順

1. 読取り接続を登録し、取得可能な状態と保存期間、更新検索、続き位置を確認する。最初に全体取得または利用可能な過去範囲の取得を行い、取得開始前の記録が欠ける場合は期間を明示する。
2. 更新時刻と続き位置を保持し、重なる時間範囲で再取得して遅延到着・順序逆転を吸収する。識別子と内容版で重複排除し、台帳への永続保存後にのみ続き位置を進める。時刻精度が粗い場合も同時刻の残りを飛ばさない。
3. 通知の受信機能がある場合も、署名・送信元・再送を検証した上で補助経路として使う。定期取得と照合を残し、通知だけで全件取得を保証しない。
4. 抑制・保管済み・誤検知済みの一覧を含めて照合する。片方の一覧にないことを削除と判断しない。保存期限、権限喪失、設定除外、原本削除を区別する。
5. 割当超過・429・タイムアウトでは待機と再試行を行い、取得遅延を通知する。保存期間を越えた欠落は `history_gap` として残す。原文の再検査で現在の状態を回復しても、失われた過去の記録が復元できたとは扱わない。
6. 製品内IDと保存先IDを公式の項目や検証済み対応表で結ぶ。版の対応が不明な候補は過去の観測として保存し、現在の原文への確定判定・許可の継承を行わない。

顧客・接続別に取得、再検査、書込みの待ち行列と割当を分ける。変更を大量投入して通常の検知取得を枯渇させない。単位時間の呼出し数、取得遅延、最古の未処理、取り込み件数の急減、打切りを監視する。

## 人の判定と通知の運用

例として、顧客管理フォルダー内の氏名・電話番号を業務上許可する。DLPが返した候補は台帳へ残し、種類・場所・許可状態で絞り込める。真検知として記録し、誤検知登録で消さない。同じ文書の秘密鍵は許可しない。

B/Cでは保存先APIで親階層と共有状態を確認し、本文の更新以外に移動、上位フォルダーの変更、外部共有、許可取消、期限到来でも再評価する。許可期限は読取り時にも検査し、共有情報は高機密5分・通常15分を初期の信頼期間とする。鮮度切れ・権限喪失・ID対応不明では抑制を継続せず、情報漏えい確定と区別した運用通知へ回す。[元設計の失効契約](adaptive_dlp_service_design_20261111.md#許可失効と過去事案の扱い)

**自社の通知を抑制しても、DLP製品自身のメール・画面・遮断・他システムへの通知は止まらない。** 初期版は既存の製品通知・保護を維持して自社側を並行検査する。通知経路を自社へ集約する場合は、対象規則について「検知を継続し記録だけを残す」構成が可能か、原本の保護動作まで無効化しないかを個別に検証する。不能なら二重通知の可能性を表示し、完全な通知停止を約束しない。

判定書戻しの既定は無効。導入試験後、実際の誤検知についてのみ、個別対象・波及なし・取消可能な操作を有効化する。業務許可は自社台帳が正とし、製品の誤検知や無視状態に置き換えない。自社画面での対応済みと製品側の対応済みは別列とし、同期失敗を隠さない。

## 何を自動改善するか

| 改善対象 | 学習する根拠 | 適用できる場所 | 自動化の限界 |
|---|---|---|---|
| 確認順序・担当・説明 | 人の確定判定、対応時間、証拠の不足 | 自社の運用処理 | 優先度を下げても候補を消さず、低優先度にも期限と監査枠を持つ |
| 許可規則の候補 | 場所・種類ごとの人の業務判断 | 自社の許可台帳 | 通知を緩める新規許可や範囲拡張は人が承認。モデルだけで登録しない |
| 製品の独自検知器・規則 | 独立した正解例と、変更前後の結果 | APIで対応を確認した設定だけ | 標準モデルの重み・内部指示文・学習過程は変更できない場合が多い |
| 補助検知の指示文・例示・辞書 | 原文に結び付いた人の正解、見逃し箇所 | Cの自前の検知部 | DLPの伏字抜粋だけで全文検知の評価をしない |
| 再検査対象・監査の配分 | 検査範囲、形式、遅延、不一致、既知の失敗 | 再検査APIまたは自前の作業待ち行列 | 製品の受付・停止を正常完了と扱わない。陰性だけに監査を限定しない |

知識は「人の確定例」「失敗知識」「実行用の承認済み設定」に分ける。元の製品、証拠水準、原文版、担当、目的、期限、派生関係を保持する。原文のないケースの知識は対応判断用とし、箇所抽出の正解へ自動昇格しない。製品の分類名から共通種類への対応も版管理し、対応変更による件数増減を精度向上と数えない。

APIに判定を登録した後、製品の将来の出力が変わっても、内部学習の因果効果とは断定しない。規則、検査対象、モデル更新、抑制、原文変更が原因になり得る。製品が内部モデルを固定できない場合、設定の照合値と観測期間を記録し、既知例の定期検査で変化を検出する。

## 見逃しを減らす補助経路

Cでは、DLPを一つの検知経路として候補集合へ加える。`製品候補 ∪ 自前規則 ∪ 専用モデル ∪ 文脈モデル ∪ 承認例検索付き検知` とし、製品が陰性でも補助経路を実行する。複数製品を同じ対象へ接続する場合も、同一内容版・範囲の対応を確認し、検知方式と抽出基盤の共通性を測る。違う製品名だけで独立とはみなさない。

高機密種類は検知結果から選別せず、事前に指定した保存先の全対応文書へ必須の補助検知を実行する。通常種類の抽出検査と人手監査は、警告あり・なし・許可済みを含む全文書から選ぶ。初期値は通常の追加検査10%、人手全文監査1%とし、処理能力と必要標本数で調整する。抽出確率と未完了の標本を記録する。資料を取得できない標本を別文書へ黙って差替えない。

Aでは「製品が検知したものの中での判定正解率・確認時間」を測る。Bでは「対象資産の列挙率・共有情報の鮮度・製品検査の観測範囲」を加える。Cで全文の正解を付けた標本を得て初めて、種類・日本語・形式別の製品単独の再現率と、補助検知を合算した再現率を測る。製品のAPIに出ていない状態を「製品が見逃した」と断定せず、検査済み・出力取得済みを証明できない場合は製品側の状態不明とする。

新種類は自社の種類定義として登録できる。製品側へ翻訳できない種類はCの補助検知だけへ追加し、A/Bでは「定義済み・検知能力未対応」と表示する。追加時は対象資産をその種類について未検査に戻し、既存文書の遡及検査を予約する。親種類の許可を自動継承しない。

## 改善候補の評価と製品への反映

1. 人の正誤・見逃し追加・不明・業務許可を分離して収集する。高機密・新種類・不一致は二重確認し、人の判定を製品ラベルで自動上書きしない。
2. 改善器が自社の指示文・例示、または製品が対応する独自検知器の候補を生成する。製品設定へ変換するときは、種類、対象、閾値、除外、処理動作の対応を一覧化し、意味を維持できない変換は拒否する。
3. 開発資料で探索し、別の固定試験と新期間標本で現行版と比較する。原文・人物・ひな形・派生文書群を分離し、製品からの回答をそのまま正解にしない。絶対性能、対比較、重大例の新規見逃し、適合率、確認負荷、費用を別々に評価する。[評価の詳細契約](adaptive_dlp_service_design_20261111.md#自動改善と適用判定)
4. 製品に試験環境・対象限定・監査のみ実行などの機能があれば、合成資料と許可された評価資料で比較する。それができず全組織へ即時反映される設定は、無人で試験適用しない。自社補助検知の候補として試すか、手動変更案に留める。
5. 合格した通常の自社検知変更は並行検査、5%の限定適用、全体適用へ進める。最低7日かつ必要標本数に達するまで評価し、人手の判定遅延中は適用拡大しない。製品への変更は初期版では承認必須とし、限定範囲・反映確認・取消を実証した低影響の操作だけ、後から自動化を許可する。
6. 改善が未証明・負荷増加・検査範囲減少なら現行を維持する。悪化時は候補の適用を止め、影響範囲を再検査する。製品の内部モデルを元へ戻せない場合は「設定だけ復元、内部モデルは未復元」と記録し、過去性能への復帰を保証しない。

候補探索回数、採用試験回数、多種類の同時判定を評価計画へ登録する。合格するまで同じ採用資料へ繰り返し挑戦しない。DLPを追加で呼び出す回数や人手待ち量が増えるだけの候補を、単純な検知数の増加で改善と扱わない。

### 変更実行の状態管理

`proposed → evaluated → approved → submitted → observed → effective` とし、`conflict / unknown / failed / reverting` を分ける。承認は変更前の設定、差分、対象、期限へ結び付ける。承認後に製品設定が変わったら失効させる。単なるHTTP成功は `submitted` に過ぎず、設定の読み直しと対象資料の再検査で `effective` を確認する。

製品に条件付き更新があれば版を指定する。なければ自社の接続別直列化、変更直前・直後の読取りを行うが、他の管理者との競合を完全には防げない。競合を検出できない広範な操作は自動化しない。冪等性の保証がない操作で応答が失われた場合、状態照会で確認するまで再送せず `unknown` とする。

複数製品の一括変更を原子的な取引とみなさない。製品ごとの結果を記録し、部分適用は運用通知する。元へ戻す際は自社が変更した項目だけを現在値と照合して戻し、別の管理者の変更を消さない。返却された対象別エラー、非対応動作、設定配布待ちを個別に追う。

製品への書戻しが再び取得されたときは、自社の変更ID・製品ID・操作・観測時刻を照合して自己循環を止める。その記録は新しい人の判定や独立した学習例として追加しない。一方、同じ対象の無関係な新しい検知まで除外しない。

## DriveとNightfallを使う運用例

以下はAPIの動作実証ではなく、方式Cを具体化した処理例である。

1. Nightfallの違反・候補を取得し、元ID、伏字、検知器、位置を保存する。Drive実体IDへ確実に結べるものだけ、Drive APIで親・共有・内容版を補う。結べない候補は対応不明として残す。
2. 顧客管理フォルダーの電話番号を人が「真検知、業務上許可」と判定する。自社の許可台帳に登録し、自社通知を止める。製品の誤検知登録やファイル全体の無視は行わない。
3. 実際の誤検知を製品へ戻す場合だけ、確認済みの個別判定APIを使用する。Nightfallの `autoApply` は公開調査では既定で真のため、個別試験では明示的に偽を指定し、対象外へ波及しないことを確認してから採用する。[P1]
4. Driveの全文書一覧から選んだ全文監査で、Nightfallの警告がない議事録内の秘密鍵を発見する。製品の検査済み版が不明なら製品側は状態不明のまま、自社の見逃し追加として原文位置を確定する。
5. 確定例から自前の秘密鍵検知規則や文脈検知の指示文候補を作り、独立評価後に補助検知へ適用する。Nightfall内部の指示文を変更したとは記録しない。
6. 同じ種類の対象文書を自前で再検査し、補助候補を台帳へ追加する。Native SaaSの違反台帳への任意結果登録は前提にせず、製品由来と補助検知由来を別表示する。
7. 顧客管理フォルダーが外部共有になれば、電話番号の許可を失効させて再通知する。製品側の検知や学習の更新を待たず、現在の共有条件で判定する。

この例で自動改善したのは自社の補助検知と運用である。製品側の検知改善は、その製品が変更可能な規則を公開し、変更前後の再検査を比較できる場合にだけ別の改善経路として評価する。

## API利用時の隔離と機密保護

[隔離実行設計](adaptive_dlp_sandbox_design_20261112.md)を引き継ぎ、DLPの読取りと書込み、保存先の原文取得、外部モデル呼出しを別の資格情報・実行主体にする。API応答に含まれる文脈・URL・説明文も信用しない入力として扱う。改善器が応答内の指示を実行したり、応答が指す任意URLから証拠を取得したりしない。

API接続部は登録された製品・顧客の宛先だけへ接続する。返却される継続URLや内容取得URLも、公式仕様で必要な宛先・経路を検証した上で使用する。転送先へ認証情報を渡さない。解析処理の通信禁止を解除せず、必要な本文は管理側が搬入する。

DLP提供者で行う検査は自社sandboxの外である。自社の台帳や補助検知を隔離しても、製品側の原文送信・保持・再委託・学習利用条件は変わらない。製品内の証拠を自社へ複製すると保持先が増えるため、原文・伏字・検索索引・監査記録ごとに保持期限と削除責任を定義する。

自社で原文・確定例を削除しても、製品側へ削除が伝播するとは限らない。削除APIがなければ契約上の削除手順・保持満了を別に追跡する。自社の権限失効時には、既に複製済みの証拠と検索結果へのアクセスも停止する。外部製品から取得した事実を、この公開リポジトリへ保存しない。

## APIと実装の順序

変更と読取りの責任者を分け、閲覧権限だけの利用者は変更計画を承認できない。承認後も実行時に顧客・操作・期限を再認可する。製品側の変更権限を細分化できない場合は、資格情報を専用実行部へ閉じ込めて操作の許可一覧を強制し、それでも影響範囲を限定できない操作は手動扱いにする。

自社APIの案は `POST /connections`、`GET /connections/{id}/capabilities`、`GET /observations`、`GET /coverage`、`POST /reviews`、`POST /allowances`、`POST /change-plans`、`POST /change-plans/{id}/approve`、`GET /change-plans/{id}`。製品固有のURLや操作名をモデルに自由入力させず、接続部が能力契約から構築する。既存製品のAPIと本サービスの提案APIは別物である。

| 段階 | 実装する範囲 | 完了条件 |
|---|---|---|
| 1 読取り連携 | 一製品、全状態取得、正規化、続き位置、欠落表示 | 重複・遅延・保存期間超過・抑制済み取得の試験に合格。書込み権限なしで稼働 |
| 2 Bの運用 | 資産対応、許可、失効、確認画面、自社通知 | 氏名・電話は記録だけ、秘密鍵は通知、移動・共有・期限で再評価。製品通知との二重性を表示 |
| 3 Cの検知改善 | 原文取得、隔離抽出、補助検知、全文監査、確定例と指示文改善 | DLPが見逃した合成例を独立経路で拾い、状態不明と実際の見逃しを区別。種類別再現率を測定 |
| 4 限定した書戻し | 個別判定、再検査、検証済み設定の変更計画 | 波及・取消・競合・応答喪失・部分適用・自己循環・再検査結果を確認 |
| 5 複数製品 | 接続追加、種類対応、横断集約、割当分離 | 別製品の欠落や停止が他の候補を消さない。製品別と合算の評価を分離 |

最小構成は、API接続処理、永続的な作業待ち行列、PostgreSQLの台帳、顧客別の短期証拠領域、確認画面、適用管理でよい。Cを追加する段階で、既存の自前設計から抽出・補助検知・評価を再利用する。A/Bの導入に全GPU基盤の構築を必須にしない。

## 受入試験と運用指標

| 反例・障害 | 期待する動作 |
|---|---|
| 同一イベントが遅れて重複し、順序が逆転 | 履歴を保持し、最新状態を巻き戻さず、再通知を重複させない |
| APIが空配列を返すが検索窓上限・権限不足がある | 取得完了とせず、不明・欠落を表示 |
| 抑制済みの結果が通常一覧から消える | 別一覧から回収し、許可・誤検知・消去を混同しない |
| 異なる人の伏字が同じ、複数製品の位置単位が違う | 値の同一視・許可伝播を行わず関連候補として保持 |
| 氏名を検知済みの文書で秘密鍵を見逃す | 陽性文書も全文監査と補助検知の対象に残る |
| 原文が旧版、共有情報が期限切れ | 現行への判定継承と通知抑制を止める |
| 製品への判定が組織全体へ波及する | 個別操作の能力不適合として無効化し、自社台帳のみで運用 |
| 書込み直後に応答喪失、管理者が設定を変更 | 再送・上書きを止め、状態照会または競合確認へ |
| 202で再検査受付後、実際には実行されない | 完了にせず期限と理由を追跡。対象と版に結び付いた結果を要求 |
| 自社の書戻しが新しいAPI事象になる | 同じ判定を再学習・再書込みせず、無関係の新規検知は残す |
| 新種類を製品APIで表現できない | 補助検知のみ、または能力未対応を明示。登録成功を検査開始としない |
| 製品内部モデルが変わり旧版へ戻せない | 設定復元とモデル復元を区別し、自動適用を停止して再評価 |

運用指標は、取得遅延・欠落期間・資産対応率・証拠充足率・検査範囲の不明率・判定待ち時間・許可失効遅延・変更の実反映率・通知重複率を持つ。Cでは製品単独と合算の種類別再現率・適合率・共同見逃し率を追加する。警告減少だけを精度向上の指標にしない。API課金・原文転送・補助推論・人手の費用を別々に測り、割当不足時は未完了を残す。
