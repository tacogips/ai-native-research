# PrivacyBench

![textual synthesis diagram](textual_synthesis_diagram.png)

PrivacyBench is a benchmark for de-identifying semi-structured data exports from work tools like email, messaging, shared file storage, calendar, and so forth. The benchmark focuses on the identification and synthesis of PII in the unstructured text fields of the data export, and introduces novel metrics for evaluating synthesis quality. PrivacyBench contains one month of workspace exports from 21 distinct personas. The data is fully synthetic and in the format a real data export produces with Slack messages as json, emails as eml files with base64-encoded attachments, and Word, Excel, CSV, and PDF files in their native formats. The email and Slack messages were generated by the [Fabricate](https://fabricate.tonic.ai/) synthetic data tool using a seed list of characters. Fabricate maintains a coherent narrative across the set of messages and timeframe, referencing documents as normal work conversations would. The documents (Word, Excel, CSV, and PDF) were generated from the message narratives using Claude Code. For half of the tasks the documents are attachments to messages and for half the tasks the documents are in a drive folder. Ground truth labels for personally identifiable information (PII) and organizational information are created using the seed list of characters, so the benchmark requires no human annotators.

Across the seven de-identification pipelines we tested, Textual Graph Synthesis, Tonic's workspace de-identification solution, performed best, with the highest detection (96.4%) and synthesis (94.3%) scores and the only combined score above 95%. Every other pipeline was a pure-LLM agent built on a frontier model from OpenAI or Anthropic. The best of them trailed Textual by five points on the combined score.

De-identifying unstructured text is difficult in two separate directions: detection of sensitive entities and coherent replacement of detected entities. Both of these directions are necessary to have private and high utility synthetic data. Detecting sensitive entities covers the privacy aspect of the synthetic data, and is done by named-entity recognition (NER). This is well studied with many benchmarks out there, [CoNLL](https://huggingface.co/datasets/eriktks/conll2003), [Ontonotes](https://catalog.ldc.upenn.edu/LDC2013T19), and [TAB](https://github.com/NorskRegnesentral/text-anonymization-benchmark) to state a few. Choosing coherent replacements of the detected entities determines the utility of the synthetic data, and no benchmarks exist that measure the accuracy of chosen synthetic replacements. This is where PrivacyBench comes in, as it measures both the privacy and the utility of synthetic data by examining what entities are detected and what their replacements are.

Consistent synthesis of replacement PII is difficult, because it requires one to consistently treat different textual representations of a character's identity. Consider a simple example with one character, Joseph Ferrara (who often goes by Joe), who has two email addresses jferrara@gmail.com and joe@tonic.ai, and has Slack handle JoeF. These different textual representations may occur within the same document or across many different documents, and the challenge is to synthesize replacement PII for all instances coherently so that the synthetic PII all align with a single synthetic character. When there are many documents of different types with a lot of cross references, character PII linking and synthesis across documents becomes very difficult.

Measuring synthesis quality is difficult due to the abundance of possible good synthetic replacement possibilities making the creation of ground truth labels difficult. PrivacyBench addresses this by cleverly creating character PII ground truth labels as part of the synthetic data generation process, and then using a simple LLM-as-a-judge to measure synthesis quality for each character in the ground truth. Rather than a single correct replacement, the ground truth records which spans belong to each character, and the judge checks whether the pipeline's replacements for those spans form one coherent synthetic identity instead of matching a fixed value. PrivacyBench uses this process to define a new metric called synthesis accuracy.

As a POC, PrivacyBench is evaluated on seven de-identification pipelines that consume the raw exports and return replaced spans in native coordinates. The seven pipelines consist of Tonic Textual's Graph Synthesis, and six agent pipelines written and processed by OpenAI's GPT-6 Astra, GPT-5.6 Terra, Sol and Luna and Claude Opus 5 and Claude Sonnet 5. Each pipeline consists of the four steps of text extraction, named-entity recognition (NER), synthesis, and output file rendering. The same LLM that wrote each pipeline also performed NER and synthesis. The scores stratify the models by capability, and Tonic Textual's Graph Synthesis performs better than any of the pure LLM pipelines.

Tonic built this benchmark and the system that scores highest on it. For that reason this dataset and the metrics have been designed so that anyone can evaluate their own de-identification systems on this data and compare directly to the scores published here. The metrics code is open source on GitHub at [TonicAI/privacy_bench_metrics](https://github.com/TonicAI/privacy_bench_metrics), and the Textual NER scores are reproducible using the [Textual SDK](https://github.com/TonicAI/textual). The Textual NER models have not been trained on any of the PrivacyBench data.

This is PrivacyBench v2.5; see [What's new in v2.5](#whats-new-in-v25) for the changes from v2, and the [`v2`](https://huggingface.co/datasets/TonicAI/Privacy-Bench/tree/v2) and [`v1`](https://huggingface.co/datasets/TonicAI/Privacy-Bench/tree/v1) tags for the earlier versions.

## Dataset overview

- **21 raw data exports**: one per fictional protagonist, each set in a different industry (pharma, retail, finance, airlines, tech, manufacturing, etc). Each export is a file tree in the real formats a de-identification pipeline ingests: RFC 5322 `.eml` emails, a Slack workspace export, and a Google Drive style listing.
- **18,040 messages** — 2,540 emails and 15,500 Slack messages, all with message-level ground truth. On average about 25,000 words, 120 emails, 740 Slack messages, and 24 characters per data export.
- **357 supporting documents** — 17 per dataset (10 PDF, 3 DOCX, 2 XLSX, 2 CSV), delivered as base64 email attachments and Slack file shares in 11 datasets and through the Drive listing in the other 10.
- **10 PII entity types**: `NAME_GIVEN`, `NAME_FAMILY`, `EMAIL_ADDRESS`, `USERNAME`, `ORGANIZATION`, `PHONE_NUMBER`, `LOCATION_ADDRESS`, `EMPLOYEE_ID`, `ACCOUNT_NUMBER`, `URL` 
- **Gold ground truth for every message and document**: 130,370 PII spans (31,088 in messages, 99,282 in documents), each carrying its location in the containing file's native coordinates (byte offsets in the `.eml`, JSON pointers in the Slack day files, per-glyph boxes in the PDFs, XPaths in the DOCX, cells in the XLSX), plus a character roster per dataset. Each span is associated to one of the characters or organizations in the data.
- **Human-annotated ground truth** for the emails, Slack messages, PDFs, and Word documents for 6 of the 21 datasets. This totals 5,198 messages, 656 PDF or Word pages, and 25,855 total spans. These human annotated tasks are used to compute full NER scores (precision, recall, F1) and to validate the generated ground truth (see [NER scores on human annotations](#ner-scores-on-human-annotations)).
- **Four-stage task**: extract (parse the raw exports into text) + NER (detect PII) + synthesis (replace coherently) + apply (render the synthetic export), scored by three metrics (see below).
- All data is **fully synthetic**.

## Metrics

The evaluation reports three headline scores (and a per-entity-type breakdown of each):

1. **NER recall**: the fraction of ground truth PII spans that the pipeline detected. `recall = TP / (TP + FN) = correctly detected ground truth spans / all ground truth spans`.
2. **Synthesis accuracy**: of the ground truth spans that were detected, the fraction whose synthetic value is coherent, as determined by an LLM-as-a-judge. The LLM-as-a-judge gets one call per character, evaluating each synthetic replacement against the character's inferred synthetic identity.
   `synthesis accuracy = coherent / (coherent + incoherent)`.
3. **Synthesis + NER accuracy**: the overall synthesis pipeline score. This score folds detection misses into the denominator of synthesis accuracy scoring the overall pipeline. It does not distinguish synthesis misses or NER misses. `synthesis + NER accuracy = √(coherent / all ground truth spans)`. Inside the square root, the  denominator is the same as the denominator of NER recall, the number of ground truth spans. The square root is a normalizing term that makes this score the geometric mean of NER recall and synthesis accuracy `synthesis + NER accuracy = √(NER recall × synthesis accuracy)`.

## Baseline results

PrivacyBench is evaluated end to end on seven de-identification pipelines. Each pipeline reads the raw exports, detects PII, chooses coherent synthetic replacements, and reports every replaced span in the containing file's native coordinates; it is scored against the full ground truth of all 21 datasets. There are two types of pipelines:

* Textual Graph Synthesis which is Tonic's workspace de-identification pipeline: Tonic Textual NER plus graph-based synthesis that links every mention of a person or organization across the export and replaces them consistently. The LLM used for Textual Graph Synthesis in these experiments was GPT-5.6 Sol.
* Pure LLM de-identification, which consists of six agent pipelines. Each agent pipeline consists of four steps: extraction, NER, synthesis, and rendering. Each LLM evaluated, acting as a coding agent in a sandbox, wrote its own extraction and rendering code. The same model then did NER and synthesis through an NER and synthesis harness we use internally to benchmark LLMs. Combining these four steps gives a pipeline that can evaluate how capable a single LLM is at de-identifying workspace data.

Scores are the macro average over the 21 datasets (each dataset weighted equally; Synthesis + NER accuracy is the geometric mean √(NER recall × synthesis accuracy) computed per dataset, then macro-averaged), ordered by the bottom-line Synthesis + NER accuracy.

| Pipeline                | NER recall | Synthesis accuracy | Synthesis + NER accuracy |
| ----------------------- | ---------- | ------------------ | ------------------------ |
| Textual Graph Synthesis | **96.4%**  | **94.3%**          | **95.3%**                |
| GPT-6 Astra             | 92.9%      | 87.5%              | 90.1%                    |
| Claude Opus 5           | 95.1%      | 85.1%              | 89.9%                    |
| GPT-5.6 Sol             | 91.2%      | 82.4%              | 86.7%                    |
| Claude Sonnet 5         | 90.3%      | 79.6%              | 84.7%                    |
| GPT-5.6 Terra           | 86.1%      | 78.7%              | 82.2%                    |
| GPT-5.6 Luna            | 55.5%      | 77.5%              | 65.4%                    |

Textual Graph Synthesis leads on every column: the highest detection recall (96.4%, 1.3 points ahead of Claude Opus 5, the strongest detector among the agent pipelines), the highest synthesis coherence (94.3%), and a combined score 5.2 points clear of the best agent pipeline. Behind it, GPT-6 astra and Claude Opus 5 sit in a dead heat (90.1 vs 89.9).

The low GPT-5.6 luna row is an extraction failure. The code that GPT-5.6 wrote to extract entities from PDFs,  places PDF spans at the wrong coordinates, so most of its document detections do not count. Writing the pipeline itself is part of the task and this points to one of the difficulties of working with documents in their native formats.

Synthesis accuracy is measured over the spans a pipeline detected, so a pipeline that detects less is judged on an easier subset; the combined score folds the misses back in through NER recall and is the number to rank by.

## NER scores on human annotations

The baseline results above show that Tonic Textual's NER model is the backbone of the strongest pipelines, but they only measure NER recall against the machine generated ground truth. The generated ground truth is built from the seed cast of characters, their PII, and the organization they work at for each dataset. It is not an exhaustive list of every person or organization that may appear in the data. Additional people and organizations that are detected but not in the generated ground truth should not penalize the NER model if the detection is correct. This is why precision is not considered in the benchmark scores. 

To get a fuller picture of NER, the email and Slack messages as well as the PDFs and Docx files of 6 of the 21 datasets (`megan_donovan_eli_lilly`, `morgan_morgan_stanley`, `daniel_lincoln_financial_group`, `isabella_chipotle`, `nora_caterpillar`, `renee_tyson_foods`) were fully annotated by human annotators. This includes 25,855 total spans across 5,198 messages and 656 PDF and Docx pages. These human annotations accomplish the two goals of providing full NER scores (precision, recall, and F1) giving a complete measure of NER quality, and validating the machine generated ground truth labels used in the benchmark scores above. 

The human gold is part of this dataset under `human_annotations/`: `<set>.jsonl` for the messages (6 datasets) and `<set>_documents.jsonl` for the annotated document pages (6 datasets) — see [File schemas](#file-schemas).

### Full NER scores

Textual is the clear winner for overall NER when precision, recall, and F1 are all considered together across the combined human annotations. The two Textual rows are the only systems above 92% F1, the only ones above 90% recall under overlap matching, and the only ones above 90% on precision, recall and F1 at once. Some of the LLM pipelines do have slightly higher precision (about one percentage point), but they lose a lot on recall (by eight percentage points or more). For pure privacy considerations, recall is the more important metric, as a precision miss over-redacts a span that wasn't PII, while a recall miss leaves real PII in the output.

Every row in this table except Textual Graph Synthesis was run on pre-extracted text (the message bodies and the extracted text of the documents). This isolates NER from text extraction, and makes the Textual via SDK row reproducible with a Textual API key (see the reproducibility note below). Textual Graph Synthesis is included for consistency with the rest of this document. It does the harder end-to-end synthesis job, extracting the document text itself. Textual Graph Synthesis is built for workspace export de-identification, so it has additional NER steps that leverage the structure of the workspace documents (for instance the to and from fields of an email or the users json file of a Slack export). This is how it achieves a comparable but different NER score to Textual via SDK even though it has the harder overall task.

[Presidio](https://microsoft.github.io/presidio/) (spaCy `en_core_web_trf`) and [GLiNER2](https://github.com/fastino-ai/GLiNER2) (`fastino/gliner2-privacy-filter-PII-multi`) are evaluated as well as the most popular open source NER models. They are run with their built-in recognizers and schema extended generically to the five document labels (Presidio: phone/location/URL/bank recognizers plus one generic prefix-dash-digits id pattern; GLiNER2: generic descriptions for the new labels).

**Note on reproducibility**

The Textual via SDK scores are from Textual v496 (2026-10-15). Textual versions can carry small changes in the underlying NER models, so scores may shift slightly from version to version. To reproduce the **Textual via SDK** row, use the [privacy_bench_metrics](https://github.com/TonicAI/privacy_bench_metrics) repo (`pip install tonic-textual regex`, set `TONIC_TEXTUAL_API_KEY`):

```bash
DATA=/path/to/this/dataset
python -m synthesis_evaluation.run_textual_ner \
  --input "$DATA/human_annotations/*.jsonl" \
  --config synthesis_evaluation/textual_config.json \
  --out textual_predictions
python -m synthesis_evaluation.run_ner_eval \
  --gold "$DATA/human_annotations/*.jsonl" \
  --predictions-dir textual_predictions \
  --run-name textual_human_gold
```

The pooled row of the output is the combined score above. The same `run_ner_eval` command scores any NER engine's predictions against the human annotations.

The **Presidio** and **GLiNER2** rows are reproduced the same way with `synthesis_evaluation.run_baseline_ner --engine presidio|gliner` over the same `human_annotations/*.jsonl` files.

### Validating the generated ground truth

The annotators started from the generated ground truth (as it stood in v2) and corrected it, so the human annotations also measure how good the generated labels are. Across the 6 datasets they reviewed 23,486 generated spans (8,250 in the messages, 15,236 on the document pages) and confirmed 22,502 of them exactly (95.8%). They removed 347 spans, moved the boundaries of 598 and changed the label of 39, and they added 2,805 spans the generator did not include. The generated ground truth is rarely wrong but somewhat incomplete: the v2.5 ground truth scored as NER predictions against the human gold reaches 98.2% precision and 88.5% recall under overlap matching. The misses concentrate on ORGANIZATION (77.9% of the human organization spans are in the generated ground truth), ACCOUNT_NUMBER (77.8%), URL (81.0%) and LOCATION_ADDRESS (82.6%), while USERNAME, PHONE_NUMBER and EMPLOYEE_ID sit at 99–100% and the name and email labels at 89–94%.

## What's new in v2.5

PrivacyBench v2.5 is an improvement of v2: the synthetic workspace export data has not changed from v2, but the generated ground truth labels have been audited and improved, and the overall NER + Synthesis accuracy score has a refined definition.

- **Corrected ground truth.** 2,539 spans were removed net (132,909 → 130,370), almost all of them spurious `ORGANIZATION` spans. `LOCATION_ADDRESS` is now street-level only where as before it covered both street-level only addresses and full street, city, state, zip complete addresses. A handful of missing `NAME_GIVEN` and `USERNAME` spans were added. Row ids, texts, and the character rosters are unchanged, so v2 pipeline outputs score directly against the v2.5 ground truth.
- **Synthesis + NER accuracy is now a geometric mean.** The combined score per dataset is √(NER recall × synthesis accuracy) instead of their product. This is the square root of the v2 combined score `coherent / all gold spans` (see [Metrics](#metrics)). By changing to the geometric mean we keep the interpretability of the v2 combined score but with a combined score that has the same scale as NER recall and synthesis accuracy allowing for more clear comparison of the three scores. The macro average over datasets is averaged over the per-dataset geometric means.
- **Newer judge.** The published synthesis accuracy scores are judged by `claude-opus-5-5` (v2 used `claude-opus-4-7`). Opus 5-5 is the newest Opus model and none of the pipelines themselves used Opus 5-5.
- **Graph synthesis improvements.** Tonic Graph Synthesis is under active development and improvements to the solution have led to higher NER recall and synthesis accuracy scores.
- **All seven pipelines rescored.** The LLM pipeline outputs are unchanged from v2. All pipelines are rescored using the improved ground truth, new LLM judge, and new combined-score definition.

The v2 data and card remain available at the `v2` revision of this repository, and v1 at the `v1` revision.

## What's new in v2

PrivacyBench v2 replaces the message-only benchmark released as v1 with a harder, end-to-end version of the same task. PrivacyBench v1 consisted of email and Slack messages in an easy to process json format, and the task asked for synthesis over five entity types. Its evaluated pipelines had two steps, NER and synthesis, and the synthesis step was always done by an LLM. PrivacyBench v2 includes the v1 data in a new format (Slack export json structure, eml for emails), adds additional file types, and includes additional labeled entity types. The task is now a full de-identification job requiring parsing the files, detecting PII, replacing it coherently, and writing the synthetic export back out in the same file format as the input. In the new version, the task is evaluated end-to-end with Tonic's Textual Graph Synthesis pipeline and full LLM pipelines.

The main changes:

- **Raw exports, not extracted text.** Inputs are now RFC 5322 `.eml` files with base64 attachments, Slack workspace exports, and Drive-style listings, and pipelines must do their own text extraction and rendering.
- **Documents.** 357 new supporting documents (PDF, DOCX, XLSX, CSV) adding to the existing 18,040 messages.
- **Ten entity types instead of five.** `PHONE_NUMBER`, `LOCATION_ADDRESS`, `EMPLOYEE_ID`, `ACCOUNT_NUMBER`, and `URL` are new.
- **Native coordinates.** Every span is located in its containing file's own coordinate system (byte offsets, JSON pointers, per-glyph boxes, XPaths, cells) rather than character offsets into a text field, so the output schema has changed.
- **New pipelines.** The v1 NER-then-synthesis pipelines are replaced by Textual Graph Synthesis and six agent pipelines built by current frontier models.

The metric definitions (NER recall, synthesis accuracy, synthesis + NER accuracy), the character-linked ground truth, and the LLM-as-a-judge protocol are unchanged. Note that scores are not comparable across versions because the data has changed significantly. Because the task is more difficult now the v2 pipeline scores are lower than the v1 pipelines scores. The v1 data and card remain available at the `v1` revision of this repository, and the matching release of [privacy_bench_metrics](https://github.com/TonicAI/privacy_bench_metrics) is tagged `v1`.

## Layout

```
tasks/<set>/                    the INPUT — one raw export tree per dataset
  email/<id>.eml                  RFC 5322 emails, one file per message
  slack/users.json                Slack workspace export: metadata files …
  slack/channels.json, groups.json, dms.json, mpims.json
  slack/<conversation>/<YYYY-MM-DD>.json          … and one day file per conversation per day
  slack/<conversation>/attachments/<id>-<name>    files shared in Slack (embed datasets)
  drive/files.json                Google Drive style file listing
  drive/<name>                    the files in Drive (drive datasets)
ground_truth/<set>/             the ANSWER KEY — never an input to a pipeline
  ground_truth.jsonl              gold PII spans with locations in each file's native coordinates
  spans.jsonl                     the same rows and spans without the locations (powers the dataset viewer)
  characters.json                 the character roster
human_annotations/<set>.jsonl   human-annotated NER gold for 6 of the datasets
reference/                      extract.py — a reference extractor for the export trees
example_output/                 an example output
```

`<set>` is the dataset name, formatted as `{protagonist}_{organization}` (e.g. `megan_donovan_eli_lilly`, `aaron_pfizer`, `renee_tyson_foods`).

There are 21 datasets, each a distinct fictional protagonist and their coworkers in a different industry. All data is synthetic, generated by Tonic [Fabricate](https://fabricate.tonic.ai) from a seed that declares each character's PII up front — which is why ground-truth labels exist without any human annotation.

Every dataset carries 17 supporting documents (10 PDF, 3 DOCX, 2 XLSX, 2 CSV). Where they live alternates by dataset:

| mode | datasets |

## Loading the data

This is a **file-tree dataset**: the inputs are raw export trees, so the way to use it is to download the files and read them directly.

```python
from huggingface_hub import snapshot_download

local = snapshot_download(
    repo_id="TonicAI/Privacy-Bench",
    repo_type="dataset"
)
```

A reference extractor ships with the dataset. It parses one export tree back into per-message and per-document records:

```bash
python reference/extract.py tasks/aaron_pfizer --out extracted/aaron_pfizer --document-text
```

writes `messages.jsonl` (one `{meta, text}` row per email and Slack message), `documents.jsonl` (one row per document with its sha256, location, and — with `--document-text` — extracted text), and the decoded document files. Identity is carried by the files themselves: an email's row id is its filename stem (also the `Message-ID` local part), a Slack message's row id is its `ts`, and the ground truth joins on `meta.row_id`. Message extraction is pure standard library; `--document-text` needs `pdfplumber`, `python-docx`, and `openpyxl`.

The two JSONL ground-truth views (`ground_truth/<set>/spans.jsonl`, `human_annotations/<set>.jsonl`) also load with the `datasets` library and back the dataset viewer; the full `ground_truth/<set>/ground_truth.jsonl` (with per-glyph PDF locations) is meant to be read directly.

```python
from datasets import load_dataset

spans = load_dataset("TonicAI/Privacy-Bench", "ground_truth_spans", split="aaron_pfizer")
```

## File schemas

### The export files

- **`email/<id>.eml`** — real headers (`From`, `To`, `Cc`, `Subject`, `Date`, `Message-ID`, `In-Reply-To`, `References`, `X-GM-THRID`, `X-Gmail-Labels`), a single `text/plain` UTF-8 body with 8-bit transfer encoding and CRLF line endings — the body text appears verbatim in the file, so gold spans can point at file offsets. In embed datasets, attachments follow as base64 MIME parts.
- **Slack day files** — the real workspace-export shape: one JSON array per conversation per day, each message with `user`, `ts`, `client_msg_id`, `text` (HTML-escaped: `&` `<` `>` as entities, URLs wrapped in `<>`, `<@USERID>` mentions literal), `user_profile`, Block Kit `blocks`, thread bookkeeping (`thread_ts`, `reply_count`, `replies`), and `files[]` for shared documents.
- **`drive/files.json`** — a `drive#fileList` of records with `id`, `name`, `mimeType`, `size`, `md5Checksum`, `createdTime`/`modifiedTime`, `owners`, `permissions`, and `webViewLink`.

### `ground_truth/<set>/ground_truth.jsonl` — gold PII spans

One row per email body, per Slack message, and per document:

```json
{
  "meta": {
    "row_id": "1768498320.332959",
    "from": {"name": "...", "email": "..."} | {"user_id": "...", "name": "..."},
    "to": [ ... ],
    "datetime": "2026-01-15T18:12:00Z",
    "thread_ts": "..." | "thread_id": "...",
    "filename": "...", "format": "pdf", "mime_type": "...", "attached_to": { ... }
  },
  "text": "the message body, or the document's canonical text",
  "file": {
    "kind": "eml | slack | pdf | docx | xlsx | csv",
    "path": "email/<id>.eml | slack/<conversation>/<day>.json | drive/<name> | ...",
    "sha256": "...",
    "container": null
  },
  "ground_truth_spans": [
    {
      "text": "<@U02CARLOS>",
      "start": 46, "end": 58,
      "label": "USERNAME",
      "characters": ["carlos"],
      "location": { "kind": "...", ...native coordinates, see below... }
    }
  ]
}
```

- The message keys (`thread_ts`/`thread_id`) appear on message rows; `filename`/`format`/`mime_type`/`attached_to` appear on document rows. `start`/`end` are character offsets into `text`.
- `label` is one of the 10 entity types. `characters` identifies which person (or, for organizations, which `org_group`) the span refers to — this is what lets the evaluation check that one real identity maps to one consistent synthetic identity.
- `file` says which export file holds the text, with its sha256. For a document embedded in an email, `file.path` is the `.eml` and `file.container` records the MIME part and the exact byte range of its base64 body:

```json
"container": {"kind": "eml_attachment", "path": "email/<id>.eml", "part_index": 0,
              "mime_part_index": 1, "content_type": "application/pdf",
              "content_transfer_encoding": "base64", "byte_start": 1535, "byte_end": 142235}
```

  Slicing those bytes and base64-decoding them yields the document (verify with `file.sha256`); the span locations refer to the decoded file.
- Every span's `location` is in the containing file's **native coordinates**:

| `location.kind` | coordinates |
| --- | --- |
| `eml` | character and byte offsets into the `.eml` file itself (`file_char_start/end`, `file_byte_start/end`) |
| `slack` | RFC 6901 JSON pointer of the message's `text` in the day file, offsets inside that escaped string, plus the Block Kit element(s) carrying the same characters |
| `pdf` | pages (1-based), merged per-line `boxes`, and one box per character in `chars` (`[char, page, x0, top, x1, bottom]`, pdfplumber conventions) |
| `docx` | XML part, paragraph XPath, and `<w:t>`-level fragments with offsets |
| `xlsx` | sheet, A1 cell address, offsets inside the cell value |
| `csv` | row/column of the field, offsets inside the field value and in the file |

- `location.status` is `located` for 99,077 of the 99,282 document spans; 151 are `not_rendered` (footer text clipped with an ellipsis at render time — those characters are not in the PDF) and 54 `partial`. Every `located` coordinate was re-read from the published files with independent tooling and matched against the span text.

### `ground_truth/<set>/spans.jsonl` — the same gold, viewer-friendly

The same rows and spans as `ground_truth.jsonl` with the `location` objects removed and `file` reduced to `{kind, path, filename, sha256}` — a flat spans view that the `datasets` library and the dataset viewer can load.

### `ground_truth/<set>/characters.json` — character roster

A map of `character_id → declared PII` for every character in the dataset, derived from the data generator's seed. Synthesis accuracy needs this: the LLM judge groups each character's PII (the names, emails, Slack handles, phone numbers, addresses, ids, and organizations the `characters` field on the spans points at) and checks the synthetic replacements form a single coherent synthetic identity.

```json
{
  "carlos": {
    "canonical_name": "Carlos Mendez",
    "first_names": ["Carlos"], "last_names": ["Mendez"],
    "nicknames": [],
    "emails": [{"value": "carlos.mendez@lilly.com", "category": "professional"}],
    "slack_handles": ["U02CARLOS"],
    "phone_numbers_linked": ["+1 317 555 0114"],
    "employee_ids": ["EL-20443"],
    "organizations": ["Eli Lilly and Company"]
  }
}
```

### `human_annotations/` — human-annotated NER gold

`<set>.jsonl` (6 datasets): same rows as the email and Slack messages (joined by `meta.row_id`), with `ground_truth_spans` holding the human-approved spans instead of the generated ones. Spans carry `{start, end, label, text}` only — no `characters` field, because the human pass validated detection, not identity linking.

```json
{
  "meta": { ... same as the message rows ... },
  "text": "...",
  "ground_truth_spans": [
    {"start": 46, "end": 58, "label": "USERNAME", "text": "<@U02CARLOS>"}
  ]
}
```

`<set>_documents.jsonl` (6 datasets): one row per human-annotated document page (PDF pages; for Docx, the segments between explicit page breaks). Span offsets index the page `text`; the page is a slice of its document's canonical text, so `meta.canonical_start + start` gives the offset in the matching document row of `ground_truth/<set>/ground_truth.jsonl` (joined by `meta.row_id`, same 4-key spans as above, all ten labels).

```json
{
  "meta": {"row_id": "<document row id>", "filename": "…", "format": "pdf",
           "page": 3, "n_pages": 8, "canonical_start": 6120, "canonical_end": 9410},
  "text": "the page's text",
  "ground_truth_spans": [
    {"start": 118, "end": 130, "label": "PHONE_NUMBER", "text": "317-555-0114"}
  ]
}
```

### Synthesizer output

A pipeline consumes `tasks/<set>/` and produces, alongside its synthetic export, one JSON line per **file unit** (an email body, a Slack message, or one document), carrying the detected spans and their replacements in the same native-coordinate conventions as the ground truth:

```json
{
  "file": {"kind": "pdf", "path": "email/<id>.eml",
           "container": {"kind": "eml_attachment", "path": "email/<id>.eml", "part_index": 0}},
  "spans": [
    {"label": "NAME_GIVEN", "text": "Megan", "new_text": "Alicia",
     "location": { ...same shape as the ground-truth locations... }}
  ]
}
```

`text` is the exact original string at the location and `new_text` the rendered replacement; a span counts as detected and replaced only when `new_text` differs from `text`.

What the scorer reads from each row, and nothing else:

- **The file unit** is `file.kind` plus `file.path` relative to the export root (`email/<id>.eml`, `slack/<channel>/<date>.json`, `drive/<name>`); for a document embedded in an email, `file.path` is the `.eml` and `file.container.part_index` names the attachment. A row whose path or part index differs from the ground truth's matches nothing.
- **`label`** is one of the ten labels above; common engine names are accepted as aliases (`LOCATION` → `LOCATION_ADDRESS`, `US_BANK_NUMBER` → `ACCOUNT_NUMBER`, `NUMERIC_PII` → the id labels). Other labels are ignored.
- **`location`** needs only the keys below (the ground-truth files carry more, for verification):

| `file.kind` | keys the scorer uses |
| --- | --- |
| `eml` | `file_char_start`, `file_char_end` (or `file_byte_start`, `file_byte_end`) into the `.eml` |
| `slack` | `json_pointer` of the message (`/<n>` or `/<n>/text`) plus `start`, `end` in that `text` string as it appears in the day file |
| `pdf` | `chars`: `[[char, page, x0, top, x1, bottom], …]` per glyph, or `boxes`: `[{"page", "x0", "x1", "top", "bottom"}, …]` (pdfplumber conventions, 1-based pages) |
| `docx` | `fragments`: `[{"xpath", "start", "end"}, …]` over `<w:t>` nodes (with or without `[1]` indices) |
| `xlsx` | `sheet`, `cell` (A1 address), optionally `char_start`, `char_end` inside the cell value |
| `csv` | `row`, `col` of the field, optionally `value_char_start`, `value_char_end` inside the value (or `file_char_start`, `file_char_end`) |

A gold span counts as detected when a predicted span of the same unit and label covers at least half of it (or contains it); predicted spans that match no gold span are not penalized, because the ground truth covers only the seed characters and their organizations. Spans on XLSX/CSV cells, on email headers, or on text the ground truth does not cover are therefore harmless but also earn nothing.

A complete example output in this format — the Claude Opus 5 agent pipeline run on `aaron_pfizer` — ships under `example_output/`, with its provenance and a ready-to-run scoring command in `example_output/README.md`. Use it to sanity-check your setup before scoring your own pipeline.



## Running the evaluation

The scoring code lives in a separate repo, [TonicAI/privacy_bench_metrics](https://github.com/TonicAI/privacy_bench_metrics).

End-to-end scoring of a raw-export pipeline (the [Baseline results](#baseline-results) numbers) uses `run_eval_native`: point it at one dataset's predictions file (the [Synthesizer output](#synthesizer-output) format) and that dataset's answer key:

```bash
DATA=/path/to/this/dataset
python -m synthesis_evaluation.run_eval_native \
  --predictions  my_pipeline/aaron_pfizer/predictions.jsonl \
  --ground-truth "$DATA/ground_truth/aaron_pfizer/ground_truth.jsonl" \
  --characters   "$DATA/ground_truth/aaron_pfizer/characters.json" \
  --run-name     aaron_pfizer_my_pipeline
```

NER recall alone is offline — add `--skip-llm-judge` and drop `--characters`, with no dependencies beyond the standard library. Synthesis accuracy uses the LLM judge, so it needs the character roster, `pip install anthropic`, and `ANTHROPIC_API_KEY` (pass `--judge-model claude-opus-5-5` to match the published scores; the judge costs on the order of a dollar per dataset).

For NER-only scoring against the human annotations, see [NER scores on human annotations](#ner-scores-on-human-annotations) for the exact commands to reproduce the published scores or to score your own NER engine.


## Synthetic data disclaimer

Every dataset in PrivacyBench is **entirely synthetic**. The protagonists, coworkers, companies, emails, Slack handles, and message contents were generated by Tonic [Fabricate](https://www.tonic.ai/) and do not describe real people, organizations, or events. Any resemblance to a real person or company is coincidental. The "PII" the benchmark asks systems to detect and replace is fictional PII embedded in fictional documents; no real personal data is present.

## Intended use

PrivacyBench is intended for **evaluating and benchmarking** PII-synthesis systems — measuring how well a pipeline detects PII and replaces it with coherent synthetic values. The ground truth (spans + character rosters) is the answer key for that evaluation.
