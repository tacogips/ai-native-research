# Workspace DLP拡張版データセット（v3）の検知能力とローカル検査の報告

報告日：2026年11月16日。DLPは機密情報の検知・保護、標準検知器はGoogleが用意した検知の部品、独自検知器は管理者が作る正規表現（文字の並びの規則）と語句一覧を指す。RE2はGoogleの正規表現の方式で、Workspaceの独自検知器はこの構文を使う。

**この報告で実測したのは、独自正規表現を自前のRE2で架空資料に当てた結果だけである。Google Workspace上の標準検知器・独自検知器・分類ラベルの動作は測っていない。** 実環境の測定結果は非公開の台帳に置き、このリポジトリへは載せない。

生成器と検査処理は[`scripts/workspace_dlp_benchmark/extended/`](../../scripts/workspace_dlp_benchmark/extended/README.md)。データセットの設計は[拡張設計](pii_dlp_sensitive_category_dataset_extension_20261116.md)、ラベルの仕様は[分類ラベルの調査](google_drive_classification_labels_20261116.md)を参照。

## 1. 結論

- **標準検知器だけで扱える項目は限られる：** 指定された項目のうち、Workspaceの公開一覧に標準検知器があるのは、個人番号・運転免許証・旅券・銀行口座・カード番号・病名（医療用語）・民族・平文パスワード・弱い一方向変換値・メール・電話・氏名（日本語の動作は未確認）と、職歴・学歴に近い「履歴書」という文書単位の分類である。[W1]
- **正規表現を足せば対象は広がるが、精度は文脈の書き方に強く依存する：** 在留カード、保険証の記号番号、基礎年金番号、資産、年収、勤務先、家族構成、健康診断、障害、信条、社会的身分、犯罪歴・手続・被害は独自検知器で候補を作れる。ローカル検査では、見出しに頼る正規表現が見出しのない文や表を見逃し、空欄の帳票を誤検知した。
- **日本語の語句一覧が使えるかは実環境で最初に確かめる必要がある：** 公式資料は「単語全体だけが一致する」とし、空白で区切らない日本語での扱いを書いていない。[W2] 部分一致なら病名の語句一覧の再現率は100%、単語全体一致なら0%になった。
- **顔・音声・映像は本文検査の対象外である。** 生成もしていない。
- **分類ラベルで「どのグループの個人情報が含まれるか」を付けることは仕様上できる。** 1グループ1ラベルで、単一選択のフィールドに確度を持たせる。

### 独自検知器の制約

| 制約 | 公開仕様 | 設計への影響 |
|---|---|---|
| 正規表現の構文 | RE2 [W2] | 先読み等を使わずに書く。今回の定義はすべてRE2でコンパイルできることを確認した |
| 正規表現の長さ | 1,000文字まで [W3] | 1項目1検知器にまとめ、最長214文字 |
| 規則で使う独自検知器 | 正規表現と語句一覧の合計100まで [W3] | 今回は32 |
| 語句一覧 | 950語・60KBまで、大文字小文字と記号を無視、単語全体だけが一致、各語は英数字2文字以上 [W2,W3] | 日本語の語が「英数字」に数えられるか、単語の区切りをどう判定するかが未記載 |
| 閾値 | 標準検知器には確信度・最小一致数がある。正規表現の条件の閾値は記載がない [W4] | 正規表現は1件一致で発火する前提で書く |
| 近接条件 | 標準検知器が独自正規表現の前後指定文字数以内にあるときだけ一致。有効な規則50件まで [W3,W4] | 「見出し語の近くの番号」は標準検知器と組み合わせる場合だけ作れる |
| 条件の組合せ | AND・OR・NOTの入れ子が可能。1規則の基本条件100まで [W4] | 1グループの検知器をORでまとめられる |

## 3. 分類ラベルによるグループ分け

| グループ | 含める項目 |
|---|---|
| G1 公的番号・本人確認 | 個人番号、運転免許証、旅券、在留カード、保険証、基礎年金、雇用保険 |
| G2 金融・資産 | カード、銀行口座、資産、年収、民間保険 |
| G3 経歴・勤務・家族 | 職歴、学歴、勤務先、家族構成 |
| G4 健康・医療（要配慮） | 病歴・診療、健康診断、障害 |
| G5 要配慮（健康以外） | 人種、信条、社会的身分、犯罪の経歴・手続・被害 |
| G6 認証情報 | 平文パスワード、一方向変換値 |
| G7 連絡先・基本属性 | メール、電話、住所、氏名 |
| G8 生体・音声・映像 | 顔、音声、映像（DLPでは付与しない） |

ラベルは`PII-G1`〜`PII-G7`の7個とし、各ラベルに単一選択のフィールド「検知」（選択肢は上から「確度高」「確度中」）を置く。規則は各グループ2本で計14本にする。

| 規則 | 条件 | 動作 |
|---|---|---|
| `PII-Gn-確度高` | そのグループの標準検知器のOR | ラベル`PII-Gn`の「検知」に「確度高」 |
| `PII-Gn-確度中` | そのグループの独自正規表現・語句一覧のOR | 同じフィールドに「確度中」 |

この形にした理由は次のとおり。

- **DLPが付けられる値は単一選択の選択肢型だけ。** 数値や複数選択は使えない。[W5]
- **同じフィールドで規則が競合すると、選択肢の並びで上位の値が付く。** 標準検知器と独自検知器の両方が一致したファイルには「確度高」が残る。[W5]
- **1つの規則で複数のラベルを付けられるかは公式資料に記載がない。** そのため1規則1ラベルにする。
- **1ファイルに付けられるラベル数に上限はなく、組織のラベルは150個まで。** 7個は余裕がある。
- **付与したラベルを条件に共有を制限する場合は、別の規則にする。** 同じ規則でラベルを条件と動作の両方に使えないため。[W5]

1ラベルに7フィールドを置く案（ラベル数を節約できる）は、別々の規則が同じラベルの別フィールドに値を付けられるかが公式資料に記載がない。実環境で確認できるまでは採らない。計画は`build.py label-plan`で機械可読な形に出力する。

### 4.1 データと方法

| 項目 | 内容 |
|---|---|
| 版 | `v3-extended`。既存の7分類・738資料の比較試験とは別の版 |

### 4.5 見えた失敗の型と改善案

| 失敗の型 | 例 | 改善案 |
|---|---|---|
| 見出しへの依存 | 番号の正規表現が見出しのない文・表で不発 | 番号は標準検知器を主にし、正規表現は標準検知器のない番号に限る。標準検知器と見出し語の近接条件を使う |
| 見出し語だけでの一致 | 「職歴：＿＿＿＿」「前科：****」で誤検知 | 見出しの後に値の文字種（数字、年月、漢字の連続）を必須にする |
| 一般文書の語 | 統計の年収、求人票の入社、法令解説の懲役 | 統計・法令の語（平均、法定刑等）を否定条件として規則に加える |
| 表の区切り | タブ区切りの表で「：」がない | 区切り文字にタブと空白を含める |
| 日本語の氏名 | 見出しのない氏名はほぼ全て見逃し | 標準の`Name occurrence`の日本語での動作を実測する。不可なら本文検査では扱わない |

改善案はまだ反映していない。反映すると同じ評価資料に合わせ込むことになるため、改善後は新しい評価用の値で測り直す。

## 5. 実環境での検査手順

1. 試験用の組織部門で、所有者と規則の適用範囲が一致することを確かめる（[レビュー記録](../../scripts/workspace_dlp_benchmark/REVIEW.md)の検知試験1・2）。
2. `build.py make`で生成した`drive_upload`だけを新しいフォルダーへ置く。正解・計画は置かない。

### 5.1 DLP内部の再検査と、検証側の反復観測

Googleの[公式説明「About DLP for Drive」](https://knowledge.workspace.google.com/admin/security/about-dlp-for-drive)（2026年11月16日確認）は、機微情報の検知を確実にするため、検査処理が同じ文書を2回検査する場合があり、規則変更による影響ファイル数が検査間で変わり得ると説明している。これはDLP内部の自動処理であり、管理者が手動で2回検査する運用の指示ではない。常に2回行うという保証でもない。検査には数時間、1日、またはそれ以上かかる場合がある。

| 区分 | 説明 |
|---|---|
| 確認できた公開仕様 | DLPが文書を2回検査する場合がある。検査間で影響ファイル数が変わり得る。 |
| 確認した公式説明に記載がないこと | 1回目・2回目それぞれの詳細な判定処理、両者の同一性、2回目の実行条件・間隔、乱数を使った判定の有無。 |
| 仮説 | 1回目と2回目で判定処理や入力の抽出方法が異なる可能性は排除できない。ただし、異なることも、その可能性が高いことも、この説明からは判断できない。 |
| 結果の解釈 | 影響ファイル数の変化だけでは、同一文書・同一条件で判定が確率的に変わった証拠にはならない。 |

検証側で同一内容・同一規則を複数回観測する手順は、この内部再検査とは別の試験設計である。監査記録だけで内部の「1回目」「2回目」と対応付けられるとは仮定しない。ファイルの版・内容の検査値・規則設定・適用範囲・観測時刻を固定または記録し、検査確認済み・処理待ち・確認不能を区別する。無ログを偽陰性や解消へ変換せず、確認できた観測の検知率と結果の一致率を別々に示す。内部処理の違いの特定は、この試験の対象外とする。この反復試験は未実施である。

#### 公開監査項目で分けられる検査モード

2026年11月17日に確認した[規則監査イベントの公式仕様](https://developers.google.com/workspace/admin/reports/v1/appendix/activity/rules)は、`scan_type` を検査モードとして定義している。

| 公開されている値 | 公式仕様の意味 |
|---|---|
| `DRIVE_ONLINE_SCAN` | 変更された単一のDrive項目に対する規則評価 |
| `DRIVE_OFFLINE_SCAN` | 更新された規則をDrive項目全体に対して評価するモード |

観測設計ではこの値を原票のイベントと結び付けて保持し、検査モードごとの検知ファイル集合と、その和集合を別々に集計する。モードから内部の「1回目」「2回目」、両者の判定処理、全対象の検査完了を推定しない。具体的な操作との因果関係も、モード名だけでは確定しない。値がない場合は不明として扱う。

少数の対照資料は、`eventName=content_matched` と `filters=resource_id==<FILE_ID>` によるファイル単位の取得を設計できる。[activities.listの公式仕様](https://developers.google.com/workspace/admin/reports/reference/rest/v1/activities/list)は不正な絞り込み条件が無視される場合を説明しているため、既知の非ゼロ対照と、返却イベントの種類・識別子・顧客・時刻の全件照合を組み合わせる。全ページ取得を要求し、0件を陰性や検査完了へ変換しない。この追記は公開仕様と設計の説明であり、実環境の測定値や既存採点器の対応済み機能を示すものではない。

### 5.3 標準検知器の対応表を明示する

公開された検知器名の候補と、採点に使う定義を分離するため、実行対応表の`standard_detector_map`にリポジトリ外のJSONとSHA-256（内容の変更を検出する検査値）を指定できるようにした。JSONには31項目をすべて記載し、非対応項目は空一覧で表す。指定がなければ既存の公開候補を使う。具体的な形式と手順は[README](../../scripts/workspace_dlp_benchmark/extended/README.md)に示す。

取込み時に表の内容と検査値を保存し、採点時にも読み直して照合する。項目欠損・未知項目・重複・不正な識別子・改変・異なる対応表の混在を拒否する。対応表を受け付けることは、記載した検知器が製品で利用可能だと確認する機能ではない。

この追加は通信を行わない11試験で検証した。既存分を含む218試験がRE2導入環境で成功し、通常の`python3 -m unittest`ではRE2未導入により1件を省略して成功した。実際の監査イベント形式への対応を追加した変更ではない。実環境の識別子・操作記録・結果はこの公開報告の対象外とし、非公開の台帳で管理する。

### 5.4 検査対照の語句一覧を分割する

先頭・末尾の検査対照について、各々を複数の語句一覧検知器へ分割できるようにした。片側の検知器は「いずれかに一致」で結合し、先頭側と末尾側は「両方に一致」で結合する。PII分類の正規表現や正解資料を変更する処理ではない。

各検知器の全文の検査値・顧客・適用範囲・語句の重複・語数と容量を照合し、各資料の対照語が該当側の語句全体に含まれることを確認する。先頭と末尾に同じ検知器を使う設定や、旧単一指定との曖昧な併用は拒否する。対照不足や版が確認できない監査を、確定した陰性へ変更しない。指定形式は[README](../../scripts/workspace_dlp_benchmark/extended/README.md)に記載した。

追加した14試験を含め、RE2導入環境で計232試験が成功した。この結果は合成入力による処理の検証であり、製品の検知精度やAPI登録上限を示さない。

### 5.5 ローカル生成物の再現基準

生成コードだけでなく、全387ファイル（検査対象TXT385件と正解・生成記録JSON2件）の相対パス・サイズ・SHA-256を[`dataset-reference.json`](../../scripts/workspace_dlp_benchmark/extended/dataset-reference.json)へ保存した。`reproduce.py make`で新規生成して固定基準へ照合し、`verify`で保存済みの生成物を再確認できる。ディレクトリ構造、余分なファイル、欠落、内容変更、生成元5ファイルの変更を検出する。改行はLF、文字コードはUTF-8に固定する。手順と正解表の項目は[再生成手順](../../scripts/workspace_dlp_benchmark/extended/README.md#同じデータセットを再生成する)を参照する。

追加4試験で固定基準、全体の再生成、変更検出、生成元の不一致、シンボリックリンク拒否を確認した。`PYTHONHASHSEED`が異なる別プロセス・別保存先でも一致した。Python 3.9.6と3.12のそれぞれで既存分を含む241試験が成功し、RE2未導入のため各1件を省略した。Googleへの通信は行っていない。これは現行コードからのローカル再生成の確認であり、過去の私有保存物の同一性、Google側の検査結果、画像・Office等のLIGHT版の全バイト一致を証明しない。
