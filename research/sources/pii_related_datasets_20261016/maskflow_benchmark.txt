      <h1>Benchmark</h1>
      <p class="lede">The numbers behind every accuracy claim on this site &mdash; per entity, precision and recall, every tool run over the same fixed corpus, reproducible on your own machine with one command. Five corpora are published so far: India, India in tables, international, <code>maskflow scan</code>, and framework-integration parity. Every entity type where a competitor beats us is on the page, not just the ones we win.</p>

      <section class="docs-section" id="summary">
        <h2><a class="heading-anchor" href="#summary" aria-label="Link to Summary">#</a>India &mdash; the short version</h2>
        <span class="benchmark-date">indiapii-v1.0 &middot; run 10 October 2026 &middot; maskflow-pack-india 0.6.0</span>
        <ul>
          <li><strong>Indian identifiers: 98.6% F1.</strong> Across the fifteen structured Indian identifier types &mdash; Aadhaar, PAN, GSTIN, IFSC, UPI VPA, voter ID, driving licence, vehicle registration, passport, ABHA, bank account, PIN code and mobile number &mdash; MaskFlow scores a micro-averaged <strong>98.6% F1</strong> (99.3% precision, 98.0% recall).</li>
          <li><strong>The competition scores zero on most of them.</strong> Stock Presidio detects none of these formats except the mobile number; <code>mask-privacy</code> detects only the mobile number and the bank account. Adding hand-written Aadhaar and PAN recognizers to Presidio lifts it to 96.6% and 100% on those two &mdash; and leaves the other thirteen at zero.</li>
          <li><strong>Names and addresses are hard for everyone.</strong> On free-text person names MaskFlow leads at 52.4% F1 (next best 30.4%). On Indian addresses <code>mask-privacy</code> leads at 50.7% F1; MaskFlow trails at 43.3%. Both figures are low, and we are not hiding either.</li>
          <li><strong>On structured identifiers MaskFlow errs toward silence, not guessing.</strong> Eleven of the fifteen &mdash; GSTIN, IFSC, UPI VPA, PAN, voter ID, driving licence, vehicle registration, passport, PIN code, ABHA address and the masked-Aadhaar form &mdash; score 100% precision and 100% recall. Aadhaar (96.8% precision, 28 checksum-passing look-alikes) and the Indian mobile number (98.0% precision, 36 false positives) are the only structured types that over-fire. ABHA number and bank account have no public checksum, so MaskFlow trades recall for precision there &mdash; 100% precision, ~87% recall.</li>
          <li><strong>Speed is in the same class as Presidio.</strong> About 70&nbsp;ms per KB of text, ~20&nbsp;ms median per document &mdash; a rounding error next to the LLM round-trip it protects.</li>
        </ul>
        <p>Full per-entity tables, both matching modes, and the raw precision/recall/error counts are below. The dataset, the scoring harness and the exact command that produced these numbers are all public.</p>
      </section>

      <section class="docs-section" id="corpus">
        <h2><a class="heading-anchor" href="#corpus" aria-label="Link to Corpus">#</a>What was measured</h2>
        <p>The corpus is <strong>IndiaPII-Bench v1.0</strong> (<code>indiapii-v1.0</code>): 2,000 synthetic documents containing 13,468 labelled entity spans, generated from a fixed random seed so every run scores exactly the same text.</p>
        <p>Documents are spread across seven realistic domains, roughly 285 each:</p>
        <ul>
          <li>bank chat transcripts</li>
          <li>HR records</li>
          <li>insurance claims</li>
          <li>KYC forms</li>
          <li>loan applications</li>
          <li>medical notes</li>
          <li>support tickets</li>
        </ul>
        <p><strong>Every identifier is synthetic and valid.</strong> Aadhaar numbers pass the Verhoeff checksum, GSTINs pass the GST check digit, and PAN, IFSC, UPI VPA and the rest are format-valid &mdash; each value is generated at random and then cross-checked against the pack's own validators before it goes into the corpus. None of these identifiers belong to a real person, business or account.</p>
        <p><strong>The corpus fights back.</strong> Alongside the real spans it plants hard negatives &mdash; strings that look like an identifier but are not one: an order ID shaped like an Aadhaar number, an invoice number shaped like a PAN, a timestamp shaped like a long number, an e-mail address shaped like a UPI VPA. A detector that fires on one of these loses precision, exactly as it would in production.</p>
      </section>

      <section class="docs-section" id="scoring">
        <h2><a class="heading-anchor" href="#scoring" aria-label="Link to Scoring">#</a>How results are scored</h2>
        <p>Ground truth is labelled <strong>per entity span, not per document</strong>. A document with nine correct matches and one miss scores as nine out of ten, not as a failure.</p>
        <p>For each entity type and each tool the harness counts true positives, false positives and false negatives, then reports:</p>
        <ul>
          <li><strong>Precision</strong> &mdash; of the spans the tool flagged, the share that were real.</li>
          <li><strong>Recall</strong> &mdash; of the real spans, the share the tool found.</li>
          <li><strong>F1</strong> &mdash; the harmonic mean of the two, which is the single number shown in the comparison tables.</li>
        </ul>
        <p>Two matching modes are computed from the same predictions:</p>
        <ul>
          <li><strong>Strict span</strong> &mdash; a prediction counts only if its start and end offsets match the gold span exactly.</li>
          <li><strong>Partial overlap</strong> &mdash; a prediction counts if it overlaps the gold span of the same type at all.</li>
        </ul>
        <p>For single-token identifiers the two modes give identical results, because there is only one correct way to bound the match. They diverge only for multi-token spans &mdash; person names and addresses &mdash; where &ldquo;<em>21, MG Road, Indiranagar, Bengaluru 560038</em>&rdquo; and &ldquo;<em>MG Road, Indiranagar</em>&rdquo; are both arguably the address. The comparison table below reports partial-overlap F1; the strict figures are in <a href="#full-data">the full-data tables</a>.</p>
        <p><strong>Label mapping is deliberate and documented.</strong> Each tool emits its own label names; the harness maps them to a shared taxonomy (Presidio's <code>PERSON</code> &rarr; <code>PERSON_NAME</code>, <code>PHONE_NUMBER</code> &rarr; <code>INDIAN_MOBILE</code>, <code>LOCATION</code> &rarr; <code>INDIAN_ADDRESS</code>, and so on). A prediction for a type outside this corpus's taxonomy is dropped before scoring rather than counted against the tool &mdash; no tool is penalised for detecting something the corpus does not label.</p>
      </section>

        <h3>Structured Indian identifiers</h3>
        <p>This is the gap MaskFlow was built to close, and the table shows why the gap is real rather than rhetorical. General-purpose PII tools were built for US and EU data, where a nine-digit number is a Social Security Number and an Aadhaar is noise. They ship no recognizer for Aadhaar, PAN, GSTIN, IFSC, UPI, ABHA, voter ID, the Indian passport format, the RTO-coded driving licence and vehicle registration formats, or the Indian bank-account and PIN-code conventions &mdash; so they score zero on all of them.</p>
        <p>The <code>Presidio + custom</code> result is the honest test of the &ldquo;you can just add a regex&rdquo; objection. Two carefully written recognizers get Aadhaar to 96.6% and PAN to 100% &mdash; genuinely useful &mdash; but the remaining thirteen types still need thirteen more recognizers, each with its own checksum, context rules, bundled reference list (RBI bank codes, NPCI handles, RTO codes) and hard-negative handling. That is the pack, not a snippet.</p>
        <p>MaskFlow's one visible miss here is Aadhaar precision: 28 false positives against 857 true matches (96.8% precision, 100% recall). These are Aadhaar-shaped strings that pass the Verhoeff checksum by chance and appear without disambiguating context. ABHA number and bank account sit at ~93% F1 because neither format has a public checksum, so MaskFlow requires nearby context (&ldquo;ABHA&rdquo;, &ldquo;account&rdquo;, &ldquo;a/c&rdquo;) before it will mask &mdash; trading a little recall for near-zero false positives on ordinary long numbers.</p>

        <h3 id="names-addresses">Person names and addresses</h3>
        <p>These two types are detected by pattern, gazetteer and context matching, not by a checksum, so both false positives and false negatives are unavoidable &mdash; for every tool. The numbers are low across the board and should be read that way.</p>
        <p>On <strong>person names</strong> MaskFlow leads (52.4% partial F1 vs. 30.4% for both <code>mask-privacy</code> and Presidio), helped by an Indian-name gazetteer, honorific and S/o&ndash;D/o patterns, and agreement scoring with the spaCy NER pass.</p>
        <p>On <strong>Indian addresses</strong> <code>mask-privacy</code> leads at 50.7% and MaskFlow trails at 43.3%. Our address gazetteer covers 554 Indian cities and places but still misses smaller localities, and the structural patterns over-extend span boundaries. This is a known weak spot and an active area of work; it is on this page precisely because a benchmark you can only cite when you win is marketing.</p>
        <p>One nuance the F1 number hides: under partial-overlap matching MaskFlow's <em>recall</em> on both names and addresses is 100% &mdash; it flags every gold span. The low F1 is entirely a precision problem: it also flags a lot of text that is not a name or an address. For a masking tool that failure mode (over-masking) is far safer than the opposite, but it still degrades the prompt, and closing it is the work.</p>
      </section>

      <section class="docs-section" id="regex-floor">
        <h2><a class="heading-anchor" href="#regex-floor" aria-label="Link to The regex floor">#</a>The regex floor</h2>
        <p>The naive-regex baseline is a useful sanity check on how much the checksums and context rules actually buy. On the same corpus, a regex-only approach scores (strict-span F1):</p>
        <div class="table-wrap">
          <table class="data-table">
            <thead>
              <tr><th>Entity</th><th>naive regex</th><th>MaskFlow</th><th>What the gap is</th></tr>
            </thead>
            <tbody>
              <tr><td>Aadhaar</td><td class="num">54.4%</td><td class="num is-best">98.4%</td><td class="wrap">Verhoeff checksum + hard-negative rejection.</td></tr>

        <p>A plain Aadhaar regex flags roughly twice as many strings as it should, because any twelve digits in the right shape match. The checksum is what turns a 54% score into a 98% one.</p>

      <section class="docs-section" id="caveats">
        <h2><a class="heading-anchor" href="#caveats" aria-label="Link to What this does not tell you">#</a>What this does not tell you</h2>
        <ul>
          <li><strong>The data is synthetic.</strong> It is realistic and adversarial, but it is generated, not sampled from real documents. Real text is messier: OCR noise, inconsistent formatting, code-mixed Hinglish and transliteration. Name and address detection in particular is measurably harder on code-mixed text than these numbers suggest.</li>
          <li><strong>It is a single run in one environment.</strong> Scores are deterministic for a given corpus version and tool version, but a CI regression gate &mdash; not a one-off &mdash; is what keeps them honest over time.</li>
          <li><strong>The LLM-detector baseline is not in yet.</strong> The adapter exists; those columns will be filled in a later revision.</li>
          <li><strong>The masking-versus-output-quality study is separate and still in progress.</strong> &ldquo;Does replacing PII with placeholders degrade the model's answer&rdquo; is a real question with its own measurement, including realistic surrogate values that preserve output quality better than bare tokens. It is not part of these detection numbers.</li>
          <li><strong>Detection accuracy is not compliance.</strong> A high F1 reduces exposure and produces evidence. It does not, on its own, make any system compliant with the DPDP Act or any other regulation.</li>
        </ul>
      </section>

      <section class="docs-section" id="tabular">
        <h2><a class="heading-anchor" href="#tabular" aria-label="Link to Tables">#</a>India in tables &mdash; the short version</h2>
        <span class="benchmark-date">indiapii-tabular-v1.0 &middot; run 14 October 2026 &middot; maskflow-core 0.8.3, maskflow-pack-india 0.6.1</span>
        <p>The prose corpus above doesn't measure the shape a coding agent or an analyst actually handles: query output and exports. This one does &mdash; 300 synthetic tables (50 each of CSV, TSV, <code>psql</code>, <code>mysql</code>, <code>sqlite3 -header</code> and markdown), 3 to 120 rows, 26,062 gold spans, CC-BY-4.0, one fixed seed. Mobiles, Aadhaar and account numbers are written bare, the way a database stores them, so the only thing saying what a value is sits in the column header, often far above it. Tables also carry look-alike <strong>decoy columns</strong> (<code>order_id</code>, <code>account_id</code>, <code>mobile_app_build</code>, <code>test_mobile</code>&hellip;) whose values are PII-shaped but aren't PII; anything masked there counts as a false positive.</p>
        <ul>
          <li><strong>Column-header context took recall from 60.9% to 99.1%.</strong> Before <code>maskflow-core</code> 0.8.3, a bare value with no checksum needed a keyword within 40 characters, and in a table that keyword was the header. Indian mobile recall went from 0.3% to 100%, PIN code from 0.4% to 100%, bank account from 0.4% to 92.5%.</li>
          <li><strong>False positives went down, not up</strong> &mdash; 220 to 153 across all 26,062 spans. Despite decoy columns built to look exactly like them, there are only 3 false mobile numbers and 5 false bank accounts; most of the rest are person names (102).</li>
          <li><strong>Prose is unchanged.</strong> IndiaPII-v1.0 scores are identical for every entity, strict and partial.</li>
          <li><strong>Bank account is the gap, and we know why.</strong> A random 12&ndash;18 digit account number sometimes passes the Luhn or Verhoeff checksum, and a checksum-validated match always wins, so the cell is masked as a credit card or an Aadhaar number instead. It is still masked, but it counts as a bank-account miss &mdash; that is most of the 7.5-point recall gap and most of Aadhaar's 43 false positives.</li>
        </ul>
        <p>No competitor columns here: this corpus measures a MaskFlow capability before and after a change, not a head-to-head. Strict and partial-overlap scores are identical.</p>

      <section class="docs-section" id="scan">
        <h2><a class="heading-anchor" href="#scan" aria-label="Link to Scan">#</a>Scan accuracy &mdash; the short version</h2>
        <span class="benchmark-date">scan-log-v1.0 &middot; run 10 September 2026</span>
        <p><code>maskflow scan</code> is a retrospective auditor, not a live masking gate, so its benchmark asks a different question: over 2,000 synthetic log-shaped records &mdash; nginx access lines, JSON app logs, stack traces, LLM request dumps, worker-task logs, 400 each &mdash; how many false positives does it surface per 1,000 records, next to realistic log-noise hard negatives (request IDs, UUIDs, git SHAs, epoch timestamps, internal IPs, base64 blobs, stack-trace frames)? 6,542 gold PII spans, 6,122 decoy spans, CC-BY-4.0, fixed seed. Two MaskFlow modes are scored &mdash; <code>--deep</code> (full NER pass) and the fast patterns-only pass &mdash; next to stock Presidio and naive regex.</p>
        <ul>
          <li><strong>Checksum-validated identifiers are close to perfect on log noise.</strong> Aadhaar, PAN, GSTIN, IFSC, UPI VPA and the Indian mobile number all score 100% F1 for both MaskFlow modes; a naive Aadhaar regex, with no checksum, flags 337 hard-negative order/reference IDs that happen to be twelve digits.</li>
          <li><strong>Headline precision: 88.4% (<code>--deep</code>) / 91.6% (patterns-only)</strong> &mdash; 428 and 298 false positives per 1,000 records respectively, against Presidio's 544 and naive regex's 433. Patterns-only beats <code>--deep</code> on this metric because the NER pass is the main source of the extra noise.</li>
          <li><strong>Almost all of it is two labels.</strong> Of <code>--deep</code>'s false positives, 438 are person names (the NER pass firing on log text &mdash; user agents, class names, stack-trace tokens) and 400 are internal IP addresses (<code>10.*</code>, <code>172.16.*</code>, <code>192.168.*</code>) that MaskFlow has no private-range suppression for yet, so every one of the 400 in the corpus is flagged. Patterns-only avoids the NER noise entirely: 178 person-name false positives instead of 438, about 2.5&times; fewer.</li>
          <li><strong>The pipeline is verified lossless.</strong> A separate plumbing check runs the real <code>scan.pipeline.run_pipeline(--deep)</code> over all 2,000 records and asserts its aggregated counts equal <code>detect()</code>'s directly &mdash; <strong>PASS</strong>, 7,396 findings across 13 entity types, so the streaming field-extraction and aggregation layer between the CLI and the detection engine loses nothing.</li>

      <section class="docs-section" id="integration-parity">
        <h2><a class="heading-anchor" href="#integration-parity" aria-label="Link to Integration parity">#</a>Integration parity &mdash; the short version</h2>
        <span class="benchmark-date">integration-parity-v1 &middot; run 10 September 2026</span>
        <p>The four framework integrations &mdash; <code>maskflow-litellm</code>, <code>maskflow-langchain</code>, <code>maskflow-llamaindex</code>, <code>maskflow-mcp</code> &mdash; aren't a second detection engine; each wraps the same core <code>maskflow.mask()</code> / <code>maskflow.unmask()</code>. This benchmark checks that wrapping doesn't lose anything. It routes 300 documents from <code>indiapii-v1.0</code> through each integration's masking layer and asserts, per document, that:</p>
        <ul>
          <li><strong>Detection parity</strong> &mdash; the <code>(entity_type, value)</code> set the wrapper masks equals what the core engine's <code>mask()</code> would produce on the same text.</li>
          <li><strong>Round-trip</strong> &mdash; the wrapper's own <code>unmask()</code> restores the document byte-exact.</li>
          <li><strong>Streaming</strong> &mdash; the masked text, fed back through the shared <code>StreamingUnmasker</code> split at 1-byte and random chunk boundaries, reassembles byte-exact.</li>
        </ul>
        <p>Every column should read 100% &mdash; a divergence anywhere is a wrapper bug, not a tolerance to manage. It did, across all four:</p>
        <div class="table-wrap">
          <table class="data-table">
            <thead>
              <tr><th>Integration</th><th>Detection parity</th><th>Round-trip</th><th>Streaming</th><th>Divergences</th></tr>

              <tr><td>maskflow-langchain</td><td class="num is-best">100%</td><td class="num is-best">100%</td><td class="num is-best">100%</td><td class="is-none">&mdash;</td></tr>
              <tr><td>maskflow-llamaindex</td><td class="num is-best">100%</td><td class="num is-best">100%</td><td class="num is-best">100%</td><td class="is-none">&mdash;</td></tr>
              <tr><td>maskflow-mcp</td><td class="num is-best">100%</td><td class="num is-best">100%</td><td class="num is-best">100%</td><td class="is-none">&mdash;</td></tr>

        <p>This is an equality gate, not a leaderboard &mdash; there's no baseline file to regress against, just a CI job (<code>integration-parity</code>) that runs on every pull request. A deliberately broken run is included in the test suite to prove the gate actually fails when parity breaks, rather than passing trivially.</p>
        <p><strong>A fifth item, JS&harr;Python cross-language parity, was scoped and dropped.</strong> <code>@maskflow/detection</code>, the browser/Node TypeScript port, already shares its test fixtures with the Python suite and is a deliberately narrow client-side helper &mdash; not a second full engine. A separate published parity corpus for it wasn't judged worth the added Node CI surface right now; it can be reopened if that changes.</p>

      <section class="docs-section" id="llm-quality">
        <h2><a class="heading-anchor" href="#llm-quality" aria-label="Link to LLM quality">#</a>LLM quality &mdash; instrumented, results pending</h2>
        <p>&ldquo;Does replacing PII with placeholders degrade the model's answer&rdquo; is a real question with its own measurement, separate from detection F1. It's the one item on this page with no number yet &mdash; said plainly, rather than left as a silent gap.</p>
        <p><strong>What's built:</strong> a 200-task LLM-utility benchmark that records its task-model and judge-model IDs directly in <code>results.json</code> / <code>results.md</code>, with <code>--task-model</code>, <code>--judge-model</code> and <code>--sample-per-type</code> flags, and <code>make quality-bench</code> / <code>make quality-bench-smoke</code> targets. The method is documented in the repo README.</p>
        <p><strong>Status:</strong> results pending. The run uses the Anthropic API directly; a backend using the <code>claude</code> CLI was prototyped and rejected, because the CLI self-redacts PII on its own, so the task model emits <code>&lt;PERSON_NAME_1&gt;</code>-style tokens even in the <em>unmasked</em> condition, which corrupts the leak-rate metric the benchmark exists to measure.</p>
        <p>Once it runs, the masked-condition leak rate is checked against 0 and <code>bench/reports/indiapii-quality-v1.0/results.md</code> is linked here. Tracked on <a href="https://github.com/maskflow/maskflow/issues/92" target="_blank" rel="noopener">the umbrella issue</a> and in the project CHANGELOG.</p>
      </section>

      <section class="docs-section" id="my-data">
        <h2><a class="heading-anchor" href="#my-data" aria-label="Link to Score it on your own data">#</a>Score it on your own data</h2>
        <p>Every number on this page is measured on a synthetic corpus &mdash; necessary for a reproducible, shareable benchmark, but still someone else's documents. <code>maskflow bench --my-data &lt;path&gt;</code> runs the same strict-span / partial-overlap scoring MaskFlow uses internally against <strong>your own</strong> labelled JSONL file and prints per-entity precision, recall and F1, so &ldquo;is it accurate on my documents?&rdquo; has a command, not just an argument. It scores MaskFlow only &mdash; not the multi-tool comparison above.</p>
        <div class="code-block">
          <div class="code-block-bar">
            <span class="code-block-title">shell</span>
          </div>
          <pre><code>pip install "maskflow-cli[bench]"
maskflow bench --my-data yourdata.jsonl --out results/</code></pre>
        </div>
        <p>One JSON object per line &mdash; <code>{"text": "...", "entities": [{"start": 22, "end": 32, "label": "PAN"}]}</code>. Label something that only looks like PII with <code>"value_class": "hard_negative"</code> so MaskFlow correctly ignoring it doesn't cost recall &mdash; only a false hit on it costs precision. Full schema and output format in <a href="https://github.com/maskflow/maskflow/blob/main/docs/bench.md" target="_blank" rel="noopener"><code>docs/bench.md</code></a>.</p>
        <p>Shipped in <code>maskflow-cli</code> 0.8.0, backed by the new <a href="https://pypi.org/project/maskflow-bench/" target="_blank" rel="noopener"><code>maskflow-bench</code> 0.1.0</a> package. Both are opt-in &mdash; <code>bench</code> only installs with the <code>[bench]</code> extra, the same policy as <code>[s3]</code>/<code>[postgres]</code>/<code>[evidence]</code>, so a bare <code>maskflow-cli</code> install stays light.</p>
      </section>
