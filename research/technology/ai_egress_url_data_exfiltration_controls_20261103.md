# AIが未許可のURLへデータを送らないための通信隔離

確認日：2026年11月3日。対象は、コード・コマンド・ブラウザ・外部の道具を使うAIの送信制御。公式文書・公開された安全設計資料に基づく調査であり、実機の通信遮断、侵入耐性、性能は未検証。提供者が説明する機能と、本稿の構成案・試験案を区別する。[実行環境の比較](ai_execution_sandbox_selection_20261027.md)の追加調査である。

2026年11月4日追記：[Compose・eBPF・代替技術と公開実例](ai_container_ebpf_alternatives_and_examples_20261104.md)に、nftables・AppArmor・SELinux・Landlock・seccompとの比較、LLM推論、Bloombergの導入報告等を追加した。

**推奨する出発点は、AIの実行環境からの外向き通信を原則拒否し、外側の代理部だけが、許可された相手・操作・データを送信する構成である。** URLの危険度判定やドメインの許可一覧は補助になるが、許可済みサービス上の攻撃者の保存先、DNS、転送、任意の入力欄を通じた持出しは別に制御する必要がある。これは以下の公開仕様と制限事項から導く本調査の設計案である。

## 1. 防ぎたい対象を明確にする

本稿の「不正なURL」は、既知の悪意あるサイトだけでなく、**その利用者・作業・データについて送信が認められていない宛先**を含む。信用できるサービスでも、別の会社の保存領域や攻撃者の受信口は許可対象にしない。

脅威は、外部文書やWebページに埋め込まれた指示にAIが従う場合と、AIが内部で任意のプログラムを実行する場合の両方を想定する。外部情報の指示によって意図しない操作を起こさせる手法は、prompt injection（入力への不正な指示の混入）と呼ばれる。OWASPも、外部情報を読むAIからの情報持出しや未承認API操作を問題にしている。[S1]

| 達成したい性質 | 必要な制約 | それだけでは残る問題 |
|---|---|---|
| 未許可の送信先に到達しない | すべて拒否を基準に、外側で通信先を限定 | 許可先へ機密を送ることは可能 |
| 許可先でも別の利用者・保存先へ送らない | 組織、受信者、保存領域、対象資源、操作を認可 | 同じ対象内の自由入力欄へ埋め込める場合がある |
| 機密データを外部へ一切送らない | 機密を読める処理と、外部へ送れる処理を分離。外部への出力を制限 | 人への回答、ログ、成果物の取り込みも別の搬出経路 |

この表は本調査の整理。悪意あるURLの拒否一覧を更新するだけでは、未知の宛先を禁止できない。送信の可否は、URLの評判ではなく、業務上の認可を基準に決める。

## 2. 制御する粒度とHTTPSの限界

| 制御する対象 | 分かる・制限できること | 足りないもの |
|---|---|---|
| IPとポート | 接続できる機械・接続口 | 同じIPを共有する複数のサービスや、URL内のパスは区別できない |
| DNS名 | 名前解決の対象と、名前に対応するIP | URLの内容や、サービス内の受信者は分からない |
| HTTPの`Host`、TLSの`SNI` | 通信に含まれる宛先名。SNIは暗号化通信の開始時に示す名前 | 暗号化されたパス・本文の検査にはならない。実際の宛先との整合確認も必要 |
| URL・HTTP操作 | 宛先名、ポート、パス、問い合わせ部分、`GET`・`POST`等 | 許可したAPIの対象組織・保存先や、本文の意味まで決まるわけではない |
| 業務操作とデータ | 「この組織のこの保存先へ、この項目だけ送る」 | 個別のAPI設計・認可が必要。自由形式の出力を許すほど保証は難しくなる |

表は本調査の整理。AWS Network Firewallのドメイン規則はHTTPSでSNI、HTTPでHostを使い、宛先IPをDNSで照合する仕組みではない。公式文書も、それらが操作された場合を考慮したIP規則の併用を説明する。[S2]

HTTPSのパス・ヘッダーを検査するには、代理部で暗号化通信を終端して検査するか、代理部自身がHTTP要求を生成する必要がある。Google Cloud Secure Web Proxyは、TLS inspection（暗号化通信をいったん復号して検査する機能）によるURL全体の可視化を説明している。[S3] ただし、URLの検査機能があることを、本文の機密判定や業務認可まで提供するという意味には広げない。

## 3. 推奨構成：直接通信を閉じて、限定した操作を外に出す

以下は製品固有の設定ではなく、本調査の構成案である。

1. **外側の管理部が作業を確定する。** 利用者、対象データ、許可する送信先と操作、期限、転送量を決める。AIに制約を追加・解除する管理権限を渡さない。
2. **実行環境からインターネットと社内ネットワークへの直接経路を閉じる。** 通信制約は、AIが管理者権限を持つ内部OSの外で強制する。子プロセスや任意の通信ライブラリにも適用する。
3. **必要な操作だけを外部の代理部へ依頼する。** 例えば`send_report(report_id, destination_id)`のように対象を識別子で指定し、URL、パス、受信組織は管理側の登録情報から生成する。AIが任意のURLと本文を渡せる汎用中継にはしない。
4. **代理部が対象とデータを認可する。** 作業の本人性を検証し、送信先組織、操作、項目、容量を確認する。認証情報は外側で保管し、その操作に必要な権限だけを使う。
5. **送信直前の内容と認可を結び付ける。** 承認が必要な場合は、宛先、操作、本文・添付、期限に承認を対応させる。承認後に内容が変われば再確認する。AIが指定する「承認済み」という値を信用しない。
6. **実際の送信結果を外側に記録する。** 許可・拒否、適用した規則の版、宛先の識別子、操作、データ区分、量、作業との対応を記録する。URLの問い合わせ部分、本文、認証ヘッダーを無加工で保存して、監査先を新たな漏えい先にしない。

`HTTP_PROXY`・`HTTPS_PROXY`という環境変数を設定するだけでは、任意のプログラムによる直接接続を禁止できない。ネットワーク側で直接経路を閉じ、代理部の障害時にも直接接続へ戻さない構成とする。

### 二つの使い方を分ける

**Webの調査用処理**には、公開情報だけを渡す。外部の任意ページを取得する機能が必要なら、機密ファイル、社内の検索結果、認証済みブラウザの状態を同じ処理へ渡さない。

**機密を扱う処理**は直接通信を閉じ、必要な公開資料を管理側から取り込み、成果物を外側で確認する。両者を連携する際も、機密を含む検索語を公開Web検索へ渡さないよう確認する。単に二つのプロセスに分け、自由な本文を相互転送するだけでは分離にならない。

これは本調査の提案である。機密を読めるAIに、任意の相手へ任意の文字列を送る機能を同時に与えたまま、「情報を絶対に流出させない」とは扱わない。

## 4. 送信先検査で塞ぐべき経路

以下はSSRF（サーバー側の通信機能を悪用して意図しない先へ接続する攻撃）への対策も参考にした設計上の確認点。OWASPは、許可先を基に要求を組み立てること、自動転送を無効にすること、IPv4・IPv6の検査、検証したIPへの接続の固定を説明する。[S4]

| 経路 | 推奨する制約・試験の観点 |
|---|---|
| URLの解釈差 | 標準の解析器を使い、方式・ホスト・ポートを明示する。利用者情報部分、曖昧な表記、検査側と接続側の解釈不一致は拒否。文字列の前方一致だけで判定しない |
| 転送先の変更 | 自動転送を原則禁止。必要なら各段階で宛先・操作を再認可し、別の宛先へ認証ヘッダーや本文を転送しない |
| DNSの回答変更 | 外側で名前解決し、検証したアドレスへ接続。接続前に別の回答へ変わる問題を防ぐ。内部IP・ループバック・リンクローカル・機械情報の取得先は原則禁止 |
| DNS問い合わせ自体での持出し | 内部から任意の名前を問い合わせさせない。管理された名前解決だけを許し、可能なら必要な名前は代理部だけが解決する |
| DNS over HTTPS / TLS | HTTPSやTLSに名前解決を載せる経路も、一般通信と同じく既定拒否。単に53番ポートを閉じるだけでは済まない |
| IPv6・UDP・QUIC・別ポート | IPv4のTCPだけを制限して完了としない。不要な方式は閉じ、使う方式は別途試験。QUICはUDPを使う通信方式でHTTP/3等の基盤 |
| SNI・Hostと実際の宛先の食違い | 代理部が宛先名・接続先・サーバー証明書を検証する。検査できない暗号化方式を無検査で通さない |
| 同じサービスの別保存先 | 汎用のクラウド保存・コード共有・メッセージサービス全体を許可しない。組織・受信者・保存領域・操作まで固定する |
| `GET`による持出し | 検索語、パス、問い合わせ部分、ヘッダーも送信データとして扱う。読取り操作の許可だけでは情報持出しを防げない |
| 長時間の接続 | WebSocket、汎用の`CONNECT`接続、既存の通信経路にも制限。規則変更・取消し時に継続中の接続をどう終了させるか確認 |

TLSを終端する代理部は平文を扱う新たな信頼対象になる。専用の認証局の秘密鍵、復号後のデータ、ログのアクセスを制限する。証明書を固定している通信等が失敗した際に、証明書検証を全体で無効にしたり、検査なしの例外を広げたりしない。

## 5. 製品・基盤ごとの確認結果

### E2B：DNSと代理部を通らない通信を確認する

現行の公式文書では、外向き通信は初期設定で有効。ドメイン許可時にはDNSサーバーとして`8.8.8.8`が自動許可され、そのIPへの許可はDNSだけに限定されない。`dnsServers: []`でDNSサーバーの許可をなくせる。また、共有配信・保存基盤では、許可したホスト名から別の宛先に到達する場合があるという注意がある。[S5]

Bring your own proxy（利用者が用意する代理部、BYOP）はホスト側でTCPを中継し、代理部の障害時は直接接続へ戻さない。一方、UDPのDNSやQUICはその中継の対象外。通信設定の更新は全体置換であり、`egressProxy`を省略すると代理設定が解除される。Cloud等と公開実装による自社運用では対応も異なる。[S6]

**選定上の提案：** DNS・UDPを別途閉じ、設定更新は承認済みの全項目を毎回適用する。SOCKS5というTCP中継方式だけで、HTTPSのパス・本文を検査できるとは扱わない。代理部で何を実際に検査できるかを確認する。

### Modal：ドメイン許可とDNSの制限は別

`block_network=True`による外向き全遮断と、IP範囲・ドメインの許可を区別する。公式資料には、全遮断以外ではDNSが無制限であるという注意がある。IP範囲とドメインの許可は、どちらかに合えば許可される。追加コンテナ経由のHTTPS中継では、443番の制御が追加コンテナ側へ置き換わる条件もある。[S7]

**選定上の提案：** ドメイン制限だけでDNSによる持出しを防げると判断しない。高機密処理は全遮断から検討し、必要な外部操作は管理側の道具へ移す。

### Docker Sandboxes：ローカル版の実効規則を確認する

現行のローカル版の説明では、外向きTCPは明示許可が必要で、UDPは初期設定で無効、ICMPは遮断。DNSも内部の名前解決機構で通信規則を適用すると説明する。機械ごと・組織ごとの設定があるため、`sbx policy ls`等で有効な規則を確認する。クラウド版へ同じ初期設定を適用しない。[S8]

**選定上の提案：** 開発道具が追加した広い許可や、組織・ローカル規則の合成結果も確認する。ドメイン許可から業務データの送信先制限へ進むには、別途操作の認可が必要。

### Kubernetes / Cilium：通信制約を実装する部品

標準のNetworkPolicyは通信規則を実装するネットワーク拡張が必要で、複数の許可規則は加算される。全拒否の規則を置いても、別の広い許可があれば到達範囲が広がる。`hostNetwork`やTCP・UDP・SCTP以外の方式、適用タイミングにも注意がある。[S9]

CiliumはDNS名とIPの対応を管理し、DNS・ポート・HTTPの規則を組み合わせる方法を説明する。[S10] ただしHTTPS本文の機密判定やサービス内の受信者認可まで、DNS制御から自動的に得られるとはしない。

**選定上の提案：** 許可された外部代理部への経路だけを作り、AIへPod作成権限、ホストの通信機能、規則変更権限を渡さない。制限の適用を確かめる前に機密データやAI処理を開始しない。

### Google Cloud / AWS：URLと保存先の境界を組み合わせる

Google Cloud Secure Web Proxyでは、TLS検査によるパス・ヘッダーの確認に加え、HTTP操作を条件とした制御を説明する。これを任意の本文検査機能と同一視しない。[S3][S11]

AWS Network FirewallのSNI・Hostによる規則は、暗号化されたURL全体を検査する機能とは異なる。[S2] S3等の保存サービスは、サービスへの通信許可だけでなく、VPC endpoint policy（私設の接続口で対象資源等を制約する規則）を使って送信先の保存領域を制限する考え方がある。[S12]

Google Cloud VPC Service Controlsも、対象サービスの境界外へのデータ移動を制限するが、一般のインターネット上の第三者サービスを遮断する機能ではない。[S13] どちらも、外向き通信の制約と組み合わせる。

## 6. URL制限の外に残る搬出経路

以下は本調査の設計上の分析である。

- **モデルの入力：** 隔離環境内で読んだデータを外部の推論APIへ送れば、実行環境の通信先を限定していても送信は発生する。モデルの接続も管理側で認可する。
- **外部の道具：** 別プロセスや別サーバーの道具が送信する場合、隔離環境だけの制約は届かない。MCP等の道具接続、検索、メール、ブラウザそれぞれの実行場所を確認する。
- **画面と自動取得：** AIの回答に画像・リンクを埋め込み、閲覧側が自動取得する経路がある。機密を含む回答では外部画像、自動プレビュー、任意URLの自動取得を制限する。
- **参照元情報：** ブラウザの`Referer`ヘッダーにも注意する。`Referrer-Policy: no-referrer`はその送信を抑えるが、アクセス先のURL自体へ情報を入れる持出しは止めない。[S14]
- **共有ファイルと成果物：** AIが設定や自動実行スクリプトを変更し、人がホストで実行したときに送信する場合がある。取り込む前に確認し、実行する場所にも制約を適用する。
- **正規の出力：** 許可した本文・ファイル名・ログ等に情報を符号化する経路は、URL検査では区別しにくい。構造を固定した必要最小限の出力へ絞り、自由な文章の搬出は別の認可対象にする。

機密情報の検出器やAIによる送信前判定は追加防御になるが、言い換え・分割・符号化まで漏れなく判定できるとする検証は本調査では行っていない。転送量の上限も被害を抑える補助であり、秘密値が少量なら上限内でも漏れる。

## 7. 受入試験と合格条件

以下は**未実施の試験案**。管理下の受信機・名前解決環境と、試験ごとに異なる架空の識別文字列を使う。実データや実際の認証情報は使わない。

| 試験 | 合格条件・確認する証拠 |
|---|---|
| 未許可URL、直接IP、別ポート、IPv6での送信 | 受信側に到達しない。管理側に適用規則と拒否理由が残る |
| プロキシ環境変数の解除、別の通信ライブラリ・子プロセス | 直接通信へ切り替えられず、同じ制限が働く |
| 任意DNS名への問い合わせ、外部DNS、DNS over HTTPS / TLS | 管理外の問い合わせが届かず、問い合わせ名で架空データを搬出できない |
| UDP・QUIC、汎用中継、長時間接続 | 未許可方式は到達しない。許可した接続にも対象・時間・量の制約がある |
| 許可URLから別の宛先・内部IPへの転送 | 転送を拒否、または各段階で再認可。本文・認証情報も転送しない |
| 名前解決の回答変更、IPv4とIPv6の混在 | 検証したアドレスへだけ接続し、内部の管理口へ到達しない |
| SNI・Host・接続先の不整合、未対応の暗号化方式 | 宛先を十分に検査できない通信を拒否する |
| 許可済みサービスの別組織・別保存先・公開投稿先 | サービスへの接続が通っても、未認可の保存先への操作は拒否 |
| `GET`の問い合わせ・パス、ヘッダー、添付への埋込み | 固定した要求形式・許可したデータ項目以外は搬出しない |
| 代理部の停止、DNS障害、証明書エラー、設定取得失敗 | 処理を止め、直接通信や無検査へ戻らない |
| 規則更新、停止・再開、設定項目の省略 | DNS・代理設定を含む制約が維持される。変更を検出できる |
| 作業取消しと権限失効 | 新規要求を拒否し、既存接続・待機中の送信を定めた時間内に停止 |
| 並行する別利用者・別作業の依頼 | 他人の送信権限や承認を再利用できない |
| 回答内の外部画像、検索、別サーバーの道具、監査出力 | 実行環境以外の経路でも架空データが未認可先へ届かない |
| 正規の許可操作 | 想定した受信者に、認可した内容だけが届く。全通信を止めただけの合格にしない |

遮断の判定には、受信側のHTTP記録・DNS記録と、代理部・基盤の記録を突き合わせる。接続の成功・失敗やAIの自己申告だけでは判定しない。E2Bも、遮断された宛先へのTCP接続が内部からは成功したように見える場合を説明している。[S5]

これらの試験に通っても、任意の将来の攻撃に対する情報非流出の証明にはならない。試験した構成・規則・製品版・適用範囲を記録し、変更時は影響する試験を再実施する。

## 8. 導入案の選び分け

| 要件 | 構成案 | 残る条件 |
|---|---|---|
| 外部送信が不要 | 実行環境の外向き通信を全遮断。データ投入と成果物搬出を管理側で実施 | 成果物、画面、ログ、モデル入力も管理する |
| 決まったAPIへの送信だけ必要 | 全遮断＋管理側の限定した業務操作 | 任意URL・本文を受け付けず、対象・内容を外側で認可 |
| 多数の既知のWebサイトが必要 | 外側のHTTP代理部＋限定したURL・操作＋DNS・別方式の遮断 | TLS検査の互換性、許可サイト内の持出し、自由な検索語を確認 |
| 自由なWeb閲覧と高機密処理が両方必要 | 公開情報を扱う処理と、機密を扱う処理を分け、間の搬出を認可 | 同じブラウザ状態・ファイル・自由文を無制限に共有しない |

最初に試すべき構成は、必要な通信を列挙できる業務を一つ選び、全拒否から限定した操作だけを開ける方式である。既知の悪意あるURLだけを閉じる運用から始めると、送信してよい範囲を定義できないままになる。
