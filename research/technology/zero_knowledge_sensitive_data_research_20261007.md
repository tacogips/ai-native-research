# ゼロ知識証明と機密データ：AI以外も含む研究・実装・公的事例

調査日：2026年10月7日。公開一次資料の本文、論文、標準草案、公開コードの固定版を確認した。目的は「原本を相手へ渡さずに、条件・処理結果を確認させる」ことと、「分類するAIにも平文を見せない」ことの関係を明確にすること。

## 1. 関係はある。ただし隠す相手が違う

**ゼロ知識証明（ZKP：Zero-Knowledge Proof）は、秘密の情報を開示せず、所定の条件を満たすことを相手に検証させる技術**。例えば、本人確認機関の署名付き情報を使い、生年月日をサイトへ渡さず「18歳以上」を証明する。ゼロ知識とは、公開される条件・結果を超えて秘密を学ばせないという暗号学的性質であり、結果そのものを隠す意味ではない。[NISTの技術分類](https://csrc.nist.gov/Projects/pec/pec-tools)。

通常、証明を作る側は秘密の入力を持つ。**証明を確認する相手に平文を見せないことと、入力から計算するAIに平文を見せないことは別**。施設内AIで診療文書を分類し、その結果の証明だけを外部へ送るなら、外部の確認者は原文を読まないが施設内AIは読む。分類処理にも平文を見せたくないなら、秘密計算や準同型暗号を併用する必要がある。

ブロックチェーンは必須ではない。証明は通常のサーバーでも検証できる。ブロックチェーンへ記録する場合は、公開項目と長期に残る情報を追加で検討する。

| 技術 | 内容を隠す対象・役割 | この目的での限界 |
|---|---|---|
| ゼロ知識証明 | 確認者へ秘密を渡さず、条件や計算を検証させる | 証明生成側のAIが平文を読む構成は可能。入力の現実の真実性、分類の意味的正しさは自動では証明されない |
| 秘密計算（MPC） | 複数の計算者に入力を分け、許容する共謀範囲内で平文を復元させず計算する | 通信・計算費用、参加者と共謀の想定、許可した出力からの漏えい |
| 準同型暗号（HE） | 暗号文のまま演算し、復号鍵を持たない計算者に平文を見せない | 対応する演算・精度・費用。結果を返す計算者の正しさの確認は別に必要 |
| 保護実行環境（TEE） | 装置内の隔離領域を用い、外部の管理者等から処理を隔離する | 領域内のAIは平文を読む。装置・実装・実行状態を信頼する範囲がある |
| 施設内AIと周辺制御 | 外部送信、権限、保存、記録を管理する | AIは平文を読む。内容を見ない暗号計算とは異なる |
| 差分プライバシー | 出力・学習結果から個人の参加等を推定するリスクを、定義した条件下で制限する | 閲覧権限や処理中の平文保護の代わりにはならない |
| 署名付き証明書の選択開示 | 信頼する発行者が保証した項目のうち必要部分だけを示す | 発行者の確認、失効、端末保護が必要。任意の条件判定には別の仕組みが必要な場合がある |

## 2. AI以外の具体例

### 2.1 EUの年齢確認：最も目的に近い公的な構成

欧州委員会は2025年7月に公開設計を提供し、2025年10月の第2版へゼロ知識証明を組み込んだ。2026年4月には技術的準備が整ったと説明する。オンラインサービスへ正確な年齢や本人情報を渡さず、年齢条件だけを確認させる。複数国が試験・国内向け調整に参加するが、**全加盟国・全利用者で本番運用済みという意味ではない**。[委員会の設計・進捗](https://digital-strategy.ec.europa.eu/en/factpages/blueprint-age-verification-solution-help-protect-minors-online)。

2026年4月29日の勧告は、加盟国が同年12月31日までに利用可能にするよう促すもの。調査日時点では将来の期限であり、実績と区別する。[勧告の説明](https://digital-strategy.ec.europa.eu/en/library/commission-sets-out-common-approach-eu-wide-age-verification-technologies)。

技術仕様の固定版 `8b9728752bd8d8eede6077ade4be8900949de2d9` の附属書Bでは、ECDSA署名を使う匿名証明書方式「Longfellow」を確認した。証明の対象は発行者の署名、必要な年齢属性、保有者の応答、期限等。接続ごとの使い捨て確認値も用いる。**発行機関は元の本人情報を確認する**。利用サイトに渡さない設計を、誰も本人情報を扱わない設計と取り違えない。[附属書B](https://github.com/eu-digital-identity-wallet/av-doc-technical-specification/blob/8b9728752bd8d8eede6077ade4be8900949de2d9/docs/annexes/annex-B/annex-B-zkp.md)。

同附属書の2026年7月更新は、外部評価で証明条件の制約不足が見つかり、修正されたと報告する。2025年時点の「未査読」という記述を現在の状況として引用しない。原理の安全性と、証明を実装するコードの安全性が別であることを示す資料。正式な標準化は進行中である。

### 2.2 Google Wallet・Sparkasse：銀行の年齢保証を必要条件へ変換

Googleは2025年7月、Sparkasseと年齢確認で協力し、ゼロ知識証明の実装を公開すると発表した。本人確認済みの銀行等から得る属性を、サービス側に必要な年齢条件へ絞って提示する構成。[Googleの発表](https://blog.google/innovation-and-ai/technology/safety-security/opening-up-zero-knowledge-proof-technology-to-promote-privacy-in-age-assurance/)。

参考になるのは、銀行が持つ本人確認情報を他のサービスへそのまま渡さない点。発表だけから全サービスでの普及数、全端末の保護、アクセス履歴の完全な非追跡性までは確認できない。EUの技術仕様と併読する。

### 2.3 INGの所得等の範囲証明：値を伏せて条件判定

INGは2017年11月、ある数値が一定範囲にあることを証明するZero-Knowledge Range Proofを公開した。給与額を明かさず住宅ローン審査等で必要な範囲条件を示す例を説明する。[銀行の原発表](https://ing.com/news/2020/07/blockchain-transactions-just-got-a-whole-lot-safer.html)。URLの年月表記と本文の発表日は異なる。

これは金融機関の技術開発・公開実装の事例であり、本文の住宅ローン説明を、そのまま本番の融資審査導入実績とは扱わない。文章の未知の機密性を理解する処理より、所得の範囲という明確な条件の証明に向く。

### 2.4 Swiss Postの電子投票：内容を隠しながら処理を確認

スイスは対象有権者を限定した電子投票の試行を実施し、システムに独立した検査を求める。[連邦官房の現況](https://www.bk.admin.ch/en/e-voting)、[独立検査](https://www.bk.admin.ch/en/examination-of-systems)。

EPFL等のプロトコル検査報告は、暗号化した投票の並べ替えや復号等の正当性を検証する証明を分析する。投票内容を公開せず、処理の検証可能性を持たせる用途で、AIを必要としない。[検査報告PDF](https://www.epfl.ch/labs/dedis/wp-content/uploads/2022/02/report-2021-3-kummer-ella_swisspostevoting.pdf)。暗号方式だけで選挙の運用全体が保証されると説明しない。

実際、2026年3月のBasel-Stadtでは2,048票を復号・集計できなかった。連邦官房は州によるPIN保護媒体の取り扱いが原因で、Swiss Postの電子投票システムとは関係がないと説明する。複数人による確認、媒体の追加、手順書の改善が対策として示された。[2026年4月17日の公式説明](https://www.bk.admin.ch/de/newnsb/Py-Tle6KOgfLZ0xglFMEz)。**証明を使っても、鍵・媒体・復旧・作業手順の管理は必要**という具体例である。

### 2.5 W3CのBBS方式：証明書の一部分を開示

**Data Integrity BBS Cryptosuites v1.0**は、署名付きの証明書から選択した項目を開示し、異なる提示の結び付けを抑える方式を定める。資格・所属・許可条件を必要な相手に必要範囲だけ示す技術基盤として読む。[2026年9月10日版](https://www.w3.org/TR/2026/CRD-vc-di-bbs-20260910/)。

この版はCandidate Recommendation Draft、すなわち勧告候補の草案。最終勧告や全製品への導入実績とは扱わない。項目を選んで開示することと、「非公開の数値が任意の範囲内である」と演算して証明することも区別する。

### 2.6 DECO・TLSNotary：既存サイトの情報を必要部分だけ証明

**DECO: Liberating Web Data Using Decentralized Oracles for TLS**（初稿2019年、ACM CCS 2020）は、既存のウェブサイトから取得した情報について、その出所と必要な条件を第三者に示す研究。[論文](https://arxiv.org/abs/1909.00938)。TLSはウェブ等の通信を保護する仕組み。本人だけが見られるサイトの応答を取り出し、単なる画面の写しではなく、当該サイトからの情報であることを秘密性を保ちながら確認させる。サーバー側の変更を必要としない点が重要である。

TLSNotaryはこの種類の出所証明・選択開示を提供する公開実装で、年齢条件の証明例も公開する。[公式説明](https://tlsnotary.org/docs/faq/)、[実装例](https://tlsnotary.org/docs/quick_start/)。標準的な通信保護だけでは第三者へ出所を証明できないため、通常の方式では秘密計算で通信鍵を分けて処理する。別方式では確認者が暗号化通信を中継し、その整合性を証明するが、信頼する通信経路の条件が変わる。

例えば銀行の残高画面を丸ごと渡さず、必要項目や条件だけを確認させる設計につながる。利用者側は平文を読む。施設の記録へ応用する場合も、「そのシステムが返した記録」であることと、「記録の医学的内容が真実」であることは異なる。公式文書の一般的な機能・公開例を、特定の病院や銀行の本番導入実績とはしない。

## 3. 医療保険の適格性：論文だけでなく公開実装を確認

**Privacy-Preserving Health Insurance Eligibility Verification on Blockchain Using zk-SNARKs**（2026年）は、診断、検査値、限度額等について条件を満たすことを証明する研究。[論文ページ](https://www.mdpi.com/2410-387X/10/5/66)。zk-SNARKは、短い証明を対話なしで検証できるゼロ知識証明方式の一群。

論文本文とPDFの直接取得は403だったため、最終本文の全評価を確認済みとはしない。一方、著者の[公開実装](https://github.com/wwarodom/zk_code)は固定版 `1a0ae9ea4f9d7fa0a9959096588a9325de4138b0` でREADME、証明条件を記述するコード、受理する契約コードを取得・静的確認した。

| 確認した内容 | 示唆・限界 |
|---|---|
| 発行機関の署名付き記録が登録集合に含まれることを検査 | 偽の自己申告だけで条件を満たす設計より強い。発行者の鍵・原本の信頼はなお必要 |
| 診断コードの対象集合、検査値の範囲、請求額と限度額を比較 | 自然言語文書全体を相手に渡す代わりに、明確な条件を証明する |
| 公開入力に請求額 `amount`、登録集合の識別値、発行者鍵、条件、受取先等が含まれる | **請求額も隠せる実装という意味ではない**。公開入力と通知に残る情報を確認する必要がある |
| 使用済み証明に対応する識別値を記録し、再利用を拒否 | 同一受付での二重利用対策。別受付・別配置への再利用対策は追加条件が必要 |
| 原構成の別配置への再利用の弱点をREADMEが明記。配置先と鎖を区別する追加構成も用意 | 修正版を選ばずに「再利用対策済み」と一般化しない |
| 評価用入力は固定の人工例、実行環境は模擬的なもの | 病院・保険会社が実患者の保険支払いへ本番導入した証拠ではない |

確認ファイルは `artifact/circuits/health_claim_core.circom`、`can20_full.circom`、`can20_full_ds.circom`、`artifact/contracts/Registry.sol` 等。実験の再実行、契約の安全性監査は行っていない。

## 4. AIの計算結果を証明する研究

### 4.1 EZKL：施設内推論の結果だけを外部へ検証させる基盤

EZKLは機械学習モデル等を証明用の計算へ変換する公開実装。入力・モデル・出力のどれを公開するかを設定し、モデルに従って計算したことを検証させる。[公式実装](https://github.com/zkonduit/ezkl)、[公式説明](https://docs.ezkl.xyz/)。

固定版 `e196b111c1bafaa61b92ae431cd3c3fe9371da05` の入力・公開項目に関わるコードを確認した。設定によって公開される項目が変わるため、「EZKLを使えば全入力・全出力が秘密」とは扱わない。外部へ証明生成を委託する場合も、生成者に渡すデータは別途確認する必要がある。

公式の医療用途説明は利用の可能性を示す例であり、特定病院の患者処理の本番実績ではない。実数演算から証明用の有限精度演算へ変換する際は、元モデルと判断が一致するかも評価する。

### 4.2 zkLLM：モデルの秘密性と入力の秘密性を区別する

**zkLLM: Zero Knowledge Proofs for Large Language Models**（ACM CCS 2024）は、大規模言語モデルの推論の正しさを効率的に証明する研究。[論文PDF](https://arxiv.org/pdf/2404.16109)。著者は130億規模のモデルで15分未満、200KB未満の証明等を報告するが、指定した処理・装置・方式での研究評価である。通常の会話全体が同条件で証明できる保証ではない。

特に、提供者の**モデルの重みを確認者から隠す**目的を含む。タイトルの「Zero Knowledge」だけで、提供者側のAIが利用者の入力を平文で読まない方式と解釈しない。PDF1～3頁の目的と方式、実験節の条件が重要。

### 4.3 ZKTorch：推論を証明へ変換する作業を一般化

**ZKTorch: Compiling ML Inference to Zero-Knowledge Proofs via Parallel Proof Accumulation**（2025年）は、複数の層・モデル構成の推論を証明用処理へ変換し、計算の証明をまとめる研究。[PDF](https://arxiv.org/pdf/2507.07031)。この調査では論文の技術提案・評価として扱い、病院・銀行の本番導入事例とはしない。

### 4.4 zkFL-Health：入力保護と正しさの証明を別の技術に担わせる

**zkFL-Health: Blockchain-Enabled Zero-Knowledge Federated Learning for Medical AI Privacy**（2025年12月、査読前）は、施設ごとの学習、保護実行環境での集約、ゼロ知識証明による集約手順の検証を組み合わせる。[PDF](https://arxiv.org/pdf/2512.21048)。

施設内のモデルは患者情報を読む。集約の入力を隠す部分は保護実行環境、所定の入力と規則を使ったことの検証はゼロ知識証明が担う。要旨は評価計画と説明する一方、本文は5病院を模した環境と数値結果を記載する。**名前のある5病院が本番運用した証拠とは扱わず、著者報告の模擬評価を伴う研究提案として読む**。PDF5～6頁の評価・制約が重要。

証明範囲も全モデルの計算ではなく、集約・付随情報の整合性と保護実行環境の保証を分けている。モデル更新が適正に集約されたことは、元の患者情報が真実であることや、悪意のある学習資料がないことの証明にはならない。本文の法令遵守に関する強い表現を、本調査が独立に確認した法的結論として採用しない。

### 4.5 全体像と標準化の現在地

**A Survey of Zero-Knowledge Proof Based Verifiable Machine Learning**（2025年）は、機械学習の検証可能性と秘密性を整理する読み物。[PDF](https://arxiv.org/pdf/2502.18535)。対象期間は主に2017～2024年で、2026年の全動向を網羅する資料ではない。

**ERC-7992: Verifiable ML Model Inference**は、モデルや入力の固定、推論結果の検証に関する提案。[原文](https://eips.ethereum.org/EIPS/eip-7992)。調査時点では草案であり、採用済みの業界標準とは説明しない。

## 5. 「平文を読まずに機密か判断したい」への適用

次の設計は資料から導いた提案であり、一つの実組織の導入構成を再現したものではない。

| 条件 | 適した構成 | 原本を読む者 |
|---|---|---|
| 既に信頼できる機密区分がある | 発行元が署名した機密区分・許可条件を、必要部分だけ証明する | 区分を決めた者。外部AI・確認者には原文を渡さない |
| 施設内AIによる平文処理は許すが、外部には渡したくない | 施設内で分類し、資料の固定値・モデル版・規則・結果に結び付く証明を外部へ送る | 施設内AIと証明生成者。外部AIは条件・結果だけ |
| 分類する計算者にも平文を見せたくない | 秘密計算または準同型暗号で分類。必要なら処理の正しさを証明する技術を追加 | 秘密計算の共謀範囲・鍵所有者等の設定による |
| 病名・検査値・所得等の条件だけが必要 | 署名付き属性から範囲・所属・資格条件を証明する | 発行機関・保有者。確認者には必要な条件だけ |
| 未知の自然言語の意味から機密性を決める | 先に分類規則・モデルと受入条件を定義し、秘密計算の対応範囲を評価する | 選択した計算方式による。ゼロ知識証明単独では実現しない |

例えば「この文書が機密ではない」とAIが出力したことを証明しても、**そのAIの分類が組織の規則として正しかったとは限らない**。証明は指定した計算をしたこと、分類評価はその計算が目的を満たすことを確認する。この二つを別に検証する。

結果と原本を結び付ける固定値には、内容を隠しながら後から変更できないようにする仕組みを使う。推測しやすい個人情報を単純なハッシュ値にするだけでは、候補を試して原文を推測される場合がある。モデル・規則の変更時も、許可された版の証明しか受理しない設計が必要。

証明を作る処理の周辺では、入力取得権限、鍵、証明の有効期限、接続ごとの確認値、失効、再利用対策、公開項目、記録を管理する。少ない情報だけを公開しても、複数回の質問や端末・通信の情報から推定される範囲は別に残る。

「zk」と呼ばれる仕組みも全て秘密を隠すわけではない。短い証明で大量の計算の正しさを確認する目的で、入力情報を公開する構成もある。[Ethereumの説明](https://ethereum.org/developers/docs/scaling/zk-rollups/)。名称より、誰が入力を持つか、何が公開されるか、何を証明するかを確認する。

## 6. 読む順序・保存

1. [NISTの54頁概説](https://csrc.nist.gov/csrc/media/presentations/2024/wpec2024-3b1/images-media/wpec2024-3b1-slides-akira-tjerand--ZKP-Overview.pdf)：証明する側と確認する側、保証する性質を理解する。講演資料であり、拘束力のある規格ではない。
2. EU年齢確認の説明と技術仕様附属書B：必要条件だけを示す公的な構成、署名・期限・実装評価の関係を読む。
3. ING、Swiss Post、医療保険の公開実装：金融、投票、医療の異なる条件と運用制約を比較する。
4. EZKL、zkLLM、ZKTorchと総説：AIの計算証明と入力の秘密性の違いを読む。
5. W3C草案とERC草案：標準化の範囲と成熟度を確認する。
